# GatewayService — WebSocket-интерфейс

## Общая информация

WebSocket используется для двунаправленной связи между фронтендом и сервером в реальном времени. Все WebSocket-соединения устанавливаются через GatewayService.

---

## Каналы WebSocket

### Чат с оркестратором

**Путь:** `/ws/chat/{user_id}`

**Назначение:** Интерактивное управление роем через естественный язык. Пользователь отправляет текстовые команды, получает потоковые ответы и обновления статуса выполнения.

**Аутентификация:** JWT-токен передаётся при установке соединения (в query-параметре `token` или в первом сообщении).

**Процесс взаимодействия:**

1. Клиент устанавливает WebSocket-соединение
2. Клиент отправляет текстовое сообщение (JSON)
3. GatewayService публикует команду в RabbitMQ (очередь Orchestrator)
4. Orchestrator обрабатывает команду через LangGraph, генерирует обновления на каждом шаге
5. Обновления передаются через Redis Pub/Sub → GatewayService → WebSocket → клиент
6. Клиент получает потоковые обновления: анализ, планирование, выполнение

**Типы сообщений от клиента:**
- `chat_message` — текстовая команда пользователя
- `cancel_task` — отмена текущей задачи
- `ping` — heartbeat

**Типы сообщений от сервера:**
- `state_update` — обновление состояния обработки (шаг LangGraph, прогресс)
- `chat_response` — текстовый ответ от LLM (потоковый или финальный)
- `action` — информация о конкретном действии, отправленном роботу
- `error` — ошибка обработки
- `pong` — ответ на heartbeat

---

### Телеметрия робота

**Путь:** `/ws/robots/{robot_id}/telemetry`

**Назначение:** Потоковая передача текущего состояния конкретного робота для отображения на дашборде.

**Аутентификация:** JWT-токен.

**Процесс:**

1. Клиент подписывается на телеметрию конкретного робота
2. GatewayService подписывается на Redis Pub/Sub канал `robot:{robot_id}:updates`
3. При каждом обновлении телеметрии (из MQTT → Redis) — данные пересылаются клиенту
4. Частота обновлений: до 30 Гц (каждые ~33 мс)

**Структура сообщений от сервера:**
- Тип `telemetry` — содержит: позицию (x, y, z, ориентация), скорость, заряд батареи, статус, данные сенсоров
- Тип `detection` — результаты детекции объектов (если активна обработка через Triton)

### Визуализация роя

**Путь:** `/ws/swarm/visualization`

**Назначение:** Агрегированные данные обо всём рое для 3D-визуализации. Передаёт позиции всех роботов, обнаруженные объекты и активные задачи.

**Аутентификация:** JWT-токен.

**Частота обновлений:** 10 Гц (каждые 100 мс)

**Структура сообщений:**
- Массив роботов: для каждого — `id`, позиция, ориентация, статус, текущая задача
- Массив обнаруженных объектов: класс, позиция, робот-обнаружитель
- Массив маршрутов: запланированные траектории роботов
- Метаданные: количество активных роботов, количество задач

**Оптимизация трафика:**
- Передаются только изменения (delta updates) после первоначального полного состояния
- Бинарный формат для минимизации объёма (MessagePack)
- Прореживание данных при медленном соединении клиента

## Управление соединениями

### Жизненный цикл соединения

1. **Установка** — клиент отправляет HTTP Upgrade запрос с JWT-токеном
2. **Аутентификация** — GatewayService проверяет токен, извлекает `user_id` и `role`
3. **Регистрация** — соединение регистрируется во внутреннем реестре (в памяти + Redis для кросс-pod обнаружения)
4. **Активная фаза** — обмен сообщениями
5. **Heartbeat** — ping/pong каждые 30 секунд для поддержания соединения
6. **Закрытие** — при отключении клиента, таймауте или ошибке — корректное закрытие, дерегистрация, очистка подписок

### Обработка переподключений

- Клиент при потере соединения автоматически переподключается с экспоненциальным backoff (1 с, 2 с, 4 с, максимум 30 с)
- При переподключении клиент отправляет `last_message_id` для получения пропущенных обновлений
- GatewayService хранит последние N сообщений для каждого канала в Redis (буфер переподключения)

### Кросс-pod маршрутизация

При горизонтальном масштабировании GatewayService (несколько pod'ов):
- Каждый pod подписывается на Redis Pub/Sub для получения обновлений
- Обновление, сгенерированное в любом месте системы, доставляется всем pod'ам
- Каждый pod пересылает обновление только тем клиентам, которые к нему подключены
- Sticky Sessions (Session Affinity) на уровне Ingress минимизируют необходимость кросс-pod маршрутизации

## Ограничения

| Параметр | Значение |
|----------|---------|
| Максимальный размер сообщения | 1 МБ |
| Максимум соединений на pod | 5 000 |
| Таймаут неактивности | 5 минут (без heartbeat) |
| Буфер переподключения | 100 последних сообщений на канал |
| Максимум подписок на клиента | 50 (роботов) |
