# SmolVLA — Edge-версия

## Варианты Edge-развёртывания

SmolVLA на edge может развёртываться в двух вариантах:

- **Полная модель (450M)**: базовая модель `lerobot/smolvla_base` запускается напрямую на edge-устройстве. Требует ~2 ГБ GPU-памяти (BF16). Рекомендуется для Jetson AGX Orin и Orin NX 16GB.
- **Дистиллированная модель (150M)**: компактная версия, созданная через Knowledge Distillation от полной модели. Используется, когда ресурсы ограничены (Jetson Orin Nano 8GB).

### Характеристики полной Edge-модели

| Параметр | Значение |
|----------|---------|
| HuggingFace ID | `lerobot/smolvla_base` |
| Параметры | ~450 миллионов |
| Vision Encoder | SigLIP-SO400M |
| Language Encoder | SmolLM2-135M |
| Action Decoder | Transformer + Flow Matching (10 denoising steps) |
| Вход (изображение) | 224×224×3, 1–3 кадра с нескольких камер |
| Вход (текст) | Инструкция задачи |
| Вход (состояние) | Сенсомоторное состояние (позиции суставов) |
| Выход | Chunk из 10–50 действий (настраивается через actions_per_chunk) |
| GPU Memory | ~2 ГБ (BF16), ~1 ГБ (INT8) |
| Формат | PyTorch (основной), ONNX, TensorRT (оптимизированный) |

### Характеристики дистиллированной Edge-модели

| Параметр | Значение |
|----------|---------|
| Параметры | ~150 миллионов |
| Vision Encoder | SigLIP-small (22M) |
| Language Encoder | Компактный (встроенный) |
| Action Decoder | Transformer (уменьшенный) + Flow Matching |
| Вход (изображение) | 224×224×3, 1–2 кадра |
| Вход (текст) | Инструкция до 128 токенов |
| Выход | Chunk из 5 действий (7-DoF) |
| Латентность | ~100 мс (Jetson Orin NX), ~200 мс (Jetson Orin Nano) |
| Память | ~800 MB (FP16), ~400 MB (INT8) |
| Формат | ONNX (основной), TensorRT (оптимизированный) |

## Оптимизации для Edge

> **Примечание**: полная модель SmolVLA (450M) требует лишь ~2 ГБ GPU-памяти, что позволяет запускать её напрямую на Jetson Orin NX/AGX без дистилляции. Оптимизации ниже применяются для создания дистиллированной версии (150M) или для дополнительного ускорения полной модели.

### Сокращение параметров (для дистиллированной версии)

Edge-версия уменьшена с 450M до 150M параметров через:

- **Knowledge Distillation**: обучение компактной модели на «мягких метках» от полной cloud-версии
- **Pruning**: удаление наименее значимых параметров (structured pruning — удаление целых attention heads и FF-подслоёв)
- **Уменьшение размерности**: сокращение embedding dimension и числа transformer-слоёв

### Квантизация

- **INT8**: квантизация до 8-бит с калибрацией на целевом датасете. Потеря точности < 3%. Рекомендуется для Jetson Orin Nano
- **FP16**: половинная точность. Рекомендуется для Jetson Orin NX (достаточно памяти)
- **Dynamic Quantization**: квантизация только весов (не активаций), проще в настройке

### Layer Skipping

Техника адаптивного пропуска слоёв transformer в зависимости от сложности задачи:

- Для простых задач (прямолинейное движение) используются только первые N слоёв
- Для сложных задач (точный захват) задействуются все слои
- Решение о пропуске принимается на основе внутреннего confidence score после каждого слоя
- Это позволяет снизить латентность для простых задач до 50 мс

### Visual Token Reduction

Для edge-версии количество визуальных токенов сокращено:

- Average Pooling: визуальные патчи объединяются (2×2 → 1), сокращая число токенов в 4 раза
- Attention-based Selection: выбираются только наиболее информативные визуальные токены (по attention score)
- Уменьшение числа входных кадров: 1 кадр вместо 3 (cloud)

## Развёртывание на Jetson

### Аппаратные требования

| Платформа | GPU Memory | CPU | RAM | Поддержка |
|-----------|-----------|-----|-----|-----------|
| Jetson Orin NX 16GB | 16 GB (shared) | 8 cores | 16 GB | Основная платформа |
| Jetson Orin Nano 8GB | 8 GB (shared) | 6 cores | 8 GB | С квантизацией INT8 |
| Jetson AGX Orin 32GB | 32 GB (shared) | 12 cores | 32 GB | Полная поддержка |

### Формат модели

Для Jetson рекомендуется TensorRT:

1. Модель конвертируется из ONNX в TensorRT на целевом устройстве (или на устройстве с идентичным GPU)
2. TensorRT оптимизирует граф вычислений под конкретное оборудование
3. Ускорение: 2–3x по сравнению с ONNX Runtime
4. Ограничение: TensorRT-план не переносим между разными GPU-архитектурами

### Процесс развёртывания

1. Модель в формате ONNX загружается из MinIO (OTA-обновление)
2. На устройстве выполняется конвертация в TensorRT (один раз, ~5–10 мин)
3. TensorRT-план кэшируется локально
4. При обновлении модели — повторная конвертация

## Async Inference на Edge (RobotClient)

### Архитектура PolicyServer / RobotClient

LeRobot предоставляет архитектуру асинхронного inference, которая разделяет процессы inference и исполнения действий:

- **PolicyServer** — сервис, выполняющий inference модели. Может работать как на cloud GPU, так и локально на edge-устройстве. Слушает подключения на настраиваемом хосте/порте.
- **RobotClient** — клиент на стороне робота. Отправляет наблюдения (изображения + состояние) на PolicyServer и получает в ответ chunk действий. Исполняет действия на роботе без ожидания следующего inference.

### Принцип «ноль простоев»

Ключевое преимущество async-архитектуры — робот **никогда не простаивает** в ожидании inference:

1. RobotClient собирает наблюдение (изображение + joint states)
2. Отправляет наблюдение на PolicyServer (локальный или облачный)
3. Продолжает исполнять действия из текущего буфера, не дожидаясь ответа
4. Когда PolicyServer возвращает новый chunk — RobotClient добавляет его в буфер
5. Перекрывающиеся действия из старого и нового chunk объединяются через **weighted_average** агрегацию

### Настройка Action Chunking на Edge

| Параметр | Диапазон | Описание |
|----------|---------|----------|
| `actions_per_chunk` | 10–50 | Количество действий, запрашиваемых за один inference. Низкие значения (10–15) — для быстрого отклика на изменения. Высокие (30–50) — для стабильных сценариев |
| `chunk_size_threshold` | 0.5–0.7 | Доля оставшихся действий в буфере, при которой запускается новый inference. Значение 0.5 — запрос нового chunk, когда исполнена половина текущего |

**Рекомендации для Edge:**

- Для задач с частыми изменениями среды (мобильный робот в динамическом окружении): `actions_per_chunk=10–15`, `chunk_size_threshold=0.7`
- Для стабильных задач манипуляции (конвейер, повторяющиеся действия): `actions_per_chunk=30–50`, `chunk_size_threshold=0.5`
- При нестабильной сетевой связи (cloud inference): увеличить `actions_per_chunk` до 50 — больший буфер компенсирует задержки сети

### Edge-only vs Edge-Cloud Async

- **Edge-only**: PolicyServer запущен на самом Jetson. Минимальная латентность, но ограничен ресурсами одного устройства.
- **Edge-Cloud**: PolicyServer в облаке (на GPU-кластере), RobotClient на Jetson. Позволяет использовать полную модель (450M) или даже X-VLA (900M) без нагрузки на edge. Буфер действий компенсирует сетевую задержку до 200–500 мс.

## Интеграция камер (LeRobot Camera API)

### Поддерживаемые бэкенды камер

LeRobot предоставляет унифицированную абстракцию для работы с камерами, интегрируемую напрямую в Edge AI Proxy:

| Бэкенд | Описание | Применение |
|--------|----------|------------|
| **OpenCVCamera** | USB и встроенные камеры через OpenCV | Универсальное подключение, простые USB-камеры |
| **ZMQCamera** | Потоковая передача через ZeroMQ (zero-copy) | Разделение процессов камеры и inference на edge |
| **RealSenseCamera** | Intel RealSense D400 (глубина + RGB) | Задачи с 3D-восприятием, определение расстояния до объектов |
| **Reachy2Camera** | Встроенные камеры робота Reachy2 | Специфичные платформы |

### Режимы чтения кадров

| Режим | Поведение | Когда использовать |
|-------|-----------|--------------------|
| `read()` | Блокирующее чтение — ждёт новый кадр | Синхронный цикл управления с фиксированной частотой |
| `async_read()` | Неблокирующее — возвращает последний доступный кадр | **Рекомендуется для edge** — inference не блокируется камерой |
| `read_latest()` | Возвращает самый свежий кадр, отбрасывая промежуточные | Когда важна актуальность кадра, а не каждый кадр (10 FPS inference при 30 FPS камере) |

### Мульти-камерная конфигурация

SmolVLA поддерживает до 3 камер одновременно (в соответствии с архитектурой полной модели). На edge типичные конфигурации:

- **1 камера**: фронтальная камера на end-effector — минимальная задержка, достаточно для простых задач
- **2 камеры**: фронтальная + верхняя обзорная — улучшенное пространственное восприятие
- **3 камеры**: фронтальная + обзорная + wrist-камера — максимальная точность для прецизионных задач

Каждая камера может использовать свой бэкенд (например, RealSense для глубины + OpenCV для обзорной).

### ZMQ для распределённого Edge

ZMQCamera позволяет разделить процессы камеры и inference на разные устройства или процессы:

- Процесс-публикатор захватывает кадры и отправляет через ZeroMQ (zero-copy)
- Процесс-подписчик (Edge AI Proxy) получает кадры без копирования в память
- Это снижает нагрузку на CPU, когда inference GPU-bound
- Полезно при сложной предобработке кадров (resize, crop) — выполняется в отдельном процессе

## Режимы работы на Edge

### Онлайн-режим (связь с облаком)

- Edge SmolVLA выполняет реактивное управление (текущий chunk)
- Параллельно cloud SmolVLA планирует следующие chunk'и
- Edge корректирует действия на основе локальных наблюдений
- При расхождении > порога — запрос к cloud за новым планом

### Оффлайн-режим (без связи)

- Edge SmolVLA работает полностью автономно
- Генерирует все chunk'и самостоятельно
- Использует локальный кэш инструкций и карту окружения
- Ограниченная сложность задач (только те, на которых модель обучена)
- При восстановлении связи — синхронизация состояния с облаком

### Гибридный режим

- Edge обрабатывает текущие действия с минимальной латентностью
- Cloud обеспечивает дальний горизонт планирования
- Если cloud-ответ не пришёл вовремя — edge продолжает автономно
- Если пришёл — edge корректирует траекторию

## Взаимодействие с ROS 2 Jazzy

### Управляющий цикл

Edge SmolVLA интегрируется в ROS 2 Jazzy control loop через Edge Bridge (см. RobotEdge/03-ROS2-Bridge):

1. **Подписка на топик камеры**: получение изображений через LeRobot Camera API (async_read) или ROS 2 image topics
2. **Подписка на joint_states**: текущее состояние манипулятора (сенсомоторный вход)
3. **Inference (локальный или async)**: генерация chunk действий через PolicyServer (локальный или облачный)
4. **Публикация в cmd_vel / joint_trajectory**: команды для контроллеров
5. **Обратная связь**: получение результата выполнения для следующей итерации

### Частота управления с учётом Async Inference

- SmolVLA inference (при `actions_per_chunk=10`): ~5–10 Hz (зависит от устройства)
- Action execution: 30–50 Hz (интерполяция между действиями в chunk)
- Визуальная обратная связь: 10–30 Hz (от камеры)

При async-режиме частота inference **не ограничивает** частоту исполнения — робот непрерывно исполняет действия из буфера. Новый chunk запрашивается при `chunk_size_threshold`.

### Foxglove Bridge для отладки

На каждом edge-устройстве работает Foxglove Bridge (порт 8765), обеспечивающий визуализацию:

- Изображения с камер (observation.image)
- Текущие действия из буфера SmolVLA
- Joint states робота
- Debugging через VNC (порт 5900) — для визуального контроля на безголовых устройствах

## Безопасность на Edge

### Ограничения действий

Все действия, сгенерированные SmolVLA, проходят через фильтр безопасности:

- **Ограничение скорости**: максимальная скорость перемещения ограничена (настраиваемый параметр)
- **Ограничение рабочей зоны**: действия за пределами допустимой зоны отклоняются
- **Ограничение силы**: для роботов с силомоментным датчиком — максимальное усилие
- **Плавность**: резкие изменения действий сглаживаются фильтром

### Watchdog

Независимый watchdog-процесс контролирует работу SmolVLA:

- Если inference не выполнен за 500 мс — аварийная остановка
- Если генерируемые действия аномальны (magnitude > порог) — остановка
- Если камера не даёт изображения > 1 сек — остановка и переход в безопасную позицию

### Локальные метрики

| Метрика | Описание |
|---------|----------|

| smolvla_edge_gpu_temp | Температура GPU (°C) |

### Передача метрик в облако

Метрики накапливаются локально и передаются в Prometheus через MQTT при наличии связи. При оффлайн-режиме метрики буферизуются и отправляются при восстановлении связи.
