# vLLM Service — Текстовые модели

## Qwen2.5-7B-Instruct

### Характеристики

| Параметр | Значение |
|----------|---------|
| Архитектура | Transformer (decoder-only) |
| Параметры | 7 миллиардов |
| Контекстное окно | 32 768 токенов |
| Словарь | ~150 000 токенов |
| Точность | BF16 (основной), AWQ INT4 (опционально) |
| GPU Memory | ~14 GB (BF16), ~5 GB (INT4) |
| Языки | Мультиязычная (русский, английский и др.) |

### Выбор модели

Qwen2.5-7B-Instruct выбрана по следующим критериям:

- **Производительность**: на уровне GPT-3.5 по большинству бенчмарков при 7B параметрах
- **Инструкционное следование**: отличное следование сложным инструкциям и системным промптам
- **Tool Calling**: нативная поддержка вызова функций (tools) в формате, совместимом с OpenAI
- **Мультиязычность**: качественная работа с русским и английским языками
- **Размер**: помещается на одном GPU A10G (24GB) с запасом для KV-кэша

## Системные промпты

### Промпт Orchestrator

Системный промпт для Orchestrator определяет модель как AI-планировщика роботизированного роя. В нём указаны: роль модели (планировщик задач для роя роботов), доступные инструменты (tools), формат ответа (структурированный JSON), ограничения (безопасность, приоритеты, ресурсы).

Промпт включает описание типов роботов, их возможностей, ограничений по батарее и грузоподъёмности, а также правила декомпозиции сложных задач на подзадачи.

### Промпт Planning Agent

Planning Agent использует специализированный промпт, который определяет: формат плана действий (последовательность шагов с условиями перехода), доступные примитивы действий (move_to, pick_up, place, inspect, patrol, charge), правила расстановки приоритетов, обработку зависимостей между задачами.

### Промпт Safety Agent

Safety Agent получает промпт с акцентом на: распознавание опасных ситуаций, оценку рисков по шкале 1–10, правила экстренного реагирования, приоритет безопасности людей над выполнением задач.

### Промпт Chat Agent

Для пользовательского чата используется промпт, который определяет: дружелюбный и информативный стиль общения, способность объяснять действия роботов простым языком, формирование ответов на основе текущего состояния системы, ограничения (не выполнять опасные операции через чат без подтверждения).

## Tool Calling

### Механизм

Qwen2.5-7B-Instruct поддерживает Tool Calling в формате OpenAI:

1. В запросе передаётся список доступных tools (функций) с описанием параметров
2. Модель анализирует запрос пользователя
3. Если нужна информация или действие — модель генерирует вызов tool с параметрами
4. Результат выполнения tool передаётся обратно модели
5. Модель формирует финальный ответ с учётом результатов

### Доступные Tools для Orchestrator

| Tool | Описание | Параметры |
|------|----------|-----------|
| get_robot_status | Получить статус конкретного робота | robot_id |
| get_all_robots | Список всех роботов с состоянием | filters (optional) |
| create_task | Создать задачу для робота | task_type, target, robot_id, priority |
| get_scene_analysis | Получить анализ сцены от Triton | robot_id, pipeline_type |
| check_battery | Проверить уровень заряда | robot_id |
| get_map_data | Получить данные карты/зон | zone_id (optional) |
| emergency_stop | Экстренная остановка | robot_id или "all" |
| get_task_history | История задач | robot_id, time_range |

### Цепочки вызовов (Multi-step Tool Calling)

Модель может выполнять несколько последовательных вызовов tools для сбора информации:

1. Пользователь: «Отправь робота с лучшим зарядом на склад»
2. Модель вызывает: get_all_robots(filters={"status": "idle"})
3. Получает список роботов → выбирает робота с max battery
4. Модель вызывает: create_task(task_type="navigate", target="warehouse", robot_id="robot_5")
5. Получает подтверждение → формирует ответ пользователю

### Параллельные вызовы

Модель также поддерживает параллельные вызовы tools, когда запросы независимы. Например, одновременный запрос статуса нескольких роботов для сравнения.

## Параметры генерации

### Настройки по контексту

| Контекст | temperature | top_p | max_tokens | Обоснование |
|----------|-------------|-------|------------|-------------|
| Планирование задач | 0.1 | 0.9 | 2048 | Детерминированность, точность |
| Tool Calling | 0.0 | 1.0 | 512 | Максимальная точность вызовов |
| Чат с пользователем | 0.7 | 0.95 | 1024 | Естественность, разнообразие |
| Оценка безопасности | 0.0 | 1.0 | 512 | Детерминированность |
| Суммаризация | 0.3 | 0.9 | 2048 | Точность с умеренной вариативностью |

### Stop-последовательности

Для каждого типа запроса настроены stop-последовательности, которые прекращают генерацию при достижении логического конца ответа. Это экономит GPU-ресурсы и предотвращает «галлюцинации» после завершения полезной части ответа.

### Контекстное окно

Общий бюджет контекстного окна (32768 токенов) распределяется:

- **Системный промпт**: ~2000–4000 токенов
- **Tool definitions**: ~1000–2000 токенов
- **История диалога / контекст задачи**: ~10000–20000 токенов
- **Результаты tool calls**: ~5000–10000 токенов
- **Генерация ответа**: ~2000–4000 токенов

При превышении контекстного окна используется стратегия усечения: сначала удаляются старые сообщения из истории, затем — детали из промежуточных результатов, системный промпт не усекается никогда.

## Streaming

### Реализация

vLLM поддерживает streaming через Server-Sent Events (SSE):

1. Клиент отправляет запрос с параметром stream=true
2. vLLM начинает генерацию и отправляет каждый токен (или группу токенов) как SSE-событие
3. Клиент получает и отображает токены по мере генерации
4. По завершении отправляется финальное событие с метаданными (usage, finish_reason)

### Применение

- **Чат-интерфейс**: пользователь видит ответ по мере генерации, как в ChatGPT
- **Планирование**: Orchestrator получает план по мере генерации и может начать подготовку ещё до завершения
- **Мониторинг**: streaming позволяет отслеживать прогресс длительных генераций

### Буферизация

Для оптимизации токены группируются в буферы по 5–10 штук перед отправкой, что снижает overhead SSE при сохранении ощущения потоковости.

## Кэширование

### Prefix Caching

vLLM поддерживает кэширование KV-кэша для общих префиксов запросов. Это особенно эффективно для данной системы, так как:

- Системные промпты одинаковы для всех запросов одного типа
- Tool definitions повторяются в каждом запросе
- Это сокращает Time-to-First-Token на 30–50% для повторных запросов

### Redis-кэш ответов

Для идентичных запросов (например, запрос статуса системы, который не изменился) используется кэширование в Redis:

- Ключ: хэш от (промпт + параметры генерации)
- TTL: 5–30 секунд (зависит от типа запроса)
- Инвалидация: при изменении состояния системы

## Квантизация

### AWQ INT4

Для сценариев с ограниченной GPU-памятью (A10G 24GB) модель может быть квантизована до INT4 через AWQ:

- Снижение использования памяти с ~14GB до ~5GB
- Потеря качества: < 2% по бенчмаркам
- Позволяет загрузить обе модели (текстовую и мультимодальную) на один GPU
- vLLM имеет встроенную поддержку AWQ

### GPTQ

Альтернативный метод квантизации, также поддерживаемый vLLM. Может быть предпочтителен для некоторых моделей. Выбор между AWQ и GPTQ определяется результатами тестирования на целевых задачах.

### BitsAndBytes (QLoRA)

Третий метод квантизации, поддерживаемый vLLM — BitsAndBytes. Особенно ценен в сочетании с LoRA-адаптерами (паттерн QLoRA):

- Поддержка 4-bit и 8-bit квантизации
- Основное преимущество — нативная совместимость с QLoRA: базовая модель квантизирована, а LoRA-адаптер работает в полной точности
- Не требует предварительной квантизации модели — выполняется «на лету» при загрузке
- Подходит для экспериментов и быстрого прототипирования (не нужна отдельная квантизированная версия модели)

### Сравнение методов квантизации

| Метод | Precision | Предварительная подготовка | Совместимость с LoRA | Рекомендуемый сценарий |
|-------|-----------|---------------------------|---------------------|----------------------|
| AWQ | INT4 | Требуется квантизированная модель | Да | Production с фиксированной моделью |
| GPTQ | INT4 | Требуется квантизированная модель | Да | Production, альтернатива AWQ |
| BitsAndBytes | INT4/INT8 | Не требуется (on-the-fly) | Да (нативный QLoRA) | Прототипирование, QLoRA-эксперименты |

## LoRA-адаптеры для текстовой модели

### Конфигурация vLLM для LoRA

Для активации поддержки LoRA в vLLM задаются параметры движка:

| Параметр | Значение | Описание |
|----------|---------|----------|
| `enable_lora` | `True` | Активация поддержки LoRA |
| `max_lora_rank` | 64 | Максимально допустимый ранг адаптера |
| `max_loras` | 4 | Максимальное число одновременно загруженных адаптеров |

### Загрузка адаптеров

LoRA-адаптеры загружаются из HuggingFace Hub или из локальной директории. Каждый адаптер идентифицируется тройкой: уникальное имя (строка), числовой идентификатор, путь к директории с весами адаптера.

vLLM поддерживает **per-request LoRA** — каждый запрос к движку может указывать собственный LoRA-адаптер. Это позволяет одному экземпляру vLLM обслуживать запросы с разными специализациями:

- Запрос от Planning Agent → адаптер, обученный на робототехническом планировании
- Запрос от Chat Agent → адаптер, обученный на диалоговых данных
- Запрос от Safety Agent → адаптер, обученный на оценке рисков
- Запрос без адаптера → базовая модель без LoRA

### Совместная работа с квантизацией

vLLM поддерживает одновременное использование квантизации и LoRA. Проверенные комбинации:

| Базовая модель | Квантизация | LoRA-адаптер | Пример |
|---------------|-------------|-------------|---------|
| LLaMA 7B | BitsAndBytes | QLoRA | Минимальный расход памяти, быстрое прототипирование |
| TinyLlama 1.1B AWQ | AWQ | LoRA | Production-оптимизированная конфигурация |
| TinyLlama 1.1B GPTQ | GPTQ | LoRA | Альтернатива AWQ |

При использовании квантизации с LoRA базовая модель загружается квантизированной, а LoRA-адаптер применяется в полной точности (FP16/BF16). Это обеспечивает значительную экономию памяти при сохранении качества адаптации.

### Управление памятью при работе с LoRA

При загрузке нескольких LoRA-адаптеров необходимо учитывать дополнительный расход GPU-памяти. Каждый адаптер занимает от десятков до сотен мегабайт в зависимости от ранга и архитектуры модели. При переключении между конфигурациями (разные комбинации модель + квантизация) рекомендуется явная очистка GPU-памяти через сборщик мусора и освобождение CUDA-кэша для предотвращения утечек памяти.
