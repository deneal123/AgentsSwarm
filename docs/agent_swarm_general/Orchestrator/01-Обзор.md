# Orchestrator — Обзор

## Назначение

Orchestrator — центральный микросервис системы, выполняющий роль «мозга». Он отвечает за интерпретацию пользовательских команд, планирование задач, распределение работы между роботами, координацию мультиагентных взаимодействий и мониторинг выполнения.

---

## Зона ответственности

- Приём и интерпретация команд пользователя (через RabbitMQ из GatewayService)
- Вызов AI-моделей для анализа ситуации (vLLM, Triton, SmolVLA)
- Генерация планов выполнения задач
- Декомпозиция планов на подзадачи
- Назначение подзадач конкретным роботам с учётом их возможностей и состояния
- Отправка команд роботам через MQTT
- Мониторинг выполнения задач и перепланирование при необходимости
- Управление состоянием роя (через Redis Feature Store)
- Координация между роботами при совместных задачах
- Хранение истории задач и решений в PostgreSQL

## Технологический стек

| Компонент | Технология | Назначение |
|-----------|------------|-----------|
| Язык | Python 3.11+ | Основной язык разработки |
| Очереди задач | Celery | Распределённое выполнение и планирование задач |
| Граф состояний | LangGraph (StateGraph, Functional API) | Управление многошаговыми процессами планирования с типизированным состоянием, чекпоинтингом, подграфами и Send API |
| Мультиагенты | Open-Agent SDK (OpenAI Agents Python SDK) | Агентная архитектура: агенты, инструменты, handoffs, guardrails, контекст, lifecycle hooks |
| Брокер задач | RabbitMQ | Очереди для Celery и событийный обмен |
| Хранение состояний | Redis | Кэш, Feature Store, Pub/Sub, RedisSaver (чекпоинтинг), RedisStore (долгосрочная память) |
| Хранение истории | PostgreSQL | Задачи, инциденты, аудит, PostgresSaver (чекпоинтинг), PostgresStore (долгосрочная память) |

## Внутренняя архитектура

### Компоненты Orchestrator

**TaskManager** (на базе Celery)
- Управляет жизненным циклом задач: создание → назначение → выполнение → завершение
- Распределяет задания между Celery workers
- Отслеживает таймауты и неуспешные выполнения
- Реализует retry-логику и dead-letter обработку

**ResourceManager** (на базе Celery)
- Ведёт реестр доступных ресурсов роботов (из Redis)
- Учитывает возможности каждого робота: тип, наличие манипулятора, камеры, текущий заряд
- Принимает решения о назначении: какой робот лучше всего подходит для данной задачи
- Балансирует нагрузку между роботами

**CoordinationManager**
- Координирует совместные действия нескольких роботов
- Реализует алгоритмы роевого интеллекта: распределение зон поиска, избегание столкновений, формирование
- Отслеживает взаимные позиции роботов и предотвращает конфликты

**LangGraph Engine**
- StateGraph с типизированным состоянием (SwarmState на основе TypedDict) и функциями-редьюсерами
- Паттерны: prompt chaining, parallelization, routing, orchestrator-worker (Send API), evaluator-optimizer
- Чекпоинтинг через PostgresSaver (продакшн) и RedisSaver для устойчивости к сбоям
- Подграфы для модульной декомпозиции (по типам задач, для планирования, для агентов)
- Долгосрочная память через PostgresStore с семантическим поиском (эмбеддинги успешных планов)
- Стриминг промежуточных результатов для реалтайм-обновлений Dashboard UI
- Functional API (entrypoint/task) для вспомогательных задач (проверка здоровья, фоновая обработка)
- Подробнее: [LangGraph-движок](02-LangGraph-движок.md)

**Open-Agent SDK Integration**
- Мультиагентная архитектура с типизированными агентами (name, instructions, tools, handoffs, guardrails, output_type)
- Два паттерна взаимодействия: Manager (agents-as-tools) на уровне LangGraph узлов + Handoffs (peer-делегация) внутри агентного цикла
- Guardrails: входные, выходные и tool-барьеры с механизмом tripwire для экстренного прерывания
- RunContextWrapper (SwarmContext) для dependency injection: Redis, PostgreSQL, MQTT, gRPC-клиенты
- Human-in-the-loop через interruptions для критических действий (emergency_stop)
- Lifecycle hooks для трассировки, метрик и публикации событий
- Подробнее: [Open-Agent SDK](03-Open-Agent-SDK.md)

## Масштабирование

### Горизонтальное масштабирование

- **Celery Workers** — основная единица масштабирования. Каждый worker обрабатывает задачи из очереди RabbitMQ независимо
- **Шардирование** — роботы могут быть разделены на группы (зоны, типы), каждая группа обрабатывается отдельным набором workers
- **Leader Election** — для координационных задач (глобальное перепланирование, управление конфликтами) используется leader election через Redis (Redlock)

### Stateless-принцип

Orchestrator не хранит состояние в памяти процесса. Всё состояние хранится в:
- **Redis** — текущие состояния роботов, активные планы, промежуточные результаты, RedisSaver (чекпоинтинг LangGraph для быстрого доступа), RedisStore (долгосрочная память)
- **PostgreSQL** — историческая информация, задачи, аудит, PostgresSaver (основной чекпоинтинг LangGraph с транзакционной целостностью), PostgresStore (долгосрочная память с семантическим поиском)
- **RabbitMQ** — очереди задач и промежуточных сообщений
- **SQLite (AdvancedSQLiteSession)** — управление историей диалогов с поддержкой ветвления для пользовательских сессий

Это позволяет перезапускать или масштабировать workers без потери данных. При сбое worker'а LangGraph автоматически восстанавливает выполнение графа с последнего чекпоинта по thread_id.

## Обработка ошибок

### Уровни устойчивости

1. **Retry** — автоматический повтор задач при временных ошибках (сеть, таймаут). Экспоненциальный backoff, максимум 3 попытки
2. **Fallback** — при недоступности vLLM — использование предопределённых шаблонов команд; при недоступности Triton — работа по последним известным данным
3. **Dead Letter Queue** — задачи, которые не удалось выполнить после всех повторов, отправляются в DLQ для ручного анализа
4. **Circuit Breaker** — при систематических отказах AI-сервисов — временное прекращение запросов с периодической проверкой доступности
5. **Guardrails (Open-Agent SDK)** — входные, выходные и tool-барьеры с механизмом tripwire для экстренного прерывания при обнаружении критических нарушений безопасности
6. **Checkpointing (LangGraph)** — автоматическое сохранение состояния графа через PostgresSaver; при сбое worker'а другой worker восстанавливает обработку с последнего чекпоинта по thread_id
7. **Max Turns / Iteration Count** — защита от зацикливания: max_turns в агентном цикле Open-Agent SDK и iteration_count в графе LangGraph; при превышении — принудительное завершение с ошибкой
