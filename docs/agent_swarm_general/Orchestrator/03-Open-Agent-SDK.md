# Orchestrator — Open-Agent SDK

## Назначение

Open-Agent SDK (OpenAI Agents Python SDK) интегрируется в Orchestrator для организации мультиагентной архитектуры. SDK предоставляет полноценный фреймворк для определения агентов, их инструментов, механизмов делегации (handoffs), защитных барьеров (guardrails), управления контекстом и жизненным циклом выполнения. Каждый агент специализируется на определённом аспекте управления роем и работает в агентном цикле: LLM анализирует ситуацию → вызывает инструменты → получает результаты → принимает следующее решение.

## Определение агентов (Agent)

### Структура агента

Каждый агент в системе определяется набором свойств:

| Свойство | Описание | Применение в системе |
|----------|----------|---------------------|
| **name** | Уникальное имя агента | Идентификация в логах, трассировке и при handoff |
| **instructions** | Системный промпт, определяющий поведение | Описание роли, возможностей и ограничений |
| **tools** | Набор доступных инструментов | Функции для взаимодействия с сервисами и данными |
| **handoffs** | Список агентов, которым можно делегировать | Определяет граф делегации между агентами |
| **model** | Модель LLM для данного агента | Выбор модели в зависимости от задачи |
| **model_settings** | Настройки модели (temperature, top_p, max_tokens и др.) | Тонкая настройка поведения LLM |
| **guardrails** | Входные и выходные защитные барьеры | Валидация данных и безопасность |
| **output_type** | Структурированный тип выходных данных | Обеспечение типобезопасности ответов |
| **tool_use_behavior** | Стратегия использования инструментов | Контроль обязательности вызова инструментов |

### Динамические инструкции (Dynamic Instructions)

Инструкции агента могут быть определены как функция, принимающая текущий контекст выполнения (RunContextWrapper) и экземпляр агента, и возвращающая строку. Это позволяет динамически формировать системный промпт на основе:
- Текущего состояния роботов (загруженного из Redis в контекст)
- Активных задач и их приоритетов
- Ролей и прав текущего оператора
- Времени суток и условий среды

Динамические инструкции вычисляются заново перед каждым вызовом LLM, обеспечивая актуальность контекста.

### Клонирование агентов (clone)

Метод clone позволяет создавать вариации существующих агентов с изменёнными параметрами без модификации оригинала. Используется для:
- Создания специализированных версий агентов для разных типов роботов (агент координации наземных роботов vs. дронов)
- Тестирования различных конфигураций (разные модели, temperature)
- Динамического создания агентов с адаптированными инструкциями для конкретных задач

### Стратегии использования инструментов (tool_use_behavior)

Свойство tool_use_behavior определяет, как агент обрабатывает вызовы инструментов:
- **По умолчанию** — агент самостоятельно решает, когда вызывать инструменты и когда давать финальный ответ
- **Принудительный вызов** — агент обязан вызвать инструмент перед формированием ответа. Используется для Safety Agent: перед одобрением плана обязателен вызов check_safety_constraints
- **Фильтрация по именам** — вызов определённых инструментов завершает текущий ход агента, и их результат используется как финальный выход

## Агенты системы

### Vision Agent (Агент зрения)

**Специализация:** Взаимодействие с сервисами компьютерного зрения

**Модель:** Мультимодальная модель через vLLM (для анализа изображений) или быстрая текстовая модель (для агрегации данных детекции)

**Инструменты:**
- `analyze_image(robot_id)` — запросить анализ последнего изображения от робота через Triton. Определён как функциональный инструмент (function tool) с автоматическим извлечением схемы из сигнатуры функции и документации (docstring). Таймаут: 10 секунд
- `get_detections(robot_id)` — получить последние детекции из Redis Feature Store. Синхронный инструмент без внешних сетевых вызовов
- `search_object(object_class, area)` — найти объект определённого класса в указанной зоне по данным от всех роботов. Параметры ограничены через валидацию: object_class — из предопределённого списка классов, area — геометрические ограничения
- `get_scene_description(robot_id)` — запросить текстовое описание сцены через vLLM (мультимодальный анализ). Таймаут: 15 секунд

**Контекст:** Имеет доступ к карте обнаруженных объектов, истории детекций, текущим изображениям от всех роботов.

**Когда вызывается:** При задачах, связанных с поиском объектов, анализом сцены, навигацией к визуальным целям.

**Guardrails:** Входной guardrail проверяет, что robot_id существует и робот онлайн, прежде чем разрешить выполнение.

### Planning Agent (Агент планирования)

**Специализация:** Генерация и оптимизация планов

**Модель:** Наиболее мощная доступная текстовая модель с повышенным max_tokens для генерации детальных планов

**Инструменты:**
- `generate_plan(context, constraints)` — сгенерировать план через vLLM. Определён как FunctionTool с явной JSON-схемой параметров для точного контроля формата ввода
- `decompose_task(high_level_task)` — разбить задачу на подзадачи. Возвращает структурированный output_type (список подзадач с зависимостями)
- `optimize_routes(robots, waypoints)` — оптимизировать маршруты для группы роботов. Таймаут: 30 секунд (сложные вычисления)
- `estimate_time(task, robot)` — оценить время выполнения задачи конкретным роботом
- `find_similar_plans(context)` — найти похожие успешные планы через семантический поиск в долгосрочной памяти (PostgresStore / RedisStore)

**Контекст:** Имеет доступ к возможностям роботов, текущим задачам, истории успешных планов, ограничениям среды.

**Когда вызывается:** На этапе генерации плана в LangGraph, при перепланировании.

**Guardrails:** Выходной guardrail валидирует структуру сгенерированного плана (наличие обязательных полей, корректность ссылок на роботов, реализуемость задач).

### Safety Agent (Агент безопасности)

**Специализация:** Мониторинг безопасности и предотвращение инцидентов

**Модель:** Быстрая текстовая модель с низким temperature для детерминистичных решений

**tool_use_behavior:** Принудительный вызов инструментов — агент обязан выполнить проверку безопасности через check_safety_constraints перед формированием ответа

**Инструменты:**
- `check_safety_constraints(plan)` — проверить план на соответствие требованиям безопасности. Определён с tool guardrail, который блокирует выполнение при обнаружении критических нарушений (tripwire)
- `emergency_stop(robot_id)` — экстренная остановка робота. Требует подтверждения оператора (Human-in-the-loop) через механизм interruptions
- `get_nearby_humans(robot_id)` — проверить наличие людей вблизи робота
- `assess_collision_risk(robot_ids)` — оценить риск столкновения между роботами
- `validate_workspace(robot_id, position)` — проверить, что целевая позиция безопасна и доступна

**Контекст:** Постоянно мониторит состояние всех роботов. Имеет приоритет над другими агентами — может прервать выполнение любого плана.

**Когда вызывается:** Перед выполнением каждого плана (валидация), при получении экстренных событий, периодически (фоновый мониторинг).

**Guardrails:** Входной guardrail (tripwire) — при обнаружении экстренной ситуации в данных телеметрии немедленно прерывает выполнение и инициирует аварийный протокол.

### Coordination Agent (Агент координации)

**Специализация:** Межроботная координация и распределение ресурсов

**Модель:** Текстовая модель среднего размера, баланс между скоростью и качеством

**Инструменты:**
- `assign_robot(task, available_robots)` — выбрать оптимального робота для задачи
- `coordinate_formation(robot_ids, formation_type)` — координация формации для группового действия. Параметр formation_type валидируется через Pydantic Field с ограничением на допустимые значения
- `resolve_conflict(robot_id_1, robot_id_2, conflict_type)` — разрешение конфликтов (пересечение маршрутов, одна цель)
- `balance_workload(tasks, robots)` — балансировка нагрузки между роботами
- `send_command(robot_id, command)` — отправка команды через MQTT. Определён с условным включением (is_enabled) — доступен только в рабочем режиме, отключён в режиме симуляции

**Контекст:** Имеет доступ к состоянию всех роботов, активным задачам, карте среды.

**Когда вызывается:** При назначении задач, координации групповых действий, разрешении конфликтов.

## Инструменты (Tools)

### Типы инструментов в системе

**Функциональные инструменты (Function Tools)**
- Основной тип инструментов для агентов системы
- Определяются через декоратор function_tool с автоматическим извлечением JSON-схемы параметров из типовых аннотаций Python и описаний из docstring
- Поддерживают Pydantic Field для валидации и ограничения параметров (минимальные/максимальные значения, паттерны, перечисления)
- Поддерживают форматы docstring: Google, Sphinx, NumPy (автоопределение)
- Возвращаемые типы: текст, структурированные объекты, изображения, файлы

**Явные функциональные инструменты (FunctionTool)**
- Создаются напрямую с указанием имени, описания, JSON-схемы и асинхронной функции вызова
- Используются для инструментов с динамической схемой или сложной логикой инициализации
- Пример: generate_plan, где JSON-схема формируется динамически в зависимости от типа задачи

**Агенты-как-инструменты (Agents-as-Tools)**
- Другие агенты могут быть представлены как инструменты через метод as_tool
- Центральный агент (оркестратор) сохраняет контроль: вложенный агент выполняется, возвращает результат, и управление возвращается оркестратору
- В отличие от handoffs, оркестратор не теряет контроль

### Агенты-как-инструменты: детали

Метод as_tool принимает:
- **tool_name** и **tool_description** — имя и описание инструмента для LLM
- **parameters** — Pydantic-модель или dataclass для структурированного ввода (вместо простой строки)
- **include_input_schema** — включение полной JSON-схемы в описание инструмента для LLM
- **input_builder** — кастомная функция преобразования структурированных аргументов во ввод вложенного агента
- **custom_output_extractor** — функция извлечения результата из RunResult вложенного агента (например, извлечение JSON из истории, конвертация формата)
- **needs_approval** — требование подтверждения оператора перед выполнением (Human-in-the-loop через interruptions)
- **on_stream** — callback для получения потоковых событий вложенного агента (токены, вызовы инструментов)
- **is_enabled** — условное включение: булево значение или функция (context, agent) → bool для динамической фильтрации по разрешениям, среде, A/B-тестированию
- **max_turns** — ограничение максимального количества ходов вложенного агента

### Таймауты и обработка ошибок

**Таймауты инструментов:**
- Каждый асинхронный функциональный инструмент может иметь таймаут
- При истечении таймаута: поведение error_as_result (по умолчанию) — LLM получает сообщение об ошибке и может повторить или выбрать альтернативный подход; поведение raise_exception — немедленное прерывание выполнения
- Кастомная функция формирования сообщения об ошибке таймаута для LLM

**Обработка ошибок:**
- Функция failure_error_function определяет, как ошибки инструментов сообщаются LLM
- По умолчанию: стандартное сообщение об ошибке для LLM, позволяющее ему адаптироваться
- Кастомная функция: формирование понятных пользователю сообщений
- Режим без обработки (None): ошибки пробрасываются наружу для обработки на уровне приложения
- Типы ошибок: ModelBehaviorError (LLM сгенерировал некорректные аргументы), UserError (ошибка в пользовательском инструменте)

### Условное включение инструментов

Параметр is_enabled позволяет динамически включать и отключать инструменты:
- Булево значение (True/False) — статическое включение/отключение
- Функция (context, agent) → bool — динамическая логика на основе контекста выполнения
- Асинхронная функция — для сложных проверок (например, проверка разрешений через внешний сервис)

Отключённые инструменты полностью скрываются от LLM. Применение в системе:
- send_command отключён в режиме симуляции
- emergency_stop доступен только операторам с соответствующей ролью
- Экспериментальные инструменты включены только в тестовой среде

## Handoffs (делегация между агентами)

### Механизм handoffs

Handoff — механизм передачи управления от одного агента к другому. В отличие от agents-as-tools, при handoff текущий агент полностью передаёт управление: вложенный агент становится «активным» и продолжает обработку.

Каждый handoff представляется для LLM как инструмент с именем `transfer_to_<agent_name>`. Когда LLM решает вызвать этот инструмент, текущий агент завершается и управление переходит к целевому агенту.

### Настройка handoffs

| Параметр | Описание |
|----------|----------|
| **tool_name_override** | Переопределение имени инструмента (по умолчанию `transfer_to_<name>`) |
| **tool_description_override** | Переопределение описания для LLM |
| **on_handoff** | Callback-функция, вызываемая при делегации (для логирования, подготовки контекста) |
| **input_type** | Pydantic-модель, которую LLM должен заполнить при вызове handoff (структурированные метаданные) |
| **input_filter** | Функция фильтрации истории сообщений при передаче (для сокращения контекста, удаления нерелевантных данных) |
| **is_enabled** | Условное включение handoff (аналогично инструментам) |

### Фильтрация ввода (input_filter)

При делегации целевой агент получает историю сообщений от предыдущего агента. Функция input_filter (HandoffInputData) позволяет:
- Удалить промежуточные технические сообщения
- Оставить только последние N сообщений
- Удалить все инструментальные вызовы, оставив только диалог
- Полностью заменить историю на краткое резюме

Предопределённые фильтры: remove_all_tools (удаление инструментальных сообщений).

### Вложенная история handoff (nest_handoff_history)

Опциональная функция (бета): при включении история предыдущего агента оборачивается в специальный формат, который даёт целевому агенту контекст о том, что предыдущий агент делал, но чётко разделяет историю текущего и предыдущего агентов.

### Применение handoffs в системе

**Граф делегации агентов:**

- **Planning Agent** → **Vision Agent**: при необходимости детального анализа сцены планировщик делегирует агенту зрения, который анализирует изображения и возвращает результат. input_type: запрос на анализ (robot_id, тип анализа, зона интереса)
- **Planning Agent** → **Coordination Agent**: для оценки доступности роботов и оптимизации назначений. input_filter: только информация о текущем плане, без истории анализа
- **Coordination Agent** → **Vision Agent**: для уточнения позиций объектов перед координацией
- **Safety Agent** (особый статус): не принимает handoff от других агентов, но может прервать выполнение любого агента через tripwire guardrail. Инициируется через внешний триггер (экстренное событие)

### Два паттерна мультиагентного взаимодействия

**Паттерн Manager (агенты-как-инструменты):**
- Центральный агент-оркестратор вызывает специализированных агентов как инструменты
- Оркестратор сохраняет контроль, получает результат и решает следующий шаг
- Используется в узлах LangGraph: каждый узел вызывает нужных агентов как инструменты и агрегирует результаты
- Преимущество: чёткий контроль, предсказуемый поток, возможность параллельного вызова нескольких агентов

**Паттерн Handoffs (peer-делегация):**
- Агенты делегируют друг другу управление на основе контекста задачи
- Каждый агент решает, может ли он обработать задачу сам или нужно передать другому
- Используется для динамических сценариев: Planning Agent начинает обработку, обнаруживает необходимость в визуальном анализе, делегирует Vision Agent
- Преимущество: гибкость, агенты самостоятельно определяют маршрут обработки

**Комбинация паттернов в Orchestrator:**
- На уровне узлов LangGraph используется паттерн Manager: узел вызывает конкретного агента как инструмент
- Внутри агентного цикла используется паттерн Handoffs: агент может делегировать задачу другому агенту, если определяет, что тот лучше подходит
- Это обеспечивает структурированность на верхнем уровне (граф LangGraph) и гибкость на уровне агентов (Open-Agent SDK)

## Guardrails (защитные барьеры)

### Типы guardrails

**Входные guardrails (Input Guardrails):**
- Выполняются при первом вызове агента (перед первым обращением к LLM)
- Проверяют входные данные на допустимость
- Применение: валидация команд пользователя, проверка наличия необходимого контекста, детекция запрещённых запросов

**Выходные guardrails (Output Guardrails):**
- Выполняются после получения финального ответа от последнего агента в цепочке
- Проверяют выходные данные на корректность
- Применение: валидация сгенерированного плана, проверка формата ответа, фильтрация нежелательного контента

**Tool guardrails (барьеры инструментов):**
- Привязываются к конкретным функциональным инструментам
- Выполняются перед и/или после вызова инструмента
- Применение: проверка параметров команды перед отправкой роботу, валидация результатов детекции

### Механизм Tripwire (прерывание)

Tripwire — механизм немедленного прерывания выполнения при обнаружении критической ситуации. Когда guardrail устанавливает tripwire_triggered = True:
- Выполнение агентного цикла немедленно прекращается
- Генерируется исключение, которое может быть обработано на уровне LangGraph
- Все незавершённые операции отменяются

Применение tripwire в системе:
- Safety Agent: при обнаружении человека в опасной зоне
- Входной guardrail: при получении запроса, нарушающего политику безопасности
- Tool guardrail: при попытке отправить роботу команду, превышающую допустимые параметры (скорость, зона)

### Режимы выполнения guardrails

- **Параллельный (по умолчанию):** guardrails выполняются параллельно с основной обработкой. Если guardrail обнаруживает нарушение — обработка прерывается даже если LLM уже начал генерацию
- **Блокирующий:** guardrails выполняются до начала основной обработки. Используется когда результат guardrail нужен для определения дальнейших действий

## Контекст выполнения (RunContext)

### RunContextWrapper

RunContextWrapper — обёртка для пользовательского контекста, который передаётся через весь агентный цикл. Контекст НЕ отправляется в LLM — он доступен только в инструментах, guardrails, динамических инструкциях и callback-функциях.

**SwarmContext** — типизированный контекст для Orchestrator, содержащий:
- Соединение с Redis для доступа к Feature Store
- Соединение с PostgreSQL для хранения задач
- MQTT-клиент для отправки команд роботам
- gRPC-клиенты для AI-сервисов (vLLM, Triton, SmolVLA)
- Текущий идентификатор оператора и его роли
- Настройки среды выполнения (режим: рабочий / симуляция / тестирование)

RunContextWrapper оборачивает SwarmContext и предоставляет:
- Типобезопасный доступ к контексту через свойство context
- Отслеживание использования (usage) — подсчёт токенов, количество запросов
- Метаданные выполнения

### ToolContext

ToolContext расширяет RunContextWrapper дополнительными метаданными инструмента:
- **tool_name** — имя текущего вызываемого инструмента
- **tool_call_id** — уникальный идентификатор вызова (для трассировки)
- **tool_arguments** — аргументы, переданные LLM (до парсинга)

Используется внутри инструментов для:
- Логирования с контекстом (какой инструмент, какой вызов)
- Доступа к общим ресурсам через context (Redis, PostgreSQL и др.)
- Отслеживания метрик использования

## Runner и агентный цикл

### Агентный цикл (Agent Loop)

Runner запускает агентный цикл — основной механизм выполнения:

1. LLM получает текущие инструкции, историю сообщений и описание доступных инструментов (включая handoffs как инструменты)
2. LLM генерирует ответ — это может быть:
   - **Финальный ответ (final_output)** — если агент определяет, что задача решена, цикл завершается
   - **Handoff** — передача управления другому агенту, текущий цикл завершается, начинается цикл целевого агента
   - **Вызов инструментов (tool_calls)** — один или несколько вызовов инструментов
3. При вызове инструментов: инструменты выполняются (параллельно, если несколько), результаты добавляются в историю сообщений
4. Цикл повторяется с шага 1

### Ограничение ходов (max_turns)

Параметр max_turns ограничивает количество итераций агентного цикла. При превышении лимита генерируется исключение MaxTurnsExceeded. Используется для защиты от зацикливания.

Настройки max_turns в системе:
- Vision Agent: max_turns = 5 (простые запросы к AI-сервисам)
- Planning Agent: max_turns = 15 (сложная генерация планов с несколькими итерациями)
- Safety Agent: max_turns = 3 (быстрые проверки безопасности)
- Coordination Agent: max_turns = 10 (координация нескольких роботов)

### Режимы запуска Runner

| Метод | Описание | Применение |
|-------|----------|-----------|
| **Runner.run()** | Асинхронный запуск, возвращает полный результат (RunResult) | Основной режим в Orchestrator (из узлов LangGraph) |
| **Runner.run_sync()** | Синхронный запуск (обёртка над run()) | Тестирование и отладка |
| **Runner.run_streamed()** | Потоковый асинхронный запуск (RunResultStreaming) | Передача ответов в реальном времени на фронтенд |

### Потоковый режим (Streaming)

RunResultStreaming предоставляет:
- **stream_events()** — асинхронный итератор по событиям выполнения (токены LLM, вызовы инструментов, handoffs)
- **current_agent** — текущий активный агент (обновляется при handoff)
- **is_complete** — флаг завершения выполнения
- **cancel()** — отмена выполнения (немедленная или после текущего хода)

Потоковый режим используется для передачи ответов агентов в Chat Interface через WebSocket.

## RunConfig (конфигурация запуска)

RunConfig определяет параметры конкретного запуска агентного цикла:

| Параметр | Описание | Применение |
|----------|----------|-----------|
| **model** | Переопределение модели для всех агентов в запуске | Использование разных моделей для разных сред (dev/prod) |
| **model_provider** | Провайдер модели | Переключение между провайдерами |
| **model_settings** | Глобальные настройки модели | Единые параметры для всех агентов |
| **input_guardrails** | Дополнительные входные guardrails | Добавление проверок на уровне запуска |
| **output_guardrails** | Дополнительные выходные guardrails | Добавление проверок на уровне запуска |
| **handoff_input_filter** | Глобальный фильтр для всех handoffs | Единая политика фильтрации истории |
| **tracing** | Настройки трассировки (workflow_name, group_id, api_key, disabled) | Интеграция с системой мониторинга |
| **trace_include_sensitive_data** | Включение чувствительных данных в трассировку | Отключено в продакшн, включено при отладке |
| **tool_error_formatter** | Глобальная функция форматирования ошибок инструментов | Единообразное представление ошибок для LLM |

## Результаты выполнения (RunResult)

### Структура результата

RunResult и RunResultStreaming предоставляют полную информацию о выполнении:

| Свойство | Описание | Применение |
|----------|----------|-----------|
| **final_output** | Финальный ответ последнего агента (str или output_type) | Результат для пользователя или следующего узла LangGraph |
| **last_agent** | Последний активный агент (после всех handoffs) | Определение агента для следующего хода |
| **new_items** | Список элементов выполнения (RunItem) с метаданными | Логирование, отладка, аудит |
| **to_input_list()** | Полная история для передачи в следующий ход | Ручное управление состоянием диалога |
| **interruptions** | Ожидающие подтверждения (для Human-in-the-loop) | Экстренные действия, требующие одобрения оператора |
| **to_state()** | Сериализуемое состояние для возобновления | Приостановка/возобновление выполнения |
| **last_response_id** | ID последнего ответа модели | Chaining через previous_response_id |
| **raw_responses** | Сырые ответы модели | Диагностика, метрики |
| **input_guardrail_results** | Результаты входных guardrails | Аудит безопасности |
| **output_guardrail_results** | Результаты выходных guardrails | Аудит безопасности |
| **context_wrapper** | Обёртка контекста с usage и метаданными | Отслеживание потребления ресурсов |

### Типы элементов выполнения (RunItem)

- **MessageOutputItem** — текстовые сообщения агента
- **ReasoningItem** — элементы рассуждения (если модель поддерживает)
- **ToolCallItem** — вызовы инструментов с аргументами
- **ToolCallOutputItem** — результаты вызовов инструментов
- **ToolApprovalItem** — вызовы, ожидающие подтверждения (interruptions)
- **HandoffCallItem** — запросы на делегацию
- **HandoffOutputItem** — результаты делегации

### Human-in-the-loop (участие оператора)

При наличии interruptions (ожидающих подтверждений) выполнение приостанавливается:
1. Результат содержит interruptions с описанием действий, требующих одобрения
2. Вызывается to_state() для сериализации текущего состояния
3. Оператор одобряет или отклоняет каждое действие (approve / reject)
4. Выполнение возобновляется через Runner.run с обновлённым состоянием

В Orchestrator этот механизм используется для:
- Экстренной остановки роботов (emergency_stop требует подтверждения)
- Выполнения потенциально опасных манипуляций (pick_up вблизи хрупких объектов)
- Подтверждения планов с высоким риском

## Управление состоянием диалога

### Стратегии сохранения истории

Open-Agent SDK предоставляет четыре стратегии управления историей диалога между вызовами:

**1. Ручная передача через to_input_list():**
- Результат предыдущего вызова (result.to_input_list()) передаётся как вход следующего
- Приложение полностью контролирует хранение истории
- Используется при интеграции с LangGraph: история управляется через SwarmState.messages

**2. Сессии (Sessions):**
- SDK автоматически загружает и сохраняет историю
- SQLiteSession — базовая реализация для локального хранения
- AdvancedSQLiteSession — расширенная реализация с поддержкой ветвления диалогов, отслеживания использования токенов, структурированных запросов к истории
- Каждая сессия идентифицируется session_id

**3. conversation_id (серверное управление OpenAI):**
- История хранится на стороне OpenAI
- Не требует передачи полной истории при каждом вызове
- Используется для прямого взаимодействия с пользователем через Chat Interface

**4. previous_response_id (chaining):**
- Продолжение цепочки ответов модели по идентификатору
- Оптимизация: не требуется повторная обработка всей истории

### Применение в Orchestrator

- **Внутри LangGraph графа:** используется стратегия to_input_list() — состояние управляется SwarmState
- **Для пользовательских сессий:** используется AdvancedSQLiteSession с ветвлением (branching) для поддержки альтернативных путей диалога
- **Для Chat Interface:** используется conversation_id для серверного управления историей

### AdvancedSQLiteSession: расширенные возможности

- **Ветвление диалогов (Branching):** создание альтернативных путей разговора от любого сообщения пользователя. Позволяет оператору «откатиться» к предыдущему сообщению и попробовать другой подход
- **Отслеживание использования (Usage Tracking):** детальная аналитика потребления токенов по ходам диалога с разбивкой на входные и выходные токены
- **Структурированные запросы:** получение диалога по ходам, статистика использования инструментов, поиск по содержимому
- **Управление ветками:** создание, переключение, удаление веток диалога

## Lifecycle Hooks (хуки жизненного цикла)

### RunHooks (хуки уровня запуска)

Срабатывают для всего запуска, независимо от количества агентов и handoffs:

- **on_agent_start** — при начале работы каждого агента (включая после handoff)
- **on_agent_end** — при завершении работы агента
- **on_llm_start** — перед каждым вызовом LLM
- **on_llm_end** — после получения ответа от LLM
- **on_tool_start** — перед выполнением инструмента
- **on_tool_end** — после получения результата инструмента
- **on_handoff** — при передаче управления между агентами

### AgentHooks (хуки уровня агента)

Привязаны к конкретному агенту и срабатывают только для него:
- Те же события, что и RunHooks, но ограниченные одним агентом
- Полезны для специфического мониторинга (например, логирование всех вызовов Safety Agent)

### Применение hooks в Orchestrator

- **Трассировка и мониторинг:** каждый вызов LLM и инструмента логируется через Jaeger
- **Метрики:** on_llm_start/end для измерения латентности LLM, on_tool_start/end для латентности инструментов
- **Публикация событий:** on_agent_start/end публикует в Redis Pub/Sub для обновления Dashboard UI
- **Аудит:** on_handoff логирует передачу управления для построения графа взаимодействий
- **Алерты:** on_tool_end проверяет результаты критических инструментов (emergency_stop) и отправляет уведомления

## Конфигурация SDK

### API-ключи и клиенты

- Основной API-ключ для LLM-запросов настраивается через переменную окружения или явно через функцию set_default_openai_key
- Кастомный клиент (AsyncOpenAI) с альтернативным base_url — для подключения к локальным vLLM-серверам через OpenAI-совместимый API
- Переключение между Responses API и Chat Completions API через set_default_openai_api

### Трассировка (Tracing)

- Трассировка включена по умолчанию и использует тот же API-ключ
- Возможность отключения трассировки или исключения чувствительных данных (trace_include_sensitive_data = False)
- Настройки трассировки через RunConfig для per-run конфигурации
- Интеграция с OpenTelemetry / Jaeger для единой системы мониторинга

### Логирование

- Два логгера: openai.agents (основной) и openai.agents.tracing (трассировка)
- По умолчанию не включают чувствительные данные (входы/выходы LLM и инструментов)
- Управление через переменные окружения: OPENAI_AGENTS_DONT_LOG_MODEL_DATA, OPENAI_AGENTS_DONT_LOG_TOOL_DATA
- Интеграция с ELK-стеком системы через стандартный Python logging

## Память и контекст

### Краткосрочная память (Short-term Memory)

Хранится в Redis и SQLite, привязана к текущей сессии (thread_id / session_id):
- Контекст текущего диалога с пользователем (через AdvancedSQLiteSession или to_input_list в SwarmState)
- Промежуточные результаты анализа (в SwarmState через LangGraph checkpointing)
- Состояние текущего графа LangGraph (через PostgresSaver / RedisSaver)
- Стратегии управления размером: обрезка сообщений, удаление, суммаризация (подробнее в документации LangGraph-движка)
- TTL: 1 час для активных задач

### Долгосрочная память (Long-term Memory)

Хранится в PostgresStore и Redis:
- Эмбеддинги успешных планов для семантического поиска (через LangGraph Store с настроенной моделью эмбеддингов)
- История выполненных задач с результатами (PostgreSQL)
- Паттерны ошибок и успешных решений (PostgresStore с пространствами имён)
- Используется Planning Agent для нахождения похожих ситуаций через метод search хранилища

## Интеграция с LangGraph

Open-Agent SDK агенты вызываются из узлов LangGraph преимущественно в паттерне Manager (агенты-как-инструменты):

- Узел **Analyze Situation** → вызывает Vision Agent (as_tool для анализа сцены) и Safety Agent (as_tool для начальной проверки безопасности)
- Узел **Query Models** → вызывает Vision Agent (as_tool для детекций с параллельным вызовом нескольких инструментов)
- Узел **Generate Plan** → вызывает Planning Agent (as_tool с output_type для структурированного плана) и Coordination Agent (as_tool для оценки назначений)
- Узел **Safety Validation** → вызывает Safety Agent (as_tool с tool_use_behavior принудительного вызова check_safety_constraints)
- Узел **Execute Plan** → вызывает Coordination Agent (as_tool для отправки команд через Send API)
- Узел **Monitor Execution** → вызывает Safety Agent (as_tool для периодической проверки безопасности)

Внутри каждого агента может происходить делегация через handoffs — Planning Agent делегирует Vision Agent для уточнения визуальной информации, Coordination Agent делегирует Vision Agent для уточнения позиций объектов.

Каждый агент имеет собственный системный промпт (динамические инструкции на основе SwarmContext), описывающий его роль, возможности и ограничения. Промпты пересчитываются при каждом вызове на основе актуального состояния системы.

Результаты выполнения агентов (RunResult.final_output) возвращаются как обновления SwarmState в соответствующих полях (plan, actions, constraints и др.).
