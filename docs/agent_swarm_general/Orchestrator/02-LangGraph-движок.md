# Orchestrator — LangGraph-движок

## Назначение

LangGraph используется в Orchestrator как основной фреймворк для управления многошаговыми процессами планирования и выполнения задач. Он реализует StateGraph — ориентированный граф состояний, где каждый узел (node) — отдельный обработчик, рёбра (edges) определяют переходы между узлами, а состояние (state) — типизированная структура данных, передаваемая через весь граф и обновляемая на каждом шаге.

LangGraph предоставляет два API: Graph API (StateGraph, узлы, рёбра) и Functional API (декораторы entrypoint и task). В Orchestrator используется преимущественно Graph API для основного цикла управления роем, а Functional API — для вспомогательных изолированных задач.

## Паттерны рабочих процессов

LangGraph поддерживает ряд архитектурных паттернов, которые комбинируются в Orchestrator для решения различных задач:

### Используемые паттерны

**Prompt Chaining (цепочка промптов)** — последовательная обработка, где выход одного узла становится входом следующего. Используется в основном цикле графа: Receive Input → Analyze Situation → Query Models → Generate Plan — каждый узел обогащает SwarmState, передавая его следующему.

**Parallelization (параллелизация)** — одновременное выполнение нескольких независимых операций с объединением результатов. Узел Query Models использует этот паттерн: параллельные запросы к Triton (детекция), vLLM (текстовый анализ) и SmolVLA (визуальное планирование) с последующим слиянием результатов в единое состояние.

**Routing (маршрутизация)** — условные переходы на основе содержимого состояния. Классифицирующий узел определяет, какой путь в графе будет пройден. Используется после анализа ситуации для направления к нужному подграфу: простая навигация, комплексная манипуляция, патрулирование.

**Orchestrator-Worker (оркестратор-рабочие)** — центральный узел динамически создаёт параллельных рабочих через механизм Send API. Узел Generate Plan использует этот паттерн: после декомпозиции задачи для каждой подзадачи динамически создаётся отдельная параллельная ветка выполнения через Send, количество которых определяется на лету по числу подзадач и доступных роботов.

**Evaluator-Optimizer (оценщик-оптимизатор)** — циклическая пара: один узел генерирует результат, другой оценивает его качество, и при необходимости происходит повторная генерация. Узлы Generate Plan и Safety Validation работают по этому паттерну: Safety Agent оценивает сгенерированный план, и при обнаружении проблем безопасности план перегенерируется с уточнёнными ограничениями.

**Agent (агентный цикл)** — LLM в цикле вызывает инструменты и принимает решения на основе их результатов. Этот паттерн реализуется через интеграцию с Open-Agent SDK: каждый специализированный агент (Vision, Planning, Safety, Coordination) работает в собственном агентном цикле с доступом к инструментам.

## Граф состояний роя (SwarmState)

### Определение состояния (StateGraph + TypedDict)

SwarmState определяется как типизированная структура данных на основе TypedDict и используется при создании StateGraph. Каждое поле имеет строгий тип, а для полей-коллекций определяются функции-редьюсеры (reducers), которые описывают, как обновляются списки при слиянии результатов из параллельных ветвей.

SwarmState содержит всю информацию, необходимую для принятия решений:

- **robots** — карта текущих состояний всех роботов (из Redis): позиция, заряд, статус, возможности, активная задача. Редьюсер: слияние по ключу robot_id с выбором более свежей записи
- **environment** — информация о среде: обнаруженные объекты, карта, условия
- **tasks** — список текущих задач с их статусами. Редьюсер: объединение списков с дедупликацией по task_id
- **plan** — сгенерированный план действий (перезаписывается при перепланировании)
- **user_input** — исходная команда пользователя
- **messages** — история сообщений LLM-контекста (на основе MessagesState). Редьюсер: добавление новых сообщений к существующим с автоматической поддержкой удаления через специальные маркеры
- **llm_response** — ответ от LLM (анализ, интерпретация)
- **actions** — список конкретных действий, отправленных роботам. Редьюсер: объединение списков
- **constraints** — ограничения (временные, ресурсные, пространственные)
- **timestamp** — временная метка начала обработки
- **iteration_count** — счётчик итераций для защиты от бесконечных циклов

Граф создаётся как StateGraph с указанием SwarmState в качестве типа состояния. Все узлы принимают текущее состояние и возвращают частичное обновление (partial update) — только те поля, которые были изменены. LangGraph автоматически применяет редьюсеры для объединения обновлений с текущим состоянием.

### Специальные узлы START и END

Граф имеет два специальных псевдоузла:

- **START** — точка входа в граф. Из него идёт ребро к первому пользовательскому узлу (Receive Input). START не выполняет обработки — он только определяет начальную точку
- **END** — точка завершения графа. Когда выполнение достигает END, граф останавливается и возвращает финальное состояние. Из узла Monitor Execution ведёт условное ребро к END при успешном завершении всех действий

### Узлы графа

**1. Receive Input (Получение ввода)**
- Входные данные: команда пользователя или системное событие (из START)
- Действия: загрузка текущего состояния всех роботов из Redis, обогащение контекста, инициализация iteration_count
- Выходные данные: частичное обновление состояния — заполненные поля robots и environment
- Переход: безусловное ребро → Analyze Situation

**2. Analyze Situation (Анализ ситуации)**
- Входные данные: состояние с командой и контекстом
- Действия: отправка контекста в vLLMService через gRPC для анализа. LLM извлекает интент, сущности, определяет тип задачи. Вызывается Vision Agent и Safety Agent через Open-Agent SDK
- Выходные данные: структурированная интерпретация команды, извлечённые ограничения, обновлённые messages
- Переход: условное ребро (routing) → выбор подграфа в зависимости от типа задачи, или прямой переход к Query Models

**3. Query Models (Запрос к AI-моделям)**
- Входные данные: интерпретированная команда
- Действия: параллельные запросы к AI-сервисам (паттерн Parallelization). В зависимости от типа задачи:
  - Детекция объектов → запрос к Triton (YOLO + трекинг)
  - Визуальное понимание → запрос к SmolVLA Cloud
  - Анализ изображения → запрос к vLLM (мультимодальная модель)
  - Все необходимые запросы выполняются параллельно, результаты объединяются через редьюсеры состояния
- Выходные данные: обогащённый контекст с результатами AI-анализа
- Переход: безусловное ребро → Generate Plan

**4. Generate Plan (Генерация плана)**
- Входные данные: полный контекст (интерпретация, детекции, состояние роботов)
- Действия:
  - Формирование промпта для vLLM с полным контекстом
  - LLM генерирует высокоуровневый план в структурированном формате
  - Декомпозиция плана на конкретные подзадачи
  - Назначение подзадач роботам (через ResourceManager)
  - Поиск похожих успешных ситуаций через семантический поиск в хранилище долгосрочной памяти для уточнения плана
  - Динамическое создание параллельных ветвей через Send API для каждой подзадачи
- Выходные данные: детальный план с подзадачами и назначениями
- Переход: безусловное ребро → Safety Validation

**5. Safety Validation (Валидация безопасности)**
- Входные данные: сгенерированный план
- Действия: Safety Agent проверяет план на соответствие требованиям безопасности (паттерн Evaluator-Optimizer)
- Выходные данные: результат валидации (approved / rejected с причиной)
- Переход: условное ребро →
  - Если план одобрен → Execute Plan
  - Если план отклонён → Generate Plan (перегенерация с уточнёнными ограничениями)
  - Если превышен лимит итераций → END с ошибкой

**6. Execute Plan (Выполнение плана)**
- Входные данные: валидированный план с назначенными подзадачами
- Действия:
  - Для каждой подзадачи через Send API создаётся параллельная ветвь выполнения
  - В каждой ветви формируется конкретная команда роботу
  - Команды отправляются роботам через MQTT (Command Service → MQTT Broker)
  - Каждое действие регистрируется в Redis и PostgreSQL
  - Результаты параллельных ветвей объединяются редьюсером в поле actions
- Выходные данные: список отправленных действий со статусами
- Переход: безусловное ребро → Monitor Execution

**7. Monitor Execution (Мониторинг выполнения)**
- Входные данные: список активных действий
- Действия:
  - Проверка статуса выполнения для каждого действия (через Redis: подтверждения от роботов)
  - Обновление прогресса
  - Обнаружение ошибок и таймаутов
  - Инкремент iteration_count
- Выходные данные: обновлённые статусы действий
- Переход: **условное ребро** →
  - Если все действия завершены → END (конец графа)
  - Если есть незавершённые → Monitor Execution (цикл мониторинга)
  - Если обнаружена ошибка или изменение среды → Analyze Situation (перепланирование)
  - Если превышен лимит итераций → END с таймаутом

### Условные переходы (Conditional Edges)

Условные переходы реализуются через функции-маршрутизаторы, которые принимают текущее состояние и возвращают имя целевого узла (или список имён для ветвления). Каждый маршрутизатор связывается с узлом и маппингом возвращаемых значений на целевые узлы.

Узел Monitor Execution содержит главную функцию-маршрутизатор с тремя ветками:

- **"complete"** — все действия выполнены успешно → возврат END
- **"continue"** — есть незавершённые действия, ожидание → возврат "monitor" (цикл)
- **"replan"** — обнаружена критическая ситуация (робот застрял, новый объект, ошибка) → возврат "analyze" (перепланирование)

Маппинг связывает строковые результаты с реальными узлами графа: "complete" → END, "continue" → Monitor Execution, "replan" → Analyze Situation.

## Send API — динамическое создание параллельных ветвей

Send API — ключевой механизм для реализации паттерна Orchestrator-Worker в LangGraph. Он позволяет одному узлу динамически создавать произвольное количество параллельных ветвей выполнения, причём количество ветвей определяется на этапе выполнения (runtime), а не при компиляции графа.

### Применение в Orchestrator

**Параллельная декомпозиция задач.** Узел Generate Plan после создания плана с N подзадачами генерирует N объектов Send, каждый из которых направляет выполнение в узел-обработчик подзадачи с уникальным состоянием (содержащим конкретную подзадачу и назначенного робота). Все N ветвей выполняются параллельно.

**Параллельная отправка команд.** Узел Execute Plan для каждого робота, которому назначена задача, создаёт отдельную ветвь через Send. Это позволяет одновременно формировать и отправлять команды всем роботам, не дожидаясь обработки каждого последовательно.

**Параллельный мониторинг.** При мониторинге большого числа активных действий узел Monitor Execution может создавать параллельные ветви проверки для каждого робота через Send.

### Механика работы

Функция-маршрутизатор условного перехода возвращает не строку с именем узла, а список объектов Send. Каждый объект Send содержит имя целевого узла и состояние, с которым этот узел будет вызван. LangGraph запускает все указанные ветви параллельно и собирает результаты через редьюсеры состояния.

## Подграфы (Subgraphs)

Подграфы позволяют декомпозировать сложный граф на модульные компоненты. Каждый подграф — самостоятельный скомпилированный StateGraph, который добавляется как узел в родительский граф.

### Использование подграфов в Orchestrator

**Подграфы по типам задач.** Для разных типов задач (навигация, поиск, манипуляция, патрулирование) определены отдельные подграфы с собственной логикой обработки. Узел Analyze Situation через маршрутизатор направляет выполнение в соответствующий подграф.

**Подграф планирования.** Цикл Generate Plan → Safety Validation оформлен как подграф с собственным внутренним состоянием и логикой итераций. Это позволяет изолировать сложную логику перегенерации плана.

**Подграфы для агентов.** Каждый агент Open-Agent SDK (Vision, Planning, Safety, Coordination) может быть обёрнут в подграф, что обеспечивает изоляцию состояния и возможность независимого тестирования.

### Автоматическое распространение чекпоинтера

При добавлении подграфа как узла родительского графа чекпоинтер (checkpointer) автоматически распространяется на все вложенные подграфы. Это означает, что состояние всех подграфов сохраняется и может быть восстановлено при сбое, без необходимости настраивать чекпоинтер для каждого подграфа отдельно.

Для подграфов, которым требуется собственное независимое сохранение состояния (например, подграф с длительным выполнением), можно включить индивидуальный чекпоинтер. Это создаёт отдельный поток сохранения для подграфа, не зависящий от родительского графа.

## Checkpointing и персистентность

### Краткосрочная память (Short-term Memory)

Краткосрочная память обеспечивается механизмом чекпоинтинга и привязана к конкретному потоку (thread). Каждый вызов графа сопровождается конфигурацией с `thread_id`, который определяет поток. Все промежуточные состояния графа автоматически сохраняются чекпоинтером.

**Чекпоинтеры (Checkpointers):**

| Чекпоинтер | Назначение | Применение |
|------------|-----------|-----------|
| InMemorySaver | Хранение в оперативной памяти | Разработка и тестирование |
| PostgresSaver | Хранение в PostgreSQL | **Продакшн (основной)** |
| RedisSaver | Хранение в Redis | Продакшн (для быстрого доступа) |

В продакшн-окружении Orchestrator использует PostgresSaver как основной чекпоинтер (надёжное хранение, транзакционная целостность) и RedisSaver как вспомогательный (быстрый доступ к активным потокам).

**Идентификация потоков:**
- `thread_id` обычно формируется как `task_{task_id}` для задач или `user_{user_id}_{session_id}` для пользовательских сессий
- При перезапуске Orchestrator worker — другой worker может продолжить обработку с последнего сохранённого checkpoint по тому же thread_id
- TTL для checkpoints: 1 час для активных задач, 24 часа для пользовательских сессий

**Управление размером контекста (история messages):**

Поле messages в SwarmState может неограниченно расти при длительных сессиях. Для управления размером применяются три стратегии:

1. **Обрезка сообщений (trim_messages)** — автоматическое удаление старых сообщений с сохранением последних N сообщений или N токенов. Системное сообщение всегда сохраняется. Применяется в начале каждого узла, обращающегося к LLM
2. **Удаление конкретных сообщений (RemoveMessage)** — точечное удаление определённых сообщений из истории по их идентификатору. Используется для удаления промежуточных технических сообщений (инструментальных вызовов) после их обработки
3. **Суммаризация** — периодическое сжатие старых сообщений в краткое резюме. При накоплении более заданного порога сообщений вызывается LLM для генерации summary, которое заменяет исходные сообщения. Применяется между итерациями перепланирования

### Долгосрочная память (Long-term Memory)

Долгосрочная память существует отдельно от чекпоинтинга и обеспечивает хранение знаний, доступных между потоками и сессиями.

**Хранилища (Stores):**

| Хранилище | Назначение | Применение |
|-----------|-----------|-----------|
| PostgresStore | Персистентное хранение | **Продакшн (основной)** |
| RedisStore | Быстрый доступ | Кэширование часто используемых данных |
| InMemoryStore | Хранение в памяти | Разработка и тестирование |

**Структура хранения:**
- Данные организованы в пространства имён (namespaces): `("plans", "successful")`, `("patterns", "errors")`, `("robots", "capabilities")`
- Каждая запись имеет ключ (key) и значение (value) в формате словаря
- Записи поддерживают обновление, удаление, поиск по ключу и по пространству имён

**Семантический поиск (Semantic Search):**
- При конфигурации хранилища задаётся модель эмбеддингов и набор индексируемых полей
- При добавлении записи автоматически генерируется эмбеддинг указанных полей
- Метод search выполняет семантический поиск по хранилищу с возвратом N наиболее похожих записей
- Используется в узле Generate Plan для поиска похожих успешных планов: текущий контекст задачи сравнивается с эмбеддингами ранее выполненных планов

**Доступ из узлов графа:**
- Хранилище передаётся при компиляции графа (как параметр store)
- Внутри каждого узла доступ к хранилищу осуществляется через объект Runtime, который предоставляется как параметр config в функцию узла
- Это позволяет любому узлу читать и записывать данные в долгосрочную память

### Управление чекпоинтами

LangGraph предоставляет API для управления сохранёнными чекпоинтами:
- Получение списка чекпоинтов для потока
- Получение состояния на конкретном чекпоинте
- Обновление состояния чекпоинта (например, для ручного вмешательства оператора)
- Удаление чекпоинтов по thread_id

Orchestrator использует управление чекпоинтами для:
- Ручного вмешательства оператора: оператор может посмотреть текущее состояние графа и изменить его (например, скорректировать план)
- Отладки: воспроизведение выполнения графа с любого чекпоинта
- Очистки: периодическое удаление устаревших чекпоинтов

## Параллельное выполнение

LangGraph поддерживает несколько механизмов параллельного выполнения:

### Статическая параллелизация (Fan-out / Fan-in)

Определяется на этапе компиляции графа: несколько узлов получают безусловные рёбра из одного источника и выполняются параллельно. Результаты объединяются через редьюсеры состояния перед переходом к следующему узлу.

Используется для:
- **Параллельных запросов к AI-моделям:** одновременный запрос к Triton (детекция) и vLLM (текстовый анализ) в узле Query Models
- **Параллельного мониторинга:** одновременная проверка статусов нескольких действий

### Динамическая параллелизация (Send API)

Определяется на этапе выполнения через Send API (описан выше):
- **Параллельная отправка команд:** одновременная отправка команд нескольким роботам в узле Execute Plan
- **Параллельная декомпозиция:** параллельное выполнение подзадач, количество которых известно только в runtime

### Map-Reduce

Комбинация Send API для параллельного выполнения (map) и редьюсеров состояния для агрегации (reduce). Используется для сбора результатов от всех роботов: узел мониторинга создаёт параллельные проверки для каждого робота (map), а редьюсер собирает результаты в единый список статусов (reduce).

## Functional API (entrypoint / task)

Для вспомогательных задач, не требующих полного графа состояний, LangGraph предоставляет Functional API на основе декораторов:

- **entrypoint** — определяет точку входа в рабочий процесс. Функция, обёрнутая этим декоратором, получает доступ к чекпоинтеру и хранилищу, может вызывать задачи и управлять состоянием
- **task** — определяет отдельную единицу работы внутри entrypoint. Задачи автоматически сохраняются чекпоинтером и могут выполняться параллельно

### Применение в Orchestrator

Functional API используется для:
- **Периодических проверок здоровья:** проверка состояния всех роботов, не требующая полного цикла графа
- **Фоновой обработки телеметрии:** агрегация и анализ потоковых данных от роботов
- **Утилитарных операций:** очистка устаревших данных, генерация аналитических отчётов
- **Простых запросов к AI:** одиночные запросы к LLM, не требующие многошагового графа

Преимущество Functional API — более простая структура при сохранении всех возможностей персистентности (чекпоинтинг, хранилища). Задачи (task) внутри entrypoint автоматически сохраняют свои результаты, и при восстановлении после сбоя уже выполненные задачи не повторяются.

## Перепланирование (Re-planning)

Система поддерживает адаптивное перепланирование при изменении условий. Перепланирование реализовано как цикл в графе: условное ребро из Monitor Execution возвращает выполнение в Analyze Situation.

### Триггеры перепланирования

- Робот сообщает об ошибке выполнения задачи
- Обнаружен новый объект, релевантный текущей задаче
- Робот разрядился ниже критического уровня
- Экстренная ситуация (препятствие, человек на пути)
- Пользователь изменил или дополнил команду
- Таймаут выполнения задачи

### Логика перепланирования

1. Все незавершённые действия помечаются как «приостановленные»
2. Роботам отправляется команда `HOLD` (ожидание)
3. Граф возвращается к узлу Analyze Situation с обновлённым контекстом (контекст содержит информацию о причине перепланирования и текущем состоянии выполнения)
4. При необходимости выполняется суммаризация накопленных сообщений для сокращения контекста
5. Генерируется новый план с учётом изменений и результатов поиска похожих ситуаций в долгосрочной памяти
6. Новые команды отправляются роботам

### Защита от бесконечных циклов

Поле iteration_count в SwarmState инкрементируется при каждом прохождении цикла. При превышении максимального порога (по умолчанию 10 итераций) граф принудительно завершается с ошибкой таймаута, все роботы получают команду HOLD, и задача передаётся в Dead Letter Queue для ручного анализа.

## Стриминг и обратная связь в реальном времени

LangGraph поддерживает стриминг — потоковую передачу промежуточных результатов выполнения графа.

### Режимы стриминга

- **values** — полное состояние после каждого узла. Используется для обновления Dashboard UI
- **updates** — только изменения (дельты) после каждого узла. Используется для инкрементальных обновлений
- **messages** — потоковая передача токенов LLM. Используется для передачи ответов LLM в Chat Interface

### Применение в Orchestrator

При запуске графа через потоковый режим каждый промежуточный результат (завершение узла, обновление состояния, генерация токена LLM) немедленно публикуется в Redis Pub/Sub для передачи через WebSocket на фронтенд. Это обеспечивает:
- Отображение прогресса планирования в реальном времени
- Потоковую передачу ответов LLM в чат-интерфейс
- Визуализацию текущего узла графа на Dashboard

## Интеграция с остальным Orchestrator

LangGraph Engine вызывается из основного цикла Orchestrator:

1. **Celery task** получает команду пользователя из RabbitMQ
2. Создаётся начальное состояние SwarmState
3. Формируется конфигурация с `thread_id`, ссылкой на чекпоинтер (PostgresSaver) и хранилище (PostgresStore)
4. Запускается граф в потоковом режиме
5. На каждом шаге графа обновления публикуются в Redis Pub/Sub для передачи на фронтенд
6. Результаты успешных планов сохраняются в долгосрочную память (store) для будущего семантического поиска
7. По завершении графа — итоговый статус записывается в PostgreSQL
