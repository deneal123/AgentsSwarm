# Orchestrator — Управление задачами

## Жизненный цикл задачи

Каждая задача проходит через определённые состояния:

**pending** → **assigned** → **executing** → **completed** / **failed**

С возможными промежуточными: **paused** (приостановлена при перепланировании), **cancelled** (отменена пользователем).

---

## Типы задач

| Тип | Описание | Пример |
|-----|----------|--------|
| `navigate` | Перемещение робота в целевую точку | «Робот 1, подойди к зоне А» |
| `search` | Поиск объекта в указанной зоне | «Найди красную коробку» |
| `pick_up` | Захват объекта манипулятором | «Возьми коробку» |
| `put_down` | Установка объекта | «Поставь коробку в зону А» |
| `scan` | Сканирование области (камера, лидар) | «Осмотри помещение» |
| `transport` | Комплексная задача: pick_up + navigate + put_down | «Принеси красную коробку в зону А» |
| `patrol` | Патрулирование маршрута | «Патрулируй периметр» |
| `composite` | Составная задача из нескольких подзадач | «Найди все коробки и отнеси в зону А» |

## Декомпозиция задач

Сложные задачи автоматически разбиваются на подзадачи. Пример:

**Команда пользователя:** «Роботы, найдите и принесите все красные коробки в зону А»

**Декомпозиция:**
1. Подзадача `search` (robot_001, sector_1): поиск красных коробок в секторе 1
2. Подзадача `search` (robot_002, sector_2): поиск красных коробок в секторе 2
3. Подзадача `search` (robot_003, sector_3): поиск красных коробок в секторе 3
4. Подзадача `pick_up` (ожидает результатов поиска): захват найденной коробки
5. Подзадача `transport` (ожидает pick_up): транспортировка в зону А

Подзадачи могут иметь зависимости (задача 4 зависит от завершения задач 1–3) и выполняться параллельно (задачи 1–3).

### Интеграция с LangGraph Send API

Параллельная декомпозиция реализуется через механизм Send API в LangGraph. Узел Generate Plan после создания плана с N подзадачами динамически генерирует N объектов Send, каждый из которых направляет выполнение в узел-обработчик подзадачи с уникальным состоянием. Количество параллельных ветвей определяется на этапе выполнения (runtime), а не при компиляции графа.

Результаты всех параллельных ветвей объединяются через редьюсеры состояния SwarmState (поле actions) перед переходом к узлу Monitor Execution.

### Валидация задач через Guardrails

Перед выполнением каждого плана Safety Agent проверяет его через инструмент check_safety_constraints. Этот инструмент определён с tool guardrail и механизмом tripwire: при обнаружении критического нарушения безопасности (человек в рабочей зоне, выход за допустимые границы) выполнение плана немедленно прерывается.

Дополнительно, входные guardrails на уровне агентного цикла проверяют:
- Корректность идентификаторов роботов (существование, онлайн-статус)
- Допустимость параметров команд (скорость, координаты в пределах рабочей зоны)
- Наличие необходимых возможностей у робота (манипулятор для pick_up, камера для search)

## Назначение роботов

### Критерии выбора робота

ResourceManager оценивает кандидатов по следующим параметрам:

1. **Возможности (capabilities):** робот должен иметь необходимое оборудование (манипулятор для pick_up, камера для search)
2. **Расстояние:** приоритет роботу, ближайшему к месту выполнения задачи
3. **Заряд батареи:** робот должен иметь достаточно энергии для выполнения задачи и возврата к зарядной станции
4. **Текущая загрузка:** свободный робот предпочтительнее занятого (если нет приоритетных задач)
5. **Приоритет задачи:** высокоприоритетная задача может прервать низкоприоритетную

### Формула оценки

Для каждого кандидата вычисляется score:

$score = w_1 \cdot capability\_match + w_2 \cdot (1 - distance\_norm) + w_3 \cdot battery\_norm + w_4 \cdot (1 - load\_norm)$

Где $w_1, w_2, w_3, w_4$ — настраиваемые веса, нормализованные значения в диапазоне [0, 1].

Робот с наивысшим score назначается на задачу.

## Мониторинг выполнения

### Источники информации о статусе

- **MQTT-подтверждения (ack):** робот публикует `ack/{robot_id}/{command_id}` со статусом `received`, `executing`, `completed`, `failed`
- **Телеметрия:** Orchestrator отслеживает позицию робота и определяет прогресс навигационных задач
- **Детекции:** результаты детекции подтверждают успешность задач search/pick_up
- **Таймауты:** если от робота нет обновлений дольше заданного времени — задача считается зависшей

### Действия при проблемах

| Проблема | Действие |
|----------|----------|
| Таймаут ожидания ack | Повторная отправка команды (до 3 раз) |
| Робот сообщает об ошибке | Анализ ошибки, при возможности — назначение другого робота |
| Робот застрял (нет прогресса) | Отмена задачи, перепланирование |
| Робот разрядился | Отправка на зарядку, переназначение задачи |
| Экстренная ситуация | Немедленная остановка, перепланирование всего роя |

## Хранение задач

### PostgreSQL (долговременное хранение)

Все задачи сохраняются в таблице `tasks` с полной историей: кто создал, когда назначена, когда выполнена, результат.

Составные задачи хранятся иерархически: корневая задача (`parent_task_id = NULL`) и подзадачи (`parent_task_id` ссылается на корневую).

### Redis (оперативное хранение)

Активные задачи дублируются в Redis для быстрого доступа:
- `task:{id}` — текущий статус и параметры задачи
- `robot:{id}:current_task` — идентификатор текущей задачи робота
- `plan:{plan_id}` — текущий активный план

## Celery интеграция

### Типы Celery-задач

- **Синхронные задачи:** обработка одной команды пользователя (цепочка LangGraph)
- **Периодические задачи:** проверка здоровья роботов (каждые 30 секунд), очистка устаревших данных (каждый час), генерация аналитики (каждые 5 минут)
- **Цепочки задач (chains):** последовательное выполнение зависимых подзадач
- **Группы задач (groups):** параллельное выполнение независимых подзадач
- **Chord:** параллельное выполнение с callback при завершении всех

### Конфигурация Celery

- Брокер: RabbitMQ
- Backend результатов: Redis
- Сериализация: JSON
- Таймаут задачи: настраивается per task (по умолчанию 300 секунд)
- Prefetch count: 1 (для равномерного распределения)
- Concurrency: 4 worker'а на pod (настраивается)
