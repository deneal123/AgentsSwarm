# Triton Inference — Модели и пайплайны

## Модели в Model Repository

### YOLO26 / YOLOv8 — Детекция объектов

Основная модель компьютерного зрения платформы. Выполняет обнаружение объектов на изображениях с камер роботов. В качестве основной модели используется **YOLO26n** (nano-вариант семейства YOLO26 от Ultralytics) — обеспечивает оптимальный баланс скорости и точности для edge- и cloud-развёртывания. Также поддерживаются модели YOLOv8x/YOLOv8l для сценариев, требующих максимальной точности.

| Параметр | Значение |
|----------|---------|
| Архитектура | YOLO26n (основная), YOLOv8x / YOLOv8l (высокая точность) |
| Вход | Изображение 640×640×3 (RGB), динамический батч |
| Выход | Bounding boxes, class_id, confidence |
| Формат хранения | ONNX (с динамическими осями), автоматическая конвертация в TensorRT |
| Batch Size | 1–16 (dynamic batching) |
| Латентность | ~5 мс (TensorRT, A100, batch=1); до 36× ускорение по сравнению с ONNX |

#### Классы детекции

Модель обучена детектировать классы объектов, релевантные для робототехники: люди, препятствия, другие роботы, целевые объекты для манипуляции, элементы окружающей среды (стены, двери, проходы), опасные зоны.

#### Пре-процессинг

Перед подачей в модель изображение проходит: ресайз до целевого разрешения (640×640), нормализацию значений пикселей (деление на 255.0), транспозицию осей (HWC → CHW), приведение к типу FP16 (при использовании TensorRT FP16).

#### Пост-процессинг

Результаты модели обрабатываются: применяется Non-Maximum Suppression (NMS) с порогом IoU (по умолчанию 0.45), фильтрация по порогу уверенности (по умолчанию 0.25), преобразование координат обратно в исходное разрешение.

#### Экспорт модели в ONNX для Triton

Модели YOLO26/YOLOv8 экспортируются из формата Ultralytics в ONNX с включением **динамических осей** (dynamic shapes). Это позволяет Triton использовать Dynamic Batching — группировать несколько изображений в один батч переменного размера.

При экспорте Ultralytics автоматически извлекает **метаданные модели** (имена входов/выходов, размерности, типы данных, задача — detect/segment/pose). Эти метаданные сохраняются и затем передаются в конфигурацию Triton через параметр `metadata` в файле `config.pbtxt`, что позволяет Triton корректно интерпретировать входы и выходы модели без ручной настройки.

#### Альтернативный экспорт: прямой TensorRT engine

Для сценариев, где не требуется динамическая конвертация на стороне Triton, модель можно сразу экспортировать в формат TensorRT engine (файл `.engine`). Это исключает задержку первого запуска (компиляцию ONNX → TensorRT), но engine привязан к конкретной GPU-архитектуре и версии TensorRT. Рекомендуется для production-окружений с фиксированным оборудованием.

#### Нативная интеграция Ultralytics с Triton

Библиотека Ultralytics поддерживает **прямое использование Triton как inference-бэкенда**. Вместо локального файла модели указывается HTTP-адрес Triton-сервера и имя модели (например, через URL вида `http://<host>:8000/<model_name>` с указанием задачи — detect, segment и т. д.). При этом Ultralytics выполняет весь пре- и пост-процессинг на стороне клиента, а Triton — только GPU-inference. Это обеспечивает:

- Единообразный API вне зависимости от способа развёртывания (локально или на сервере)
- Прозрачное масштабирование: переключение между локальным и удалённым inference — замена одного параметра
- Сохранение всех возможностей Ultralytics (визуализация, трекинг, экспорт результатов)

### ByteTrack — Трекинг объектов

Алгоритм многообъектного трекинга (MOT), работающий поверх детекций YOLO.

| Параметр | Значение |
|----------|---------|
| Алгоритм | ByteTrack |
| Вход | Bounding boxes от YOLO + предыдущие треки |
| Выход | Track ID, trajectory, velocity |
| Формат | Python Backend (Triton) |
| Латентность | ~1 мс |

#### Принцип работы

ByteTrack использует двухуровневую ассоциацию: сначала сопоставляет высокоуверенные детекции с существующими треками по IoU, затем обрабатывает низкоуверенные детекции для восстановления потерянных треков. Это обеспечивает устойчивость к кратковременным окклюзиям.

#### Управление треками

- **Создание**: новый трек создаётся при появлении детекции, не ассоциированной ни с одним существующим треком, после подтверждения в нескольких кадрах (по умолчанию 3 кадра)
- **Обновление**: координаты, скорость и направление обновляются с каждым кадром
- **Удаление**: трек удаляется, если объект не детектировался в течение настраиваемого числа кадров (по умолчанию 30 кадров)
- **Реидентификация**: при повторном появлении объекта используется визуальная схожесть (ReID features) для восстановления старого трека

### DeepSORT — Альтернативный трекер

Резервный алгоритм трекинга с использованием визуальных признаков для повышения точности реидентификации.

| Параметр | Значение |
|----------|---------|
| Алгоритм | DeepSORT |
| Вход | Bounding boxes + crop изображений |
| Выход | Track ID с ReID embedding |
| Формат | TensorRT (ReID CNN) + Python Backend |
| Латентность | ~8 мс (из-за извлечения ReID features) |

#### Отличия от ByteTrack

DeepSORT требует дополнительной CNN для извлечения визуальных дескрипторов (ReID), что увеличивает латентность, но повышает точность при длительных окклюзиях и при большом числе объектов одного класса. Используется в сценариях, где критична идентификация конкретного объекта.

### Семантическая сегментация

Модель для попиксельной классификации сцены.

| Параметр | Значение |
|----------|---------|
| Архитектура | DeepLab v3+ / SegFormer |
| Вход | Изображение 512×512×3 |
| Выход | Маска сегментации (H×W, каждый пиксель — class_id) |
| Формат | TensorRT |
| Латентность | ~12 мс (A100) |

#### Классы сегментации

Пол/земля, стены/препятствия, проходимые области, люди, роботы, целевые объекты, опасные зоны (жидкости, обрывы), транспортные пути.

#### Применение

Результаты сегментации используются для: построения карты проходимости, планирования маршрутов, обнаружения опасных зон, оценки рабочего пространства для манипуляторов.

### Depth Estimation — Оценка глубины

Монокулярная оценка глубины для построения 2.5D-карты окружения.

| Параметр | Значение |
|----------|---------|
| Архитектура | MiDaS / Depth Anything |
| Вход | Изображение 384×384×3 |
| Выход | Карта глубины (H×W, значение — расстояние в условных единицах) |
| Формат | TensorRT |
| Латентность | ~10 мс (A100) |

#### Применение

Используется совместно с данными LiDAR (при наличии) для создания более точной 3D-реконструкции, а также при отказе LiDAR — как основной источник информации о глубине. Помогает в оценке расстояний до объектов без стереокамер.

---

### Pose Estimation — Оценка позы

Оценка позы людей для задач безопасности и взаимодействия.

| Параметр | Значение |
|----------|---------|
| Архитектура | YOLOv8-pose |
| Вход | Изображение 640×640×3 |
| Выход | 17 ключевых точек тела (COCO формат) |
| Формат | TensorRT |
| Латентность | ~7 мс (A100) |

#### Применение

Определение позы людей для: предотвращения столкновений (оценка направления движения), обнаружения жестов и сигналов, оценки безопасности рабочей зоны, обнаружения упавших людей (Safety Agent).

## Производительность TensorRT

### Ускорение по сравнению с ONNX Runtime

Конвертация моделей YOLO из ONNX в TensorRT даёт значительный прирост производительности. По результатам бенчмарков, ускорение для модели YOLO26n на NVIDIA GPU составляет **до 36× по скорости inference** по сравнению с выполнением в ONNX Runtime. Это обеспечивается оптимизациями TensorRT: слияние слоёв (layer fusion), оптимизация ядер под конкретную GPU-архитектуру, использование тензорных ядер при FP16.

### Кэширование TensorRT Engine

При использовании ONNX-моделей с TensorRT-бэкендом Triton выполняет конвертацию в TensorRT engine при первой загрузке модели. Этот процесс занимает от нескольких десятков секунд до нескольких минут в зависимости от размера модели и сложности графа. Скомпилированный engine сохраняется в указанную директорию кэша (настраивается через параметр `trt_engine_cache_path` в конфигурации модели). Все последующие запуски используют кэш и происходят практически мгновенно.

### Рекомендации по развёртыванию

- Для production-окружений рекомендуется либо заранее прогревать кэш TensorRT (выполнить один inference после запуска), либо использовать предварительно скомпилированные `.engine` файлы
- Кэш engine привязан к конкретной GPU-архитектуре, версии CUDA и TensorRT — при смене оборудования кэш пересоздаётся автоматически
- Рабочая область (workspace) TensorRT по умолчанию настроена на 3 ГБ (`max_workspace_size_bytes: 3221225472`), что достаточно для большинства моделей YOLO

## Ensemble-пайплайны

### Пайплайн «Полный анализ сцены»

Комплексный пайплайн для полного понимания окружения робота. Выполняется по запросу или периодически (каждые 5–10 секунд).

**Последовательность выполнения:**

1. **Этап 1 (параллельный)**: YOLO-детекция + Семантическая сегментация + Оценка глубины
2. **Этап 2**: ByteTrack (использует результаты YOLO из этапа 1)
3. **Этап 3 (агрегация)**: Объединение всех результатов в единую структуру SceneAnalysis

Результат содержит: список объектов с ID трека, классом, координатами в 3D (с учётом карты глубины), маску проходимости, информацию о людях и их позах.

### Пайплайн «Быстрая детекция»

Облегчённый пайплайн для задач, требующих минимальной латентности.

**Последовательность:** YOLO-детекция → ByteTrack (только высокоуверенные)

Используется для: навигации в реальном времени, реактивного обхода препятствий, критических ситуаций безопасности.

### Пайплайн «Манипуляция»

Специализированный пайплайн для задач захвата и перемещения объектов.

**Последовательность:**

1. YOLO-детекция (целевой объект)
2. Segmentation (точная маска объекта)
3. Depth Estimation (расстояние до объекта)
4. Pose Estimation (если рядом находится человек)
5. Агрегация → 6DoF-оценка объекта

---

## Маршрутизация запросов

Выбор пайплайна определяется типом задачи и контекстом:

| Тип задачи | Пайплайн | Приоритет |
|------------|----------|-----------|
| Навигация | Быстрая детекция | Высокий |
| Патрулирование | Полный анализ | Средний |
| Манипуляция | Манипуляция | Высокий |
| Обзор окружения | Полный анализ | Низкий |
| Экстренная ситуация | Быстрая детекция | Критический |

Приоритет определяет порядок обработки в очереди при перегрузке GPU. Запросы с критическим приоритетом вытесняют низкоприоритетные.

## Хранение результатов

### Redis Feature Store

Результаты каждого inference сохраняются в Redis для быстрого доступа:

- **Детекции**: последние N кадров для каждого робота, TTL 30 секунд
- **Треки**: активные треки для каждого робота, TTL 60 секунд
- **Сегментация**: последняя маска для каждого робота, TTL 10 секунд
- **Сцена**: полный результат SceneAnalysis, TTL 30 секунд

### MinIO (долгосрочное)

Изображения и результаты анализа для инцидентов и обучения сохраняются в MinIO: изображения кадров, результаты детекции в JSON, маски сегментации, метаданные для последующего дообучения.
