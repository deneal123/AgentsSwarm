# Triton Inference — Конфигурация и оптимизация

## Структура Model Repository

Triton использует файловую систему (или S3-совместимое хранилище, в нашем случае MinIO) для хранения моделей. Каждая модель располагается в отдельной директории с фиксированной структурой.

### Организация

Корневая директория Model Repository содержит поддиректории для каждой модели. Внутри каждой — конфигурационный файл и поддиректории версий. Версии именуются числами (1, 2, 3...), последняя загружается по умолчанию.

#### Конкретная структура для YOLO-модели

Для модели YOLO используется следующая файловая структура внутри репозитория:

```
triton_repo/
└── yolo/
    ├── config.pbtxt
    └── 1/
        └── model.onnx
```

- `triton_repo/` — корневая директория Model Repository, монтируемая в контейнер Triton
- `yolo/` — директория модели (имя определяет endpoint: `/v2/models/yolo`)
- `config.pbtxt` — конфигурация модели (описание входов/выходов, оптимизация, метаданные)
- `1/` — директория версии (номер версии)
- `model.onnx` — файл модели в формате ONNX с динамическими осями

Аналогичная структура используется для остальных моделей (segmentation, depth_estimation, bytetrack и др.).

### Конфигурация модели YOLO (config.pbtxt)

Конфигурационный файл `config.pbtxt` для модели YOLO содержит следующие ключевые секции:

#### Основные параметры

- **name** — имя модели (например, `yolo`), совпадает с именем директории
- **backend** — `onnxruntime` (Triton использует ONNX Runtime с возможностью TensorRT-оптимизации)

#### Параметр metadata

В секции `parameters` указывается ключ `metadata` со строковым значением, содержащим JSON-сериализованные метаданные модели. Эти метаданные автоматически извлекаются при экспорте модели из Ultralytics и включают: имена и размерности входных/выходных тензоров, тип задачи (detect, segment, pose), количество классов, имена классов. Triton и клиентские библиотеки Ultralytics используют эти метаданные для корректной интерпретации входов и выходов.

#### Секция оптимизации (optimization)

В блоке `optimization` → `execution_accelerators` → `gpu_execution_accelerator` настраивается TensorRT-оптимизация:

| Параметр | Значение | Описание |
|----------|---------|----------|
| `name` | `tensorrt` | Активация TensorRT-бэкенда |
| `precision_mode` | `FP16` | Половинная точность — ускорение ~2× при минимальной потере качества |
| `max_workspace_size_bytes` | `3221225472` (3 ГБ) | Максимальная рабочая область GPU для построения TensorRT-плана |
| `trt_engine_cache_enable` | `1` | Включение кэширования скомпилированного TensorRT engine |
| `trt_engine_cache_path` | путь к директории кэша | Директория для хранения кэшированных engine-файлов |

Кэширование TensorRT engine критически важно: первая загрузка модели включает компиляцию ONNX → TensorRT (минуты), все последующие загрузки используют кэш (секунды).

### Хранилище моделей в MinIO

Model Repository размещается в MinIO-бакете, что обеспечивает: версионирование на уровне хранилища, репликацию между нодами, доступ через S3-совместимый API, интеграцию с CI/CD пайплайном обновления моделей.

Triton настраивается на MinIO через параметры: endpoint URL, access key, secret key, bucket name.

## Конфигурация моделей

### Параметры конфигурации

Для каждой модели задаются:

- **Платформа**: TensorRT, ONNX Runtime, PyTorch, Python Backend
- **Входы и выходы**: имена, типы данных, размерности (с поддержкой динамических осей)
- **Instance Group**: количество экземпляров модели на GPU, привязка к конкретным GPU
- **Dynamic Batching**: параметры автоматической группировки запросов

### Instance Groups

Определяют, сколько экземпляров модели загружается и на каких устройствах:

| Модель | Экземпляры | Устройство | Обоснование |
|--------|-----------|------------|-------------|
| YOLO26/v8 | 2 | GPU 0 | Основная нагрузка, параллельные запросы |
| ByteTrack | 1 | CPU | Лёгкий алгоритм, не требует GPU |
| DeepSORT ReID | 1 | GPU 0 | Средняя нагрузка |
| Сегментация | 1 | GPU 1 | Большой расход памяти |
| Depth Estimation | 1 | GPU 1 | Параллельно с сегментацией |
| Pose Estimation | 1 | GPU 0 | По запросу, нечастый |

При наличии одного GPU все модели размещаются на нём, при этом Triton управляет конкуренцией через внутренний планировщик.

## Dynamic Batching

### Принцип работы

Когда несколько запросов поступают с малым интервалом, Triton объединяет их в один батч для GPU. Это значительно повышает throughput при незначительном увеличении латентности.

### Настройка по моделям

| Модель | Max Batch | Preferred Sizes | Max Queue Delay |
|--------|-----------|-----------------|-----------------|
| YOLO26/v8 | 16 | 1, 4, 8 | 100 мкс |
| Сегментация | 8 | 1, 4 | 200 мкс |
| Depth Estimation | 8 | 1, 4 | 200 мкс |
| Pose Estimation | 8 | 1, 4 | 150 мкс |
| DeepSORT ReID | 32 | 8, 16 | 500 мкс |

### Preferred Batch Sizes

Указание предпочтительных размеров батча помогает Triton принимать решение: ждать ещё запросов до preferred size или отправлять текущий батч. Размеры выбраны так, чтобы эффективно утилизировать тензорные ядра GPU (кратные 8 для TensorRT).

### Sequence Batching

Для трекера (ByteTrack) используется Sequence Batching вместо Dynamic Batching, так как трекинг требует сохранения состояния между кадрами одного потока. Каждый робот образует отдельную sequence, и Triton гарантирует маршрутизацию всех кадров одного робота к одному и тому же экземпляру модели.

## Оптимизация производительности

### TensorRT

Для максимальной производительности модели конвертируются в формат TensorRT:

- **FP16**: режим половинной точности, ускорение в ~2 раза при минимальной потере качества (потеря mAP < 0.5% для YOLO). Рекомендован для production. Для моделей YOLO26/YOLOv8 бенчмарки показывают **до 36× ускорения** по сравнению с ONNX Runtime
- **INT8**: режим квантизации до 8 бит, ускорение до 4 раз. Требует калибровочного датасета. Используется для моделей, где допустима потеря точности (Depth Estimation)
- **Dynamic Shapes**: TensorRT планы компилируются с поддержкой переменного размера батча (min=1, opt=4, max=16), что позволяет работать с Dynamic Batching. Для этого модель должна быть экспортирована в ONNX с динамическими осями

### Кэширование TensorRT Engine

При использовании ONNX-моделей с включённой TensorRT-оптимизацией Triton автоматически выполняет конвертацию ONNX → TensorRT engine при первой загрузке модели. Поведение:

1. **Первый запуск**: компиляция TensorRT engine из ONNX — занимает от 30 секунд до нескольких минут в зависимости от размера модели и GPU
2. **Сохранение**: скомпилированный engine сохраняется в директорию кэша (параметр `trt_engine_cache_path` в config.pbtxt)
3. **Последующие запуски**: Triton обнаруживает кэш и загружает engine напрямую — запуск за секунды
4. **Инвалидация**: кэш автоматически пересоздаётся при изменении модели, версии CUDA, версии TensorRT или GPU-архитектуры

Рекомендация для production: включить кэширование (`trt_engine_cache_enable: 1`) и использовать persistent volume для директории кэша, чтобы кэш сохранялся при перезапуске контейнера.

### GPU Memory Management

- **CUDA Memory Pool**: Triton использует пул памяти для минимизации аллокаций
- **Pinned Memory**: используется для ускорения передачи данных CPU ↔ GPU
- **Model Loading Strategy**: 
  - **poll**: модели загружаются при обнаружении в репозитории
  - **explicit**: модели загружаются только по API-запросу (используется для редко вызываемых моделей)
- **GPU Memory Fraction**: при нескольких моделях на одном GPU ограничивается максимальная доля памяти для каждой (через instance_group и memory settings)

### CUDA Streams и Concurrency

Triton создаёт отдельные CUDA-потоки для каждого экземпляра модели, что обеспечивает параллельное выполнение inference на одном GPU. Параметр `rate_limiter` позволяет ограничить конкуренцию при нехватке памяти.

## Ensemble Configuration

### Scheduler

Ensemble-пайплайн использует собственный планировщик, который: определяет зависимости между моделями, параллельно запускает независимые этапы, агрегирует результаты.

### Промежуточные тензоры

Между моделями в ensemble данные передаются через разделяемую память (shared memory), что исключает лишние копирования CPU ↔ GPU. Промежуточные тензоры остаются на GPU.

### Пример конфигурации «Полный анализ сцены»

Ensemble определяет:

1. **Input**: image (FP16, -1×3×640×640)
2. **Step 1** (параллельно): yolov8_detection, segmentation, depth_estimation
3. **Step 2**: bytetrack_tracker (входы: boxes от yolov8 + sequence_id)
4. **Step 3**: scene_aggregation (Python Backend, собирает все результаты)
5. **Output**: scene_analysis (JSON-сериализованный результат)

## Docker-развёртывание Triton

### Базовый образ

Triton Inference Server развёртывается из официального Docker-образа NVIDIA:

| Параметр | Значение |
|----------|---------|
| Образ | `nvcr.io/nvidia/tritonserver:24.09-py3` |
| Размер образа | ~8.57 ГБ |
| Содержимое | Triton Server, ONNX Runtime, TensorRT, PyTorch Backend, Python Backend |

### Запуск контейнера

Контейнер запускается с NVIDIA GPU runtime и монтированием Model Repository:

- **Runtime**: `--runtime=nvidia` с указанием конкретных GPU (например, `--gpus 0` или `--gpus all`)
- **Монтирование**: локальная директория Model Repository (например, `triton_repo/`) монтируется в `/models` внутри контейнера
- **Порты**: 8000 (HTTP), 8001 (gRPC), 8002 (Metrics)
- **Команда**: `tritonserver --model-repository=/models` с дополнительными параметрами по необходимости

### Параметры запуска сервера

| Параметр | Описание |
|----------|----------|
| `--model-repository` | Путь к Model Repository внутри контейнера |
| `--repository-poll-secs` | Интервал проверки обновлений моделей (секунды) |
| `--strict-model-config=false` | Автогенерация конфигурации для моделей без config.pbtxt |
| `--log-verbose=1` | Уровень детализации логов |

### Docker Compose

В составе AgentsSwarm Triton описывается как сервис в docker-compose с: привязкой к GPU-ресурсам через `deploy.resources.reservations.devices`, монтированием тома моделей, настройкой health check по HTTP-эндпоинту `/v2/health/ready`, зависимостями от MinIO (для загрузки моделей) и сети для связи с Orchestrator.

## Клиентское взаимодействие

### Библиотека tritonclient

Для программного взаимодействия с Triton используется Python-пакет `tritonclient[all]`, предоставляющий клиенты для HTTP и gRPC протоколов.

#### Проверка готовности

Перед отправкой inference-запросов рекомендуется проверить готовность сервера и конкретной модели:

1. Создание HTTP-клиента с указанием адреса Triton (например, `localhost:8000`)
2. Опрос метода `is_model_ready(model_name)` в цикле с задержкой (рекомендуется 0.5 с)
3. После получения подтверждения готовности — отправка inference-запросов

Этот паттерн критичен при автоматическом развёртывании, так как загрузка модели и компиляция TensorRT engine занимают время.

#### Отправка inference-запроса

Через `tritonclient` формируются входные тензоры (имя, форма, тип данных), выполняется вызов `infer()` с указанием имени модели и списка входов, результат содержит выходные тензоры с результатами детекции.

### Интеграция через Ultralytics

Альтернативный и более высокоуровневый способ взаимодействия — через библиотеку Ultralytics. Модель YOLO инициализируется с URL Triton-сервера вместо пути к локальному файлу:

- URL формируется как `http://<host>:<http_port>/<model_name>` (например, `http://localhost:8000/yolo`)
- Указывается тип задачи: `detect`, `segment`, `pose` и др.
- Ultralytics автоматически выполняет всю пре- и пост-обработку (ресайз, нормализация, NMS)
- Результаты возвращаются в стандартном формате Ultralytics Results (bounding boxes, класcы, confidence, маски)

Этот подход рекомендуется для клиентских приложений, которые уже используют Ultralytics, так как обеспечивает единый API для локального и удалённого inference.

## Мониторинг и метрики

### Встроенные метрики Triton

Triton экспортирует метрики в формате Prometheus (порт 8002):

| Метрика | Описание |
|---------|----------|
| nv_inference_request_success | Количество успешных запросов |
| nv_inference_request_failure | Количество ошибок |
| nv_inference_count | Общее число inference |
| nv_inference_exec_count | Число выполнений (с учётом батчинга) |
| nv_inference_request_duration_us | Время обработки запроса (мкс) |
| nv_inference_queue_duration_us | Время ожидания в очереди (мкс) |
| nv_inference_compute_input_duration_us | Время подготовки входных данных |
| nv_inference_compute_infer_duration_us | Время собственно inference |
| nv_inference_compute_output_duration_us | Время подготовки выходных данных |
| nv_gpu_utilization | Утилизация GPU (0–1) |
| nv_gpu_memory_total_bytes | Общая память GPU |
| nv_gpu_memory_used_bytes | Используемая память GPU |

### Алерты

| Условие | Уровень | Действие |
|---------|---------|----------|
| GPU utilization > 90% (5 мин) | Warning | Уведомление, рассмотреть масштабирование |
| Queue duration > 50 мс (p99) | Warning | Увеличить instance count или batch size |
| Inference failure rate > 1% | Critical | Проверить модель, перезагрузить |
| GPU memory > 95% | Critical | Выгрузить редко используемые модели |
| Inference latency > 100 мс (p99) | Warning | Оптимизировать модель или пайплайн |

## Масштабирование

### Горизонтальное

При увеличении числа роботов (и соответственно запросов) Triton масштабируется:

- **Kubernetes**: Deployment с HPA (Horizontal Pod Autoscaler) по метрике GPU utilization или queue depth
- **GPU Node Pool**: автоматическое масштабирование пула GPU-нод в облаке
- **Model Sharding**: разные модели на разных нодах (например, нода 1 — детекция, нода 2 — сегментация+глубина)

### Вертикальное

- Переход на более мощные GPU (A10G → A100)
- Увеличение instance count на GPU
- Оптимизация моделей (FP16 → INT8)
- Уменьшение разрешения входных изображений

### Целевые показатели

| Параметр | Целевое значение |
|----------|-----------------|
| Латентность детекции (p95) | < 20 мс |
| Латентность полного анализа (p95) | < 50 мс |
| Throughput (запросов/сек, 1 GPU) | > 100 |
| GPU utilization (рабочий режим) | 60–80% |
| Доступность | 99.9% |

## Обновление моделей

### Процедура обновления

1. Новая версия модели загружается в MinIO в новую поддиректорию версии
2. Triton обнаруживает обновление через polling (или через Model Control API)
3. Новая версия загружается в память GPU
4. Трафик переключается на новую версию (latest version policy)
5. Старая версия остаётся загруженной для возможного отката
6. После подтверждения стабильности старая версия выгружается

### Canary Deployment

Поддерживается A/B-тестирование моделей: через Kubernetes можно направить часть трафика на Triton-под с новой моделью, сравнить метрики качества и производительности перед полным переключением.

### Откат

При обнаружении деградации качества или производительности: откат через Model Control API (загрузка предыдущей версии), или через Kubernetes rollback (возврат к предыдущему деплойменту).
