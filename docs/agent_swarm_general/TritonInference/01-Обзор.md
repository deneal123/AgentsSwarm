# Triton Inference Server — Обзор

## Назначение

Triton Inference Server (NVIDIA) — микросервис для выполнения ресурсоёмких задач компьютерного зрения на GPU. Обрабатывает изображения с камер роботов, выполняет детекцию объектов, трекинг, сегментацию и оценку глубины.

---

## Зона ответственности

- Детекция объектов в реальном времени (YOLO26 / YOLOv8 через Ultralytics)
- Трекинг объектов между кадрами (ByteTrack, DeepSORT)
- Семантическая сегментация сцены
- Оценка глубины (Depth Estimation)
- Оценка позы (Pose Estimation)
- Ensemble-пайплайны для сложных задач (детекция → трекинг → сегментация)

## Технология

| Параметр | Значение |
|----------|---------|
| Платформа | NVIDIA Triton Inference Server |
| Docker-образ | `nvcr.io/nvidia/tritonserver:24.09-py3` (~8.57 GB) |
| GPU | NVIDIA A100, A10G или аналогичные |
| Формат моделей | ONNX (основной, с конвертацией в TensorRT), TensorRT engine, PyTorch (TorchScript) |
| API | HTTP/REST (порт 8000), gRPC (порт 8001), Metrics/Prometheus (порт 8002) |
| Клиентская библиотека | `tritonclient[all]` (Python) |
| Интеграция с Ultralytics | Нативная — модели YOLO26/YOLOv8 загружаются напрямую как Triton-модели |

## Взаимодействие

### Входящие запросы

| Источник | Протокол | Описание |
|----------|----------|----------|
| Orchestrator | gRPC | Запрос детекции по изображению |
| RobotEdge (fallback) | gRPC Streaming | Прямой потоковый запрос при необходимости |
| Data Aggregation Service | gRPC | Пакетная обработка сохранённых изображений |

### Исходящие данные

| Назначение | Канал | Описание |
|-----------|-------|----------|
| Redis Feature Store | Redis Protocol | Результаты детекции и трекинга |
| Orchestrator | gRPC Response | Ответ на запрос |

## Ключевые возможности Triton

### Dynamic Batching
Triton автоматически группирует несколько входящих запросов в один батч для оптимального использования GPU. Настраиваемые параметры: максимальный размер батча, максимальная задержка ожидания (preferred_batch_size, max_queue_delay_microseconds).

### Model Ensemble
Triton поддерживает создание пайплайнов из нескольких моделей, где выход одной модели подаётся на вход другой. Пример: изображение → YOLO (детекция) → ByteTrack (трекинг) → результат.

### Model Versioning
Каждая модель может иметь несколько версий. Triton поддерживает одновременную загрузку нескольких версий для A/B тестирования и плавного перехода на новую версию.

### Model Repository Polling
Triton периодически проверяет хранилище моделей на наличие обновлений. Новые модели загружаются автоматически без перезапуска сервера (параметр: `--repository-poll-secs=30`).

### Metrics
Встроенный экспорт метрик в формате Prometheus (порт 8002): inference latency, GPU utilization, queue depth, throughput, batch size distribution.

### TensorRT Backend с автоматическим кэшированием

При использовании ONNX-моделей Triton автоматически конвертирует их в TensorRT-планы при первой загрузке. Первый запуск модели занимает значительно больше времени из-за этой конвертации (минуты). Скомпилированный TensorRT engine сохраняется в кэш, и все последующие запуски используют кэшированную версию, запускаясь за секунды. Это позволяет хранить модели в универсальном ONNX-формате, получая при этом максимальную производительность TensorRT.

### Нативная интеграция с Ultralytics

Библиотека Ultralytics (YOLO26, YOLOv8 и др.) поддерживает прямое взаимодействие с Triton-сервером. Модель YOLO можно инициализировать, указав URL Triton-эндпоинта и имя модели вместо локального файла. При этом Ultralytics берёт на себя пре- и пост-процессинг (ресайз, нормализацию, NMS), а Triton выполняет собственно inference на GPU. Это упрощает клиентский код и обеспечивает единообразный интерфейс для локального и удалённого inference.

### Проверка готовности сервера и моделей

Triton предоставляет эндпоинты для проверки состояния: готовность сервера (health/ready), готовность конкретной модели (model ready). Через клиентскую библиотеку `tritonclient` можно в цикле опрашивать готовность модели, что используется в скриптах развёртывания для ожидания полной инициализации сервера перед отправкой inference-запросов. Рекомендуемая стратегия — периодический опрос с задержкой (например, каждые 0.5 секунды) до получения подтверждения готовности.
