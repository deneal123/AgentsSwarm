# MQTT Брокер (EMQX)

## Роль

MQTT-брокер — основной канал связи между роботами и облачной платформой. Отвечает за безопасность, маршрутизацию сообщений, хранение оффлайн-сообщений и управление подключениями. Работает по модели Publish/Subscribe: издатели публикуют сообщения в иерархические топики, а подписчики получают сообщения из интересующих их топиков. Брокер EMQX выступает посредником, управляя маршрутизацией и доставкой.

---

## Протокол MQTT

### Версии протокола

Система поддерживает MQTT v3.1.1 и MQTT v5.0. Версия v5.0 является предпочтительной для новых интеграций благодаря расширенным возможностям:

- **MQTT v3.1.1** — стабильный базовый протокол, широкая совместимость с устройствами. Параметр `clean_session` управляет персистентностью сессий
- **MQTT v5.0** — расширенная версия с поддержкой:
  - Properties на сообщениях (connect, publish, subscribe) для передачи метаданных
  - Reason codes — детальные коды ответов от брокера на каждую операцию
  - Topic aliases — числовые псевдонимы для снижения overhead при частых публикациях в один и тот же топик
  - Параметр `clean_start` вместо `clean_session`: управляет только начальным состоянием сессии, а `session_expiry_interval` — временем жизни сессии отдельно
  - Shared Subscriptions — стандартизированная балансировка нагрузки между подписчиками

### Транспортные уровни

| Транспорт | Порт | Применение в AgentsSwarm |
|-----------|------|--------------------------|
| TCP | 1883 | Основной канал: роботы в пределах VPN/внутренней сети |
| TLS/mTLS | 8883 | Безопасный канал: роботы через публичный интернет |
| WebSocket | 8083 | Dashboard UI, Chat Interface — браузерные клиенты |
| WebSocket + TLS | 8084 | Безопасные браузерные подключения |

Настройка TLS выполняется с указанием CA-сертификата, клиентского сертификата и ключа. Для mTLS (mutual TLS) брокер требует и валидирует сертификат каждого робота, что обеспечивает строгую аутентификацию устройств.

## Конфигурация EMQX

- **Кластеризация**: несколько нод EMQX с шардингом подключений для горизонтального масштабирования
- **Persistence**: хранение retained-сообщений и offline queues в persistent storage
- **Authentication**: JWT-токены и mTLS-сертификаты для устройств; возможна интеграция с внешним auth-провайдером
- **ACL**: per-topic ACL на уровне топиков с ролевыми и групповыми политиками; фильтрация по шаблонам с подстановкой client_id, username
- **LWT**: Last Will and Testament для обнаружения падения роботов (см. раздел ниже)
- **Rate Limiting**: ограничение скорости публикаций и подключений на уровне клиента и глобально
- **Shared Subscription**: поддержка `$share/<group>/<topic>` для балансировки нагрузки между несколькими обработчиками

## QoS — Уровни качества обслуживания

MQTT определяет три уровня QoS, каждый из которых предоставляет различные гарантии доставки:

### QoS 0 — At most once (fire-and-forget)

Сообщение отправляется один раз без подтверждения. Возможна потеря при сетевых проблемах. Используется для высокочастотной телеметрии, где потеря отдельного значения некритична (поза робота с частотой 10–50 Гц, температура, загрузка CPU). Минимальный overhead — максимальная производительность.

### QoS 1 — At least once

Сообщение доставляется гарантированно хотя бы один раз. Издатель отправляет PUBLISH, получатель отвечает PUBACK. Если PUBACK не получен в течение таймаута, издатель повторяет отправку. Возможны дубликаты — обработчик должен быть идемпотентным. Используется для команд роботам, событий, результатов задач, application-level acknowledgments.

### QoS 2 — Exactly once

Сообщение доставляется ровно один раз благодаря четырёхэтапному рукопожатию (PUBLISH → PUBREC → PUBREL → PUBCOMP). Максимальная гарантия, но наибольший overhead. Используется ограниченно: критические команды безопасности (аварийная остановка, переключение режимов), финансовые/бизнес-события. Не рекомендуется для массовой телеметрии из-за нагрузки на брокер.

### Выбор QoS по типу сообщения

| Тип сообщения | QoS | Обоснование |
|---------------|-----|-------------|
| Телеметрия (поза, сенсоры) | 0 | Высокая частота, потеря одного значения некритична |
| Метрики системы | 0 или 1 | Зависит от важности |
| Команды роботам | 1 | Гарантия доставки, идемпотентная обработка |
| Подтверждение выполнения (ack) | 1 | Надёжная обратная связь |
| Аварийная остановка (E-Stop) | 2 | Ровно одно выполнение |
| Обновление конфигурации | 1 | Гарантированная доставка, идемпотентна |
| Статус робота (online/offline) | 1 + retain | Всегда доступен последний известный статус |

## Управление подключениями

### Keepalive

Механизм keepalive обеспечивает обнаружение разрыва соединения. Клиент периодически отправляет PINGREQ, брокер отвечает PINGRESP. Значение по умолчанию — 60 секунд. Если в течение 1.5 × keepalive_interval не было активности, брокер считает клиента отключённым и запускает LWT. Для роботов на нестабильных каналах рекомендуется keepalive 30–60 секунд; для Dashboard-клиентов — 60–120 секунд.

### Reconnect с экспоненциальным backoff

При потере соединения клиент автоматически пытается переподключиться. Стратегия — экспоненциальный backoff с параметрами:

- **min_delay** — минимальная задержка перед первой повторной попыткой (рекомендуется 1 секунда)
- **max_delay** — максимальная задержка между попытками (рекомендуется 120 секунд)

Задержка удваивается с каждой неудачной попыткой от min_delay до max_delay, затем остаётся на уровне max_delay. Это предотвращает «stampede» — лавинообразное переподключение всех роботов одновременно после сетевого инцидента.

### Персистентные сессии

- **MQTT v3.1.1**: параметр `clean_session=False` — брокер сохраняет подписки клиента и накапливает сообщения (QoS 1/2) в offline-очереди на время отключения. При переподключении клиент получает пропущенные сообщения. Флаг `session_present` в CONNACK указывает, была ли восстановлена существующая сессия
- **MQTT v5.0**: параметр `clean_start=False` + `session_expiry_interval` — аналогичная функциональность с отдельным контролем времени жизни сессии

Персистентные сессии критичны для роботов, которые могут временно терять связь: при восстановлении соединения все пропущенные команды и события будут доставлены.

## Last Will and Testament (LWT)

LWT — механизм обнаружения неожиданных отключений. Клиент при подключении регистрирует «завещание» — сообщение, которое брокер опубликует, если клиент отключится аварийно.

### Как работает

1. Робот при подключении задаёт LWT: топик, payload, QoS, retain
2. Робот работает нормально, периодически отправляет keepalive (PINGREQ)
3. Если связь прерывается (сеть, краш, обрыв TCP), брокер обнаруживает отсутствие PINGREQ в течение 1.5 × keepalive
4. Брокер публикует LWT-сообщение в заданный топик
5. Подписчики (Orchestrator, Dashboard, мониторинг) получают уведомление о падении робота

### Важно

- LWT публикуется только при **аварийном** отключении (потеря TCP, отсутствие PINGREQ, crash)
- При **штатном** отключении (клиент вызывает disconnect()) LWT **не** публикуется
- Для полной картины робот при штатном отключении должен явно опубликовать статусное сообщение перед disconnect()

### Конфигурация LWT в AgentsSwarm

- **Топик LWT**: `agentswarm/{tenant}/{robot_id}/status/lwt`
- **Payload**: JSON с кодом состояния, последней известной позицией, timestamp
- **QoS**: 1 (гарантированная доставка)
- **Retain**: True (любой новый подписчик сразу увидит последний известный статус)

## Retained Messages

Retained-сообщение — сообщение с флагом `retain=True`, которое брокер сохраняет как «последнее известное значение» для данного топика. Любой новый подписчик при подписке сразу получает последнее retained-сообщение, не дожидаясь следующей публикации.

Применение:

- Статус робота (online/offline/busy) — новый подписчик сразу знает текущее состояние
- Последняя известная позиция робота
- Текущая конфигурация робота
- Версии прошивки

## Система подписок и Wildcard

### Wildcard в подписках MQTT

MQTT поддерживает два wildcard-символа в подписках (но НЕ в публикациях):

- **`+`** (single-level wildcard) — заменяет ровно один уровень иерархии топика
  - `agentswarm/companyA/+/telemetry/pose` — телеметрия позиции всех роботов компании A
  - `agentswarm/+/robot_001/cmd/+` — все команды роботу 001 от любого тенанта

- **`#`** (multi-level wildcard) — заменяет ноль или более уровней, может стоять только в конце подписки
  - `agentswarm/companyA/robot_001/#` — все сообщения робота 001
  - `agentswarm/companyA/#` — все сообщения всех роботов компании A
  - `#` — все сообщения в системе (использовать только для отладки)

### Topic-specific callbacks

Клиент может зарегистрировать отдельные обработчики для конкретных шаблонов топиков через механизм message_callback_add. Это позволяет организовать обработку без единого диспетчера: каждый шаблон подписки получает свой callback, а общий on_message выступает fallback для необработанных сообщений. Порядок приоритета: topic-specific callback > общий on_message.

## Обработка сообщений

### Payload

Максимальный размер payload MQTT-сообщения — 256 МБ (268 435 455 байт), однако в AgentsSwarm рекомендуется ограничивать payload до минимума. Для крупных данных (изображения, 3D-облака точек) используется паттерн: в MQTT отправляется JSON с метаданными и ссылкой на объект в MinIO, а сами данные загружаются через MinIO (S3-совместимый API).

### Manual Acknowledgment

Для критичных сценариев можно включить ручное подтверждение обработки сообщений на стороне клиента (manual_ack). В этом режиме:

1. Клиент создаётся с параметром `manual_ack=True`
2. Сообщение считается обработанным только после явного вызова acknowledge с указанием message_id и QoS
3. До подтверждения сообщение остаётся «в обработке» и может быть повторно доставлено при разрыве соединения

Этот механизм предотвращает потерю сообщений при сбое обработки: если клиент упал во время обработки, сообщение будет повторно доставлено при переподключении.

### Отслеживание доставки

Каждая операция publish возвращает объект MQTTMessageInfo с:

- **mid** (message ID) — уникальный идентификатор сообщения в рамках сессии
- **rc** (return code) — код результата операции
- Метод wait_for_publish() — блокирующее ожидание до подтверждения доставки (актуально для QoS 1/2)
- Метод is_published() — проверка статуса доставки без блокировки

## Управление потоком

### Max Inflight Messages

Параметр max_inflight_messages ограничивает количество сообщений QoS > 0, которые одновременно находятся «в полёте» (отправлены, но ещё не подтверждены). По умолчанию — 20. Установка значения 1 обеспечивает строгий порядок доставки, но снижает пропускную способность. Для телеметрии роботов рекомендуется значение 20–50.

### Max Queued Messages

Параметр max_queued_messages ограничивает размер очереди исходящих сообщений в клиенте. По умолчанию — без ограничения. Значение 0 означает неограниченную очередь. Рекомендуется установить разумный лимит (1000–10000) для предотвращения OOM при длительной потере связи.

## Callback-система (Python-клиент Paho)

Paho MQTT Client предоставляет событийную модель через callbacks:

- **on_connect** — вызывается при успешном (или неуспешном) подключении к брокеру. Содержит reason_code с результатом и флаг session_present (была ли восстановлена персистентная сессия). Рекомендуется выполнять все подписки в on_connect — при переподключении они будут автоматически восстановлены
- **on_connect_fail** — вызывается при неудачной попытке подключения (до TCP handshake)
- **on_disconnect** — вызывается при отключении (штатном или аварийном). Reason code указывает причину
- **on_message** — вызывается при получении сообщения. Объект MQTTMessage содержит: topic, payload, qos, retain, mid, properties (v5.0), timestamp
- **on_publish** — вызывается при подтверждении отправки сообщения (для QoS 1: после PUBACK; для QoS 2: после PUBCOMP). Для QoS 0 вызывается сразу после помещения в исходящую очередь
- **on_subscribe** / **on_unsubscribe** — подтверждение подписки/отписки
- **on_log** — получение лог-сообщений от клиента для отладки

### Callback API v1 vs v2

Paho поддерживает две версии Callback API:

- **v1** (legacy): callbacks принимают параметры (client, userdata, ...) — userdata передаётся явно
- **v2** (рекомендуемый): callbacks принимают параметры (client, userdata, ...) с расширенными объектами (ConnectFlags, DisconnectFlags, Properties). Указывается при создании клиента через `CallbackAPIVersion.VERSION2`

В AgentsSwarm используется Callback API v2 для новых клиентов.

## Event Loop — Цикл обработки событий

Клиент Paho MQTT требует активного цикла обработки событий для работы с сетевым трафиком. Доступны три режима:

### loop_start() — Потоковый режим (рекомендуемый)

Запускает фоновый поток для обработки сетевого трафика. Основной поток свободен для логики приложения. Вызов loop_stop() завершает фоновый поток. Рекомендуется для сервисов AgentsSwarm (Edge AI Proxy, Gateway, Orchestrator).

### loop_forever() — Блокирующий режим

Блокирует текущий поток и обрабатывает события бесконечно. Автоматически переподключается при потере связи. Подходит для простых клиентов, которые только получают и обрабатывают сообщения (например, отдельный микросервис-подписчик).

### loop() — Ручной режим

Однократный вызов для обработки накопленных событий. Необходимо вызывать регулярно (чаще, чем keepalive_interval). Подходит для интеграции в собственный event loop (например, ROS 2 spin loop на Edge).

## Bridge Mode

Режим моста (bridge mode) предназначен для соединения двух MQTT-брокеров. Включение bridge mode гарантирует отсутствие зацикливания сообщений при подписке с wildcard `#` между брокерами. Применяется для:

- Подключение Edge-брокера (Mosquitto на роботе) к облачному EMQX
- Федерация между регионально распределёнными EMQX-кластерами
- Тестовые окружения с изолированными брокерами

## Отказоустойчивость

- **Кластеризация EMQX**: репликация состояния брокера (подписки, сессии, retained messages) между нодами
- **Автоматическое перенаправление**: при падении ноды подключения перебрасываются на живые ноды кластера
- **Мониторинг подключений**: алерты при массовых отключениях (потеря > N роботов за M секунд)
- **Persistent sessions**: накопление offline-сообщений для отключённых роботов с контролем TTL и максимального объёма
- **Graceful degradation**: при перегрузке — приоритизация QoS 2 > QoS 1 > QoS 0

## Proxy

Клиент Paho MQTT поддерживает подключение через прокси:

- **SOCKS4/SOCKS5** — для подключения через корпоративный прокси или Tor
- **HTTP CONNECT** — для подключения через HTTP-прокси

Настройка прокси выполняется через указание типа прокси, адреса, порта и (опционально) учётных данных. Используется на Edge-устройствах в корпоративных сетях с ограниченным выходом в интернет.

## Best Practices

- Разделение топиков по namespace: `{tenant}/{robot_id}/{component}/{channel}` — строгая иерархия
- Минимизация payload: метаданные + ссылки на MinIO вместо передачи изображений/3D-данных напрямую
- Использование LWT для быстрого обнаружения аварийных отключений + явное сообщение при штатном disconnect
- Retained messages для текущего статуса и конфигурации
- Подписки в on_connect: автоматическое восстановление подписок при переподключении
- Персистентные сессии (`clean_session=False`) для роботов, которые могут терять связь
- Экспоненциальный backoff при reconnect: min_delay=1, max_delay=120
- Manual ack для критичных команд — предотвращение потери при сбое обработки
- max_inflight_messages=20 для баланса между пропускной способностью и управляемостью
- Callback API v2 для всех новых клиентов
- QoS 0 для массовой телеметрии, QoS 1 для команд, QoS 2 только для safety-critical операций
