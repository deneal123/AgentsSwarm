# Communication Service — Обзор

## Назначение

Сервис коммуникации отвечает за надёжную и масштабируемую передачу сообщений между облаком и роботами, а также внутри системы между микросервисами. Архитектура построена на двух специализированных протоколах: MQTT для взаимодействия с IoT-устройствами (роботами) и AMQP (RabbitMQ) для внутренних микросервисных коммуникаций. Каждый протокол выбран исходя из своих сильных сторон для конкретного сценария.

---

## Компоненты

- **MQTT Broker (EMQX)** — взаимодействие с роботами по протоколу MQTT v3.1.1/v5.0. Pub/Sub модель с иерархическими топиками и уровнями QoS
- **RabbitMQ** — внутренние очереди на базе AMQP 0-9-1 с маршрутизацией через exchange'ы (direct, fanout, topic), задачи Celery, RPC-паттерн
- **Router/Bridge** — мосты между MQTT и RabbitMQ для маршрутизации сообщений между роботами и внутренними сервисами
- **Topic Manager** — шаблоны топиков MQTT и routing key RabbitMQ, политика доступа
- **Monitoring & ACL** — мониторинг, аудит и контроль доступа

## Сравнение протоколов

| Характеристика | MQTT (EMQX) | AMQP / RabbitMQ |
|----------------|-------------|-----------------|
| **Назначение в системе** | Робот ↔ Облако | Микросервис ↔ Микросервис |
| **Модель** | Publish/Subscribe с иерархическими топиками | Producer → Exchange → Queue → Consumer |
| **Маршрутизация** | Иерархия топиков с wildcard-подписками (`+`, `#`) | Exchange'ы: direct, fanout, topic, headers |
| **QoS** | 3 уровня (0, 1, 2) на уровне протокола | Acknowledgments + durable queues + persistent messages |
| **Типичный payload** | Компактные сообщения (JSON, Protobuf): телеметрия, команды, ack | Любой формат: задачи Celery, события, RPC-запросы |
| **Оффлайн-доставка** | Retained messages + persistent sessions | Durable queues + persistent messages |
| **Обнаружение отключений** | LWT (Last Will and Testament) | Consumer heartbeat + TCP keepalive |
| **Паттерн RPC** | Не нативный (возможен через пару топиков) | Нативная поддержка через reply_to + correlation_id |
| **Масштабирование** | Кластер EMQX, шардинг подключений | Кластер RabbitMQ, зеркалированные очереди |
| **Python-клиент** | paho-mqtt (Paho MQTT Client) | pika (AMQP 0-9-1) |

## Требования

- Низкая латентность для критических сообщений (команды роботам, экстренные события)
- Гарантированная доставка для команд (MQTT QoS 1/2, RabbitMQ manual ack + durable)
- Масштабируемость и мульти-тенантность
- Механизмы LWT, Retained messages и Offline queues для обнаружения и обработки отключений роботов
- Справедливое распределение нагрузки (RabbitMQ prefetch_count для Work Queues)
- Поддержка RPC-паттерна для синхронных запросов между сервисами

## Потоки данных

### Робот → Облако (Uplink)

1. Робот публикует сообщение в MQTT-топик (телеметрия, событие, ack на команду)
2. EMQX маршрутизирует сообщение подписчикам:
   - Прямые подписчики (мониторинг Dashboard, Data Aggregation Service)
   - Router/Bridge: MQTT → RabbitMQ для внутренней обработки
3. RabbitMQ exchange маршрутизирует сообщение в соответствующие очереди
4. Celery workers и микросервисы потребляют из очередей

### Облако → Робот (Downlink)

1. Orchestrator формирует команду для робота
2. Команда публикуется через MQTT-клиент (Paho) в соответствующий топик робота
3. EMQX доставляет сообщение роботу с заданным QoS
4. Робот подтверждает получение (MQTT ack для QoS 1/2 + application-level ack в отдельном топике)

### Микросервис ↔ Микросервис

1. Producer отправляет сообщение в RabbitMQ exchange с routing_key
2. Exchange маршрутизирует в bound queues по типу exchange'а и binding keys
3. Consumer потребляет из очереди, обрабатывает, отправляет acknowledgment
4. При ошибке: сообщение возвращается в очередь (nack/reject) или перенаправляется в Dead Letter Queue
