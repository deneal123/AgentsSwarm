# RabbitMQ — Внутренние очереди и Celery

## Роль

RabbitMQ обеспечивает асинхронную коммуникацию между микросервисами, очереди задач Celery, обработку событий и надёжную доставку сообщений внутри платформы. Работает по протоколу AMQP 0-9-1 с Python-клиентом Pika. Ключевой принцип: сообщения **никогда** не отправляются напрямую в очередь — они всегда проходят через exchange, который маршрутизирует их по правилам.

---

## Базовая модель AMQP 0-9-1

Модель передачи сообщений в RabbitMQ строится на четырёх основных сущностях:

1. **Producer** — отправляет сообщение в exchange с указанием routing_key
2. **Exchange** — маршрутизирует сообщение в одну или несколько очередей на основе типа exchange, binding keys и routing_key сообщения
3. **Queue** — буфер для хранения сообщений до их потребления
4. **Consumer** — получает и обрабатывает сообщения из очереди

Связь между exchange и queue называется **binding** — это правило, по которому exchange решает, в какую очередь направить сообщение. Binding может иметь дополнительный параметр — **binding_key**, который используется для фильтрации (в зависимости от типа exchange).

---

## Типы Exchange

### Default Exchange (безымянный, "")

Безымянный exchange, предоставляемый брокером по умолчанию. Каждая создаваемая очередь автоматически привязывается к нему с binding_key, равным имени очереди. Сообщение с routing_key = "task_queue" доставляется в очередь с именем "task_queue".

Применение в AgentsSwarm: простейшие point-to-point коммуникации, прямая отправка задач в конкретную очередь.

### Fanout Exchange

Broadcast-маршрутизация: exchange отправляет копию сообщения во **все** привязанные (bound) очереди, полностью игнорируя routing_key. Каждый подписчик получает свою копию.

Применение в AgentsSwarm:

- Системные уведомления (maintenance window, конфигурационные изменения)
- Событие "новый робот подключён" — все заинтересованные сервисы получают уведомление
- Глобальные broadcast-события от Orchestrator
- Логирование: каждый сервис-аудитор получает копию всех событий

### Direct Exchange

Маршрутизация по точному совпадению: сообщение доставляется в очередь, если routing_key сообщения **точно совпадает** с binding_key привязки очереди к exchange. Одна очередь может иметь несколько binding_key, а несколько очередей могут быть привязаны с одинаковым binding_key — в этом случае сообщение доставляется во все совпавшие очереди (поведение fanout для этого ключа).

Применение в AgentsSwarm:

- Маршрутизация команд по severity (info, warning, error, critical) — каждый обработчик подписывается на нужные уровни
- Направление задач конкретному сервису по его имени
- Раздельная обработка телеметрии и событий

### Topic Exchange

Паттерн-маршрутизация: routing_key представляет собой строку из слов, разделённых точками (например, `robot.telemetry.pose`). Binding_key может содержать wildcard-символы:

- **`*`** (звёздочка) — заменяет ровно **одно** слово
- **`#`** (решётка) — заменяет **ноль или более** слов

Максимальная длина routing_key — 255 байт.

Особые случаи:

- Если binding_key состоит только из `#` — exchange ведёт себя как fanout (получает все сообщения)
- Если binding_key не содержит wildcards — exchange ведёт себя как direct (точное совпадение)

Применение в AgentsSwarm (основной тип exchange для внутренней маршрутизации):

- `robot.*.telemetry.#` — вся телеметрия всех роботов
- `robot.robot_001.cmd.*` — все команды конкретного робота
- `inference.triton.result.*` — результаты инференса от Triton
- `orchestrator.task.*.completed` — уведомления о завершении задач
- `alert.#` — все алерты системы

### Headers Exchange

Маршрутизация по заголовкам (headers) сообщения вместо routing_key. Binding задаёт набор пар ключ-значение и критерий совпадения (all — все заголовки должны совпасть, any — достаточно одного). Используется редко — для сложных сценариев фильтрации, где иерархия routing_key недостаточна.

Применение в AgentsSwarm: фильтрация по комбинации метаданных (тип робота + модель ИИ + приоритет задачи).

## Work Queues (Очереди задач)

Work Queues (Task Queues) — паттерн распределения ресурсоёмких задач между несколькими воркерами. Множество consumers подключаются к одной очереди, и RabbitMQ распределяет сообщения между ними.

### Round-Robin Dispatch

По умолчанию RabbitMQ распределяет сообщения round-robin: каждое N-е сообщение отправляется N-му consumer'у. Распределение происходит в момент отправки сообщения, а не в момент подтверждения — это означает, что один consumer может накопить много неподтверждённых сообщений, пока другой простаивает.

### Fair Dispatch (prefetch_count)

Для справедливого распределения нагрузки используется параметр **prefetch_count** через настройку basic_qos. Значение prefetch_count=1 означает: не отправлять следующее сообщение consumer'у, пока он не подтвердил обработку предыдущего. RabbitMQ будет направлять новые сообщения свободным consumer'ам.

Рекомендации:

- **prefetch_count=1** — для задач с неравномерной длительностью (инференс, обработка изображений). Максимальная справедливость, но ниже пропускная способность
- **prefetch_count=10–50** — для однотипных коротких задач. Выше пропускная способность за счёт batch-доставки
- **prefetch_count=1** для RPC-серверов — обеспечивает масштабирование добавлением новых инстансов

## Acknowledgments (Подтверждения)

### Manual Acknowledgment (рекомендуемый)

Consumer явно подтверждает обработку каждого сообщения отправкой basic_ack с delivery_tag. До получения ack сообщение остаётся в статусе "unacked". Если consumer отключается (crash, потеря TCP, закрытие канала) до отправки ack, сообщение автоматически ставится обратно в очередь и доставляется другому consumer'у.

Таймаут подтверждения: если ack не получен в течение **30 минут**, RabbitMQ считает consumer зависшим и переставляет сообщение в очередь.

Варианты ответа consumer'а:

- **basic_ack** — сообщение успешно обработано, удалить из очереди
- **basic_nack** — ошибка обработки; с параметром requeue=True сообщение возвращается в очередь, requeue=False — отправляется в Dead Letter Queue (если настроен) или отбрасывается
- **basic_reject** — аналогично nack, но для одного сообщения

### Auto Acknowledgment

Сообщение считается обработанным сразу после доставки consumer'у (auto_ack=True). Если consumer упадёт во время обработки — сообщение потеряно. Используется только для некритичных сценариев с высокой пропускной способностью.

В AgentsSwarm **по умолчанию используется manual ack** для всех очередей.

## Durability — Гарантии сохранности

Для предотвращения потери сообщений при перезапуске RabbitMQ необходимо обеспечить durability на двух уровнях:

### Durable Queue

Очередь объявляется с параметром `durable=True`. При перезапуске RabbitMQ очередь восстанавливается (но не её содержимое, если сообщения не persistent).

### Persistent Messages

Сообщение отправляется с параметром `delivery_mode=Persistent` (delivery_mode=2). Такие сообщения записываются на диск. Однако есть окно уязвимости: между принятием сообщения и записью на диск (fsync) может пройти время — при crash в этот момент сообщение будет потеряно.

### Publisher Confirms

Для строгой гарантии доставки используются **Publisher Confirms**: брокер подтверждает издателю, что сообщение было записано на диск и/или реплицировано. Рекомендуется для критичных сообщений (команды роботам, финансовые события).

В AgentsSwarm все критичные очереди объявляются как durable, все сообщения — persistent, критичные продюсеры используют publisher confirms.

## Publish/Subscribe (Fanout)

Паттерн для рассылки одного сообщения множеству получателей:

1. Producer публикует сообщение в fanout exchange
2. Exchange копирует сообщение во все привязанные очереди
3. Каждый consumer получает свою копию

### Temporary Queues (Exclusive Queues)

Для pub/sub часто используются **временные очереди**: очередь создаётся с пустым именем (сервер генерирует уникальное имя), параметром `exclusive=True`. Такая очередь:

- Автоматически удаляется при отключении consumer'а
- Доступна только создавшему её соединению
- Идеальна для «подписчиков-слушателей», которым не нужно хранить историю

Применение: Dashboard-подписки на live-события, временные мониторинг-сессии, отладочные подключения.

## RPC-паттерн (Remote Procedure Call)

RabbitMQ поддерживает паттерн синхронного запрос-ответ поверх асинхронных очередей.

### Механизм

1. **Клиент** создаёт exclusive callback-очередь (временная, с уникальным именем)
2. **Клиент** отправляет сообщение-запрос в очередь сервера с двумя специальными свойствами:
   - **reply_to** — имя callback-очереди, куда сервер должен отправить ответ
   - **correlation_id** — уникальный идентификатор запроса (UUID) для соотнесения запросов и ответов
3. **Сервер** получает запрос, обрабатывает его и отправляет ответ в очередь, указанную в reply_to, сохраняя correlation_id
4. **Клиент** получает ответ из callback-очереди и сопоставляет его с исходным запросом по correlation_id

### Масштабирование RPC

Добавление новых инстансов RPC-сервера тривиально: все серверы подключаются к одной очереди запросов. С настройкой prefetch_count=1 нагрузка равномерно распределяется между серверами. Клиенту не нужно знать о количестве серверов.

### Применение в AgentsSwarm

- Gateway → Orchestrator: синхронные запросы на статус задачи
- Orchestrator → TritonInference: запрос инференса с ожиданием результата
- Dashboard → любой сервис: интерактивные запросы пользователя

### Рекомендации

- При сомнении — предпочитать асинхронные пайплайны вместо RPC (меньше coupling, лучше масштабируемость)
- Обязательно устанавливать timeout на ожидание ответа
- Не создавать отдельную callback-очередь на каждый запрос — одна exclusive очередь на клиент, фильтрация по correlation_id

## Свойства сообщений

Протокол AMQP 0-9-1 определяет набор стандартных свойств сообщения:

| Свойство | Описание | Применение в AgentsSwarm |
|----------|----------|--------------------------|
| **delivery_mode** | Persistent (2) или Transient (1) | Persistent для всех критичных сообщений |
| **content_type** | MIME-тип содержимого | `application/json` для большинства сообщений |
| **reply_to** | Имя callback-очереди для ответа | RPC-паттерн |
| **correlation_id** | Уникальный ID для сопоставления запрос-ответ | RPC-паттерн, trace correlation |
| **headers** | Произвольные заголовки | Маршрутизация headers exchange, метаданные |
| **expiration** | TTL сообщения в миллисекундах | Автоудаление устаревших команд |
| **priority** | Приоритет сообщения (0–9) | Приоритизация critical-команд |
| **message_id** | Уникальный идентификатор сообщения | Дедупликация, аудит |
| **timestamp** | Время создания сообщения | Мониторинг задержек |

## Dead Letter Exchange (DLX) и Dead Letter Queue (DLQ)

Сообщения, которые не удалось обработать, перенаправляются в Dead Letter Exchange при следующих условиях:

- Consumer отклонил сообщение (basic_nack / basic_reject с requeue=False)
- Истёк TTL сообщения
- Очередь переполнена (достигнут max-length)

Конфигурация DLX задаётся при объявлении очереди через аргументы:

- **x-dead-letter-exchange** — имя exchange для dead letter сообщений
- **x-dead-letter-routing-key** — routing_key для dead letter (опционально)

Dead Letter Queue подключается к DLX и позволяет:

- Анализировать причины ошибок обработки
- Повторно обрабатывать (retry) после исправления бага
- Мониторинг: алерт при росте DLQ выше порога
- Архивация необработанных сообщений

## High Availability

- **Quorum Queues** (рекомендуемый): реплицированные очереди на базе Raft-консенсуса. Данные реплицируются на N/2+1 нод. Автоматическое переключение leader'а при падении ноды
- **Classic Mirrored Queues** (legacy): зеркалирование очередей на указанные ноды кластера. Менее надёжны, чем quorum queues
- **Streams**: журнально-ориентированные очереди для сценариев с многократным потреблением (fan-out + replay). Подходят для event sourcing

В AgentsSwarm критичные очереди (команды роботам, задачи инференса, DLQ) используют Quorum Queues.

## Интеграция с Celery

Celery использует RabbitMQ в качестве message broker для фонового выполнения задач:

- **Task Queues**: каждый тип задачи маршрутизируется в отдельную очередь (inference_tasks, data_processing, notifications)
- **Retry Policy**: настраиваемые retry с экспоненциальным backoff (max_retries, retry_backoff, retry_backoff_max)
- **Visibility Timeout**: максимальное время выполнения задачи, после которого она возвращается в очередь
- **Rate Limits**: ограничение скорости выполнения задач по типу (например, не более 10 запросов инференса в секунду)
- **Priority Queues**: поддержка приоритетов задач через priority routing
- **Task Routing**: маршрутизация задач на конкретные воркеры через exchange и routing_key

Celery workers подключаются с prefetch_count, соответствующим concurrency настройке (для prefork — prefetch_count = concurrency × prefetch_multiplier).

## Мониторинг и алерты

- **Queue depth** — количество сообщений в очереди: алерт при превышении порога
- **Rate of consumption** — скорость обработки: алерт при снижении ниже нормы
- **Unacked messages** — количество неподтверждённых сообщений: алерт при росте (зависшие consumers)
- **DLQ depth** — количество сообщений в Dead Letter Queue: алерт при любом росте
- **Connection count** — количество активных подключений: алерт при аномалиях
- **Message latency** — задержка от публикации до потребления (через timestamp в свойствах)
- **Channel/connection churn** — частота создания/закрытия соединений: индикатор нестабильности

Мониторинг реализуется через RabbitMQ Management Plugin (HTTP API + Web UI), Prometheus exporter (rabbitmq_prometheus) и интеграцию с Grafana-дашбордами платформы.
