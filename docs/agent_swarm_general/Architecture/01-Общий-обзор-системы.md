# Общий обзор системы

## Назначение платформы

**AgentsSwarm** — это платформа для централизованного управления роем автономных роботов, объединяющая технологии робототехники, машинного обучения и распределённых систем. Платформа позволяет оператору управлять десятками и сотнями роботов через единый интерфейс, используя команды на естественном языке, а также обеспечивает автономную координацию роботов на основе AI-планирования.

---

## Ключевые цели системы

### Управление на естественном языке
Оператор взаимодействует с системой через чат-интерфейс, отдавая команды вида: *«Робот 1, подойди к синему ящику и проверь его состояние»* или *«Роботы, найдите и принесите все красные коробки в зону А»*. Система интерпретирует намерение, декомпозирует его на задачи, назначает подходящих роботов и контролирует выполнение.

### Реальное время
Все критичные потоки данных работают с задержкой менее 50 миллисекунд. Телеметрия роботов, команды управления и экстренные события обрабатываются в реальном времени. Фронтенд отображает текущее состояние роя с минимальной задержкой.

### Автономность на краю
Каждый робот оснащён бортовым компьютером с локальными AI-моделями. При потере связи с облаком робот продолжает выполнять текущую задачу, реагировать на препятствия и обеспечивать безопасность. При восстановлении связи происходит синхронизация состояния.

### AI-планирование и координация
Система использует многоуровневый подход к планированию:
- **Стратегический уровень** — LLM анализирует команду пользователя и формирует общий план
- **Тактический уровень** — Orchestrator распределяет задачи между роботами с учётом их возможностей и текущего состояния
- **Операционный уровень** — локальные планировщики на роботах обеспечивают навигацию и избегание препятствий

### Масштабируемость
Архитектура рассчитана на управление от единиц до тысяч роботов. Каждый микросервис масштабируется независимо, а коммуникационный слой обеспечивает пропускную способность для миллионов сообщений.

## Высокоуровневая архитектура

Система состоит из шести функциональных уровней:

### Уровень 1 — Пользовательский интерфейс (Frontend)
Веб-приложение, предоставляющее оператору визуальные инструменты: дашборд с состоянием роя, чат для голосового/текстового управления, 3D-визуализацию среды и роботов, панель администрирования. Взаимодействует с системой через REST API и WebSocket.

### Уровень 2 — API-шлюз (GatewayService)
Единая точка входа для всех внешних запросов. Принимает REST-запросы и WebSocket-соединения от фронтенда, выполняет аутентификацию и авторизацию, проксирует запросы к внутренним микросервисам. Обеспечивает изоляцию внутренней архитектуры от клиентов.

### Уровень 3 — AI-оркестрация и планирование (Orchestrator)
Центральный «мозг» системы. Интерпретирует команды пользователя через LLM, декомпозирует задачи, назначает роботов, генерирует планы выполнения и контролирует их реализацию. Использует граф состояний (LangGraph) для управления сложными многошаговыми процессами и Open-Agent SDK для организации мультиагентных взаимодействий.

### Уровень 4 — AI-инференс (TritonInference, vLLMService, SmolVLA)
Набор GPU-ускоренных сервисов для выполнения ресурсоёмких AI-задач:
- **Triton Inference Server** — компьютерное зрение (детекция, трекинг, сегментация)
- **vLLM Server** — языковые и мультимодальные модели (понимание текста, генерация планов, визуальный анализ)
- **SmolVLA Server** — Vision-Language-Action модели для генерации низкоуровневых действий робота на основе визуального контекста и текстовых инструкций

### Уровень 5 — Коммуникационный слой (CommunicationService)
Обеспечивает надёжную передачу данных между всеми компонентами:
- **MQTT (EMQX)** — основной протокол для связи с роботами, оптимизированный для нестабильных сетей и IoT-устройств
- **RabbitMQ** — внутренний брокер для асинхронного обмена сообщениями между микросервисами
- **gRPC** — синхронные высокопроизводительные вызовы между сервисами

### Уровень 6 — Краевой слой (RobotEdge)
Программное обеспечение, работающее непосредственно на бортовых компьютерах роботов. Включает:
- **Edge AI Proxy** — управление локальными моделями, выбор между локальным и облачным инференсом
- **ROS2 Bridge** — трансляция между внутренними ROS2-топиками робота и внешними протоколами (MQTT, gRPC)
- **SmolVLA Edge** — компактная версия VLA-модели для мгновенного реагирования
- **Локальный кэш** — хранение последних команд и состояний при потере связи

### Хранение данных (DataStorage)
Многоуровневое хранилище, оптимизированное под различные типы данных:
- **InfluxDB** — временные ряды телеметрии
- **Neo4j** — графовые связи между роботами, объектами и локациями
- **Redis** — кэш текущих состояний, Feature Store с векторным поиском
- **MinIO** — объектное хранилище для моделей, изображений и логов
- **PostgreSQL** — реляционные данные (пользователи, задачи, реестр роботов)

### Мониторинг
Инфраструктура наблюдаемости (observability):
- **Prometheus** — сбор метрик со всех компонентов
- **Grafana** — визуализация метрик и создание дашбордов
- **Jaeger** — распределённая трассировка запросов
- **Elasticsearch + Kibana** — централизованные логи

## Принципы проектирования

### Микросервисная архитектура
Каждый компонент системы представляет собой независимый микросервис с собственным жизненным циклом, хранилищем данных и API. Это обеспечивает независимую разработку, тестирование и масштабирование каждого компонента.

### Event-Driven подход
Взаимодействие между компонентами построено преимущественно на событиях. Телеметрия, команды и статусы публикуются в брокеры сообщений, а заинтересованные сервисы подписываются на нужные потоки. Это обеспечивает слабую связанность и позволяет добавлять новые потребители данных без модификации существующих сервисов.

### Edge-Cloud гибридность
Система работает в двух контурах: облачные вычисления для сложного анализа и планирования, краевые вычисления на роботах для быстрого реагирования. Распределение нагрузки между контурами адаптивно и зависит от доступности сети, сложности задачи и требований к задержке.

### Graceful Degradation
При отказе любого компонента система продолжает работать с пониженной функциональностью. Роботы автономны при потере облака. AI-сервисы имеют fallback-стратегии. Данные буферизуются при недоступности хранилищ.

### Наблюдаемость
Каждый запрос получает уникальный идентификатор трассировки (trace_id), который проходит через все микросервисы. Метрики, логи и трейсы собираются централизованно, обеспечивая полную прозрачность работы системы.

## Целевые сценарии использования

1. **Складская логистика** — координация роботов для перемещения грузов, инвентаризации, поиска объектов
2. **Промышленная инспекция** — автономный обход территории, обнаружение аномалий, отчётность
3. **Спасательные операции** — координация группы роботов для поиска и обнаружения в сложных условиях
4. **Исследовательские задачи** — совместная картография, сбор данных, научные исследования
5. **Сельское хозяйство** — координация дронов и наземных роботов для мониторинга и обработки угодий

## Ограничения текущей версии

- Поддерживается только управление через веб-интерфейс (мобильное приложение планируется)
- Голосовое управление (ASR) не входит в MVP, но архитектурно предусмотрено
- Максимальное количество одновременно управляемых роботов ограничено пропускной способностью MQTT-кластера и GPU-ресурсами AI-сервисов
- Система проектируется для работы в локальной сети с выходом в облако, полностью облачный режим требует дополнительной настройки сетевой инфраструктуры
