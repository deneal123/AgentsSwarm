# Протоколы коммуникации

## Обзор протоколов

Система использует несколько протоколов, каждый из которых оптимизирован для конкретного типа взаимодействия.

| Протокол | Назначение | Направление | Задержка | Особенности |
|----------|-----------|-------------|----------|-------------|
| MQTT | Связь с роботами | Cloud ↔ Edge | 10–50 мс | Лёгкий, QoS, Pub/Sub, LWT |
| gRPC | Сервис ↔ сервис | Cloud внутри | 1–10 мс | Типизация, streaming, высокая скорость |
| HTTP/REST | Фронтенд → шлюз | Клиент → Cloud | 50–200 мс | Универсальность, простота |
| WebSocket | Шлюз → фронтенд | Cloud → Клиент | 10–50 мс | Двусторонняя, real-time |
| AMQP | Внутренний обмен | Cloud внутри | 1–5 мс | Гарантированная доставка, очереди |
| ROS2 DDS | Внутри робота | Edge внутри | < 1 мс | Стандарт робототехники |

## MQTT (Message Queuing Telemetry Transport)

### Назначение
Основной протокол для коммуникации между облаком и роботами. Выбран как замена Kafka для данного сценария.

### Обоснование выбора

**Преимущества перед Kafka в данном контексте:**
- **Низкая задержка** — 10–50 мс против 100+ мс у Kafka, что критично для real-time управления роботами
- **Оптимизация для нестабильных сетей** — встроенный автореконнект, persistent sessions, QoS-уровни
- **Низкое потребление ресурсов** — минимальный оверхед на стороне робота (Edge), важно для ограниченных бортовых компьютеров
- **Last Will and Testament (LWT)** — автоматическое обнаружение отключения робота без дополнительной логики heartbeat
- **Создан для IoT** — протокол изначально проектировался для устройств с ограниченными ресурсами в нестабильных сетях

### Уровни качества обслуживания (QoS)

**QoS 0 — At Most Once**
- Применяется для: регулярная телеметрия (позиция, скорость, сенсоры)
- Логика: потеря нескольких точек телеметрии не критична, новые данные придут через миллисекунды
- Максимальная пропускная способность и минимальная задержка

**QoS 1 — At Least Once**
- Применяется для: команды управления, статусы задач, подтверждения
- Логика: команда должна быть гарантированно доставлена. Допускается дублирование (идемпотентная обработка на стороне получателя)
- Подтверждение доставки от брокера

**QoS 2 — Exactly Once**
- Применяется для: экстренные команды (emergency stop), обновления конфигурации, критические события
- Логика: команда должна быть выполнена ровно один раз, дублирование недопустимо
- Четырёхэтапный handshake (PUBLISH, PUBREC, PUBREL, PUBCOMP)

### Retain-сообщения
Используются для публикации текущего статуса робота. Новый подписчик (например, перезапущенный сервис) сразу получает последнее известное состояние робота без ожидания следующего цикла публикации.

### Last Will and Testament (LWT)
Каждый робот при подключении к брокеру регистрирует LWT-сообщение:
- Топик: `status/{robot_id}/connection`
- Payload: `{"status": "offline", "timestamp": "..."}`
- QoS: 1, Retain: true

При нештатном отключении робота брокер автоматически публикует это сообщение, и все подписчики мгновенно узнают об отключении.

### Брокер: EMQX
Выбран EMQX как MQTT-брокер:
- Поддержка кластеризации для высокой доступности
- Горизонтальное масштабирование на миллионы одновременных подключений
- Встроенная поддержка MQTT over WebSocket (порт 8083) для прямого подключения фронтенда
- Rule Engine для маршрутизации сообщений в базы данных
- Встроенный дашборд мониторинга (порт 18083)
- Поддержка аутентификации через JWT и клиентские сертификаты

## gRPC (Google Remote Procedure Call)

### Назначение
Синхронные высокопроизводительные вызовы между микросервисами внутри облака. Используется для взаимодействия Orchestrator с AI-сервисами.

### Обоснование выбора
- **Бинарная сериализация** (Protobuf) — в 3–10 раз эффективнее JSON по объёму и скорости парсинга
- **Строгая типизация** — Protobuf-контракты гарантируют совместимость между сервисами
- **Bidirectional Streaming** — позволяет передавать потоковые данные (например, стриминг телеметрии от vLLM, потоковая генерация ответов LLM)
- **HTTP/2** — мультиплексирование, сжатие заголовков, серверный push
- **Кодогенерация** — автоматическая генерация клиентского и серверного кода из .proto файлов

### Режимы вызовов

**Unary (запрос-ответ)**
- Orchestrator → TritonInference: отправка изображения, получение детекций
- Orchestrator → vLLMService: отправка промпта, получение ответа (для коротких ответов)

**Server Streaming**
- Orchestrator → vLLMService: потоковая генерация текста (токен за токеном) для интерактивного чата
- Orchestrator → TritonInference: потоковые результаты трекинга

**Client Streaming**
- RobotEdge → TritonInference: потоковая отправка кадров с камеры для обработки

**Bidirectional Streaming**
- Orchestrator ↔ SmolVLA Cloud: двунаправленный поток для итеративного планирования действий

### Политики повторов и таймауты
- Каждый gRPC-вызов имеет deadline (таймаут): 2 секунды для детекции, 10 секунд для генерации плана
- Retry с экспоненциальным backoff (100 мс → 200 мс → 400 мс, максимум 3 попытки)
- Circuit Breaker: если сервис недоступен более 30 секунд, запросы к нему прекращаются на 60 секунд (half-open state)

## HTTP/REST

### Назначение
Взаимодействие фронтенда с API-шлюзом для статических запросов (получение списков, конфигурации, исторических данных).

### Обоснование выбора
- Универсальность и простота интеграции с любым клиентом
- Широкая поддержка инструментов (Swagger/OpenAPI, Postman, curl)
- Кэширование через HTTP-заголовки (ETag, Cache-Control)
- Подходит для идемпотентных запросов, не требующих real-time

### Применение
- `GET /api/v1/robots` — получение списка роботов
- `GET /api/v1/robots/{id}/telemetry?from=...&to=...` — историческая телеметрия
- `POST /api/v1/tasks` — создание задачи (альтернатива чату)
- `GET /api/v1/tasks/{id}` — статус задачи

## WebSocket

### Назначение
Двунаправленная связь между GatewayService и фронтендом для real-time обновлений.

### Обоснование выбора
- Двусторонняя связь без polling
- Минимальный оверхед после установки соединения
- Нативная поддержка в браузерах
- Возможность передачи как текстовых (JSON), так и бинарных данных

### Каналы WebSocket

**Чат:** `/ws/chat/{user_id}`
- Двунаправленный: пользователь отправляет текстовые команды, получает ответы от LLM и обновления статуса
- Формат сообщений: JSON с полями `type`, `payload`, `message_id`

**Телеметрия робота:** `/ws/robots/{robot_id}/telemetry`
- Однонаправленный (сервер → клиент): потоковая передача текущего состояния робота
- Формат: JSON с полями `position`, `battery`, `status`, `detections`

**Визуализация роя:** `/ws/swarm/visualization`
- Однонаправленный (сервер → клиент): агрегированные данные о всём рое для 3D-визуализации
- Частота: 10 Гц (100 мс)
- Формат: бинарный (для эффективности) или JSON

### Механизм heartbeat
- Клиент отправляет ping каждые 30 секунд
- Сервер отвечает pong
- Если pong не получен за 60 секунд — соединение закрывается, клиент переподключается

## AMQP (RabbitMQ)

### Назначение
Внутренний асинхронный обмен сообщениями между микросервисами облака.

### Обоснование выбора
- Гарантированная доставка с подтверждениями (ack)
- Гибкая маршрутизация: direct, topic, fanout exchange
- Dead-letter очереди для обработки ошибок
- Готовая интеграция с Celery для управления задачами Orchestrator

### Очереди и exchanges

**Exchange: `user_commands` (direct)**
- Очередь: `commands.user` → Orchestrator
- Содержимое: команды пользователя из Gateway

**Exchange: `robot_events` (topic)**
- Очередь: `events.telemetry.*` → DataStorage
- Очередь: `events.emergency.*` → Orchestrator (с приоритетом)
- Очередь: `events.task.*` → Orchestrator

**Exchange: `system_notifications` (fanout)**
- Все подписчики: уведомления о событиях системы (перезапуск сервиса, обновление конфигурации)

### Celery интеграция
Orchestrator использует Celery поверх RabbitMQ для:
- Распределённого выполнения задач (TaskManager)
- Планирования периодических задач (health checks, аналитика)
- Управления цепочками задач (chains, groups, chords)
- Хранения результатов в Redis

## ROS2 DDS (Data Distribution Service)

### Назначение
Внутренняя коммуникация компонентов на роботе (сенсоры, актуаторы, планировщики).

### Характеристики
- Задержка менее 1 мс для локальных коммуникаций
- Pub/Sub модель с типизированными сообщениями
- QoS-профили (Reliable, Best Effort, Transient Local)
- Стандарт де-факто для робототехники

### Примеры топиков
- `/odom` — одометрия (позиция и ориентация)
- `/scan` — данные LiDAR
- `/camera/image_raw` — сырое изображение камеры
- `/cmd_vel` — команды движения (линейная и угловая скорость)
- `/battery_state` — состояние батареи
