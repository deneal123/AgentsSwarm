# Масштабирование и отказоустойчивость

## Стратегия масштабирования

Система проектируется для поддержки от единиц до тысяч роботов. Каждый компонент масштабируется независимо в зависимости от нагрузки.

---

## Горизонтальное масштабирование компонентов

### GatewayService
- **Тип:** Stateless (сессии хранятся в Redis)
- **Масштабирование:** Автоматическое через Kubernetes HPA (Horizontal Pod Autoscaler)
- **Метрика:** CPU utilization > 70% или количество WebSocket-соединений > 1000 на pod
- **Количество реплик:** 2–10 (в зависимости от числа операторов)
- **Балансировка:** Kubernetes Service с Session Affinity (для WebSocket) или Sticky Sessions через Ingress

### Orchestrator
- **Тип:** Условно stateless (состояние в Redis и PostgreSQL)
- **Масштабирование:** Горизонтальное через Celery workers
- **Организация:** Leader-follower для координационных задач (leader election через Redis); множество worker'ов для параллельного выполнения задач
- **Метрика:** Длина очереди задач в RabbitMQ, время обработки
- **Шардирование:** По группам роботов — каждый worker обрабатывает подмножество роботов

### Triton Inference Server
- **Тип:** Stateless (модели загружаются из хранилища)
- **Масштабирование:** Добавление GPU-узлов
- **Метрика:** GPU utilization > 80%, queue latency > 100 мс
- **Особенности:** Каждый инстанс требует выделенного GPU. Автоматическое батчирование запросов внутри Triton уменьшает потребность в дополнительных инстансах
- **Количество реплик:** 1–4 (зависит от количества видеопотоков)

### vLLM Server
- **Тип:** Stateless (KV-кэш в GPU-памяти, не persisted)
- **Масштабирование:** Добавление GPU-узлов; tensor parallelism для больших моделей
- **Метрика:** Tokens per second, queue depth
- **Количество реплик:** 1–2 (LLM-запросы менее частые, чем детекция)

### SmolVLA Cloud
- **Тип:** Stateless
- **Масштабирование:** Добавление GPU-узлов
- **Метрика:** Inference latency, queue depth
- **Количество реплик:** 1–2

### MQTT Broker (EMQX)
- **Тип:** Stateful (кластер с репликацией)
- **Масштабирование:** Добавление узлов в кластер EMQX
- **Ёмкость:** Один узел EMQX обрабатывает до 1 миллиона одновременных подключений
- **Количество узлов:** 2–3 для высокой доступности

### RabbitMQ
- **Тип:** Stateful (кластер с quorum queues)
- **Масштабирование:** Кластер из нечётного количества узлов (3, 5)
- **Особенности:** Quorum queues обеспечивают консенсус и устойчивость к потере узлов

### Redis
- **Тип:** Stateful
- **Масштабирование:** Redis Cluster (шардирование) + Sentinel (высокая доступность)
- **Шардирование:** Автоматическое по ключам через consistent hashing
- **Репликация:** Master-replica с автоматическим failover

### PostgreSQL
- **Тип:** Stateful
- **Масштабирование:** Streaming replication с read-replicas для чтения
- **Запись:** Один master
- **Чтение:** 1–3 read-replicas для аналитических запросов

### InfluxDB
- **Тип:** Stateful
- **Масштабирование:** InfluxDB Clustered (или InfluxDB IOx) для горизонтального масштабирования
- **Retention Policies:** Автоматическое прореживание старых данных

### Neo4j
- **Тип:** Stateful
- **Масштабирование:** Causal Cluster (core + read replicas)
- **Особенности:** Core-серверы обеспечивают консенсус, read-replicas — масштабирование чтения

## Отказоустойчивость

### Принцип Graceful Degradation

При отказе любого компонента система продолжает работать с пониженной функциональностью:

| Отказавший компонент | Последствия | Mitigation |
|---------------------|-------------|------------|
| vLLMService | Невозможно интерпретировать текстовые команды | Fallback на предопределённые шаблоны команд; ручное управление |
| TritonInference | Нет облачной детекции объектов | Edge SmolVLA/Tiny YOLO продолжают работать локально |
| SmolVLA Cloud | Нет сложного VLA-планирования | Edge SmolVLA продолжает базовые действия |
| Orchestrator | Нет централизованного планирования | Роботы продолжают текущие задачи автономно |
| MQTT Broker | Нет связи с роботами | Роботы переходят в автономный режим; локальный буфер |
| RabbitMQ | Нет внутренней коммуникации | Retry с backoff; сервисы буферизуют сообщения |
| Redis | Потеря кэша состояний | Восстановление из БД; пересчёт состояний |
| PostgreSQL | Потеря доступа к метаданным | Read-replicas для чтения; write-буферизация |
| InfluxDB | Потеря записи телеметрии | Буферизация в Redis; запись позже |
| GatewayService | Нет доступа для пользователя | Kubernetes автоматически перезапускает; другие реплики принимают трафик |

### Автономность роботов (Edge Resilience)

Критически важная особенность системы — роботы остаются работоспособными при полной потере связи с облаком:

**Время автономной работы:** не менее 30 минут активного выполнения задач

**Что доступно офлайн:**
- Локальная детекция объектов (Tiny YOLO)
- Локальное VLA-планирование (SmolVLA Edge)
- Навигация и избегание препятствий (LocalPlanner)
- Построение карты (LocalMapper)
- Экстренная остановка
- Кэш последних N команд

**Что недоступно офлайн:**
- Интерпретация текстовых команд (требует vLLM)
- Глобальная координация между роботами
- Сложный анализ сцены (требует Triton Cloud)
- Обновления планов от оператора

**Синхронизация при восстановлении:**
- Робот буферизует телеметрию и события в локальный Redis/файл
- При восстановлении связи — пакетная отправка буферизованных данных
- Orchestrator обновляет состояние робота и при необходимости корректирует план

### Кластеризация критичных компонентов

**MQTT Broker (EMQX):**
- Минимум 2 узла в кластере
- Static discovery или DNS-based обнаружение
- Сессии реплицируются между узлами
- При падении одного узла — автоматическое переподключение клиентов к оставшимся

**RabbitMQ:**
- Кластер из 3 узлов с quorum queues
- Автоматический failover при потере одного узла
- Mirrored queues для критичных очередей

**Redis:**
- Redis Sentinel: 3 sentinel-узла, 1 master + 2 replicas
- Автоматический failover за 5–30 секунд
- Приложения используют sentinel-aware клиенты

**PostgreSQL:**
- Master + 2 streaming replicas
- Patroni или Stolon для автоматического failover
- Read-write splitting через PgBouncer

## Disaster Recovery

### Резервное копирование

| Компонент | Частота | Метод | Хранение | Время восстановления |
|-----------|---------|-------|----------|---------------------|
| PostgreSQL | Ежечасно | pg_dump + WAL archiving | MinIO | < 30 минут |
| InfluxDB | Ежедневно | Snapshot | MinIO | < 1 час |
| Neo4j | Ежедневно | Online backup | MinIO | < 1 час |
| Redis | Постоянно | RDB + AOF | Локальный том | < 5 минут |
| MinIO | — | S3 replication | Внешнее хранилище | Зависит от объёма |
| Конфигурация | Постоянно | GitOps (ArgoCD) | Git-репозиторий | < 10 минут |
| Модели AI | При изменении | Версионирование в MinIO | MinIO | < 30 минут |

### Multi-AZ развёртывание (для продакшена)

Для критичных инсталляций рекомендуется развёртывание в нескольких зонах доступности:
- Kubernetes-кластер распределён по 2–3 зонам
- Stateful-сервисы (БД, брокеры) имеют реплики в разных зонах
- DNS-based failover между зонами
- RTO (Recovery Time Objective): 5 минут
- RPO (Recovery Point Objective): 1 минута для критичных данных

### Point-in-Time Recovery

- PostgreSQL: восстановление до любого момента времени через WAL-архивы
- InfluxDB: восстановление через snapshot + continuous queries
- Модели: версионирование в MinIO с возможностью отката на любую предыдущую версию

## Планирование ёмкости

### Расчёт ресурсов по количеству роботов

| Количество роботов | MQTT Broker | Orchestrator Workers | Triton GPU | vLLM GPU | Redis RAM | PostgreSQL |
|-------------------|-------------|---------------------|------------|----------|-----------|------------|
| 10 | 1 узел | 1 worker | 1 GPU | 1 GPU | 2 ГБ | 1 инстанс |
| 100 | 2 узла | 3 workers | 2 GPU | 1 GPU | 8 ГБ | 1 master + 1 replica |
| 1 000 | 3 узла | 10 workers | 4 GPU | 2 GPU | 32 ГБ | 1 master + 2 replicas |
| 10 000 | 5 узлов | 30 workers | 8 GPU | 4 GPU | 128 ГБ | Кластер |

### Узкие места

1. **GPU-ресурсы** — основной лимитирующий фактор для AI-сервисов. Батчирование и оптимизация моделей (TensorRT, quantization) помогают снизить потребность
2. **Пропускная способность MQTT** — при 10 000 роботов с частотой 30 Гц = 300 000 сообщений/сек. EMQX кластер из 5 узлов справляется
3. **Redis RAM** — при большом количестве роботов Feature Store может потреблять значительный объём памяти. Решение: TTL на ключах, агрегация старых данных
4. **Сетевая пропускная способность** — при передаче видеопотоков с роботов в облако. Решение: сжатие на Edge, передача только ключевых кадров
