# Микросервисная архитектура

## Общие принципы декомпозиции

Система разделена на микросервисы по принципу единой ответственности (Single Responsibility). Каждый микросервис:

- Выполняет одну чётко определённую функцию
- Имеет собственное хранилище данных (Database per Service)
- Общается с другими сервисами исключительно через определённые API и брокеры сообщений
- Развёртывается и масштабируется независимо
- Имеет собственный жизненный цикл и может быть обновлён без остановки остальных

## Зависимости между сервисами

### Критические зависимости

Эти зависимости являются необходимыми для работы системы. При их отказе функциональность существенно деградирует.

- **GatewayService → RabbitMQ**: Шлюз не может передавать команды без брокера сообщений
- **Orchestrator → Redis**: Оркестратор хранит состояние планирования в Redis; без него невозможна координация
- **Orchestrator → RabbitMQ**: Получение команд от пользователя и публикация событий
- **RobotEdge → MQTT Broker**: Единственный канал связи робота с облаком
- **Orchestrator → MQTT Broker**: Отправка команд роботам

### Некритические зависимости

При отказе этих зависимостей система продолжает работать с пониженной функциональностью.

- **Orchestrator → vLLMService**: При отказе LLM — деградация до заранее определённых шаблонов команд
- **Orchestrator → TritonInference**: При отказе детекции — работа по последним известным данным
- **Orchestrator → SmolVLA Cloud**: Роботы переключаются на локальные Edge-модели
- **DataStorage (InfluxDB, Neo4j)**: Потеря исторических данных не влияет на текущее управление
- **Мониторинг**: Отказ мониторинга не влияет на работу системы

## Домены ответственности

### Домен «Пользователь»
Ответственный сервис: **GatewayService**, **Frontend**  
Включает: Аутентификация, авторизация, управление сессиями, маршрутизация запросов, WebSocket-менеджмент.

### Домен «Планирование»
Ответственный сервис: **Orchestrator**  
Включает: Понимание команд, декомпозиция задач, назначение ресурсов, генерация планов, мониторинг выполнения, перепланирование.

### Домен «AI-инференс»
Ответственные сервисы: **TritonInference**, **vLLMService**, **SmolVLA**  
Включает: Детекция объектов, трекинг, семантическая сегментация, понимание текста, генерация текста, визуальный анализ, генерация действий.

### Домен «Коммуникация»
Ответственные сервисы: **CommunicationService** (MQTT, RabbitMQ)  
Включает: Доставка сообщений, маршрутизация по топикам, гарантии доставки, управление сессиями устройств.

### Домен «Робот»
Ответственный сервис: **RobotEdge**  
Включает: Локальное управление, сбор сенсорных данных, трансляция протоколов, локальный инференс, экстренные реакции.

### Домен «Данные»
Ответственные сервисы: **DataStorage** (все БД)  
Включает: Хранение телеметрии, графовых связей, состояний, файлов, реляционных данных.

### Домен «Наблюдаемость»
Ответственные сервисы: **Prometheus**, **Grafana**, **Jaeger**, **ELK**  
Включает: Метрики, логирование, трассировка, алертинг, визуализация состояния системы.

## Взаимодействие между доменами

### Пользователь → Планирование
Поток: Пользователь вводит команду → Frontend → GatewayService (HTTP/WS) → RabbitMQ → Orchestrator

### Планирование → AI-инференс
Поток: Orchestrator запрашивает анализ → gRPC → TritonInference / vLLMService / SmolVLA Cloud → gRPC ответ → Orchestrator

### Планирование → Коммуникация → Робот
Поток: Orchestrator формирует команду → MQTT → RobotEdge → ROS2 → Актуаторы робота

### Робот → Коммуникация → Данные
Поток: Сенсоры → ROS2 → RobotEdge → MQTT → Подписчики (InfluxDB, Redis, Orchestrator, AI-сервисы)

### Робот → Локальный AI
Поток: Камера → ROS2 → Edge AI Proxy → SmolVLA Edge → Локальное действие (обход препятствия, остановка)

## Границы контекста (Bounded Contexts)

Каждый микросервис имеет собственную модель данных. Примеры различий:

- **Orchestrator** оперирует понятиями «задача», «план», «назначение», «статус выполнения»
- **RobotEdge** оперирует понятиями «нода ROS2», «топик», «действие», «сенсор»
- **TritonInference** оперирует понятиями «модель», «батч», «инференс», «детекция», «bounding box»
- **DataStorage** оперирует понятиями «запись», «индекс», «агрегация», «ключ»

Трансляция между контекстами происходит в точках интеграции (Gateway, Bridge, Adapter), которые преобразуют данные из одной модели в другую.

## Версионирование API

Все внешние API (REST, gRPC) версионируются через префикс пути или package:

- REST: `/api/v1/`, `/api/v2/`
- gRPC: `package robotcontrol.v1;`
- MQTT: Версионирование через структуру топиков: `v1/telemetry/{robot_id}/...`

При изменении контрактов поддерживается обратная совместимость минимум на одну мажорную версию. Новые потребители подключаются к новой версии, старые продолжают работать с предыдущей.
