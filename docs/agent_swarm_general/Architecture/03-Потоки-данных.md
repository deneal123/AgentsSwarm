# Потоки данных

## Основные потоки

В системе выделяются семь фундаментальных потоков данных, каждый из которых имеет свои характеристики по задержке, объёму, гарантии доставки и направлению.

---

## Поток 1: Команда пользователя (User Command Flow)

**Направление:** Пользователь → Робот  
**Задержка:** до 500 мс (включая AI-обработку)  
**Гарантия:** At Least Once  

### Последовательность шагов

1. **Ввод команды** — Пользователь вводит текст в Chat Interface фронтенда, например: *«Роботы, найдите и принесите все красные коробки в зону А»*

2. **Передача в шлюз** — Сообщение отправляется через WebSocket-соединение в GatewayService. Шлюз добавляет метаданные: идентификатор пользователя, временную метку, идентификатор трассировки (trace_id).

3. **Публикация в брокер** — GatewayService публикует сообщение в RabbitMQ в очередь `commands.user`. Формат: JSON с полями `user_id`, `text`, `timestamp`, `trace_id`, `priority`.

4. **Получение оркестратором** — Orchestrator, подписанный на очередь `commands.user`, получает сообщение и запускает граф обработки LangGraph.

5. **Интерпретация команды** — Orchestrator вызывает vLLMService через gRPC для извлечения интента и сущностей из текста. Результат: структурированное представление команды (действие, объекты, место назначения, ограничения).

6. **Сбор контекста** — Orchestrator запрашивает текущее состояние роботов из Redis (позиции, заряд, занятость, наличие манипуляторов) и при необходимости — детекции из TritonInference.

7. **Генерация плана** — На основе контекста и интерпретированной команды Orchestrator (через LangGraph + vLLM) генерирует план: список подзадач с назначением конкретных роботов.

8. **Отправка команд** — Orchestrator публикует команды в MQTT-топики: `commands/{robot_id}/action` с QoS 1. Каждая команда содержит `command_id`, `task`, `parameters`, `priority`.

9. **Получение на роботе** — Edge AI Proxy на роботе получает команду через MQTT, валидирует и при необходимости обогащает (через локальную SmolVLA).

10. **Трансляция в ROS2** — ROS2 Bridge преобразует команду в ROS2-сообщение и публикует в соответствующий топик.

11. **Обратная связь** — Фронтенд получает обновления прогресса через WebSocket: подтверждение приёма, статус «выполняется», результат.

## Поток 2: Телеметрия в реальном времени (Telemetry Flow)

**Направление:** Робот → Облако → Фронтенд  
**Задержка:** до 50 мс  
**Частота:** 1–30 Гц в зависимости от типа данных  
**Гарантия:** At Most Once (QoS 0) для регулярных данных  

### Последовательность шагов

1. **Сбор сенсорных данных** — SensorManager на роботе агрегирует данные с сенсоров (LiDAR, камеры, IMU, одометрия, батарея) и публикует в локальные ROS2-топики.

2. **Агрегация и сериализация** — ROS2 Bridge подписан на ROS2-топики. Он агрегирует данные, преобразует в унифицированный формат (MessagePack/Protobuf) и передаёт в Edge AI Proxy.

3. **Публикация в MQTT** — Edge AI Proxy публикует телеметрию в MQTT-топики:
   - `telemetry/{robot_id}/pose` — позиция и ориентация (10–30 Гц)
   - `telemetry/{robot_id}/battery` — заряд батареи (0.1 Гц)
   - `telemetry/{robot_id}/sensors` — данные сенсоров (5–10 Гц)
   - `telemetry/{robot_id}/camera` — сжатые изображения (1–5 Гц)

4. **Распределение подписчикам** — MQTT Broker (EMQX) рассылает сообщения подписчикам:
   - **InfluxDB** — долговременное хранение для аналитики
   - **Redis** — обновление кэша текущего состояния робота (ключ `robot:{id}:latest`)
   - **Orchestrator** — мониторинг выполнения задач
   - **Data Aggregation Service** — нормализация и обогащение данных

5. **Обновление фронтенда** — GatewayService подписан на Redis Pub/Sub (канал `robot:{id}:updates`). При получении обновления — пересылает клиенту через WebSocket.

6. **3D-визуализация** — Frontend получает данные о позициях и обновляет 3D-сцену в реальном времени.

### Оптимизация объёма

- Телеметрия позиции отправляется с максимальной частотой (до 30 Гц) только при движении робота; в покое — 1 Гц
- Изображения с камер отправляются в облако только по запросу или при обнаружении значимого события на Edge
- Данные сенсоров сжимаются (MessagePack даёт ~30% выигрыш по сравнению с JSON)

## Поток 3: Компьютерное зрение (Vision Pipeline Flow)

**Направление:** Робот → Triton → Feature Store → Orchestrator  
**Задержка:** 100–500 мс  
**Гарантия:** Best Effort для регулярных кадров, At Least Once для запросов  

### Последовательность шагов

1. **Захват изображения** — Камера робота захватывает кадр, SensorManager публикует в ROS2-топик `/camera/image_raw`.

2. **Локальная предобработка (Edge)** — SmolVLA Edge на роботе выполняет быструю детекцию (Tiny YOLO) для обнаружения непосредственных угроз. Если угроза обнаружена — немедленная локальная реакция (см. Поток 5).

3. **Отправка в облако** — Если требуется детальный анализ, Edge AI Proxy отправляет кадр в облачный TritonInference через gRPC Streaming (для тяжёлых кадров) или MQTT (для сжатых изображений).

4. **Детекция объектов** — Triton запускает YOLO v8 для детекции объектов: определяет классы, bounding boxes и confidence scores.

5. **Трекинг** — Результаты детекции подаются в трекер (ByteTrack / DeepSORT) для сопоставления с предыдущими кадрами и присвоения идентификаторов отслеживаемым объектам.

6. **Сохранение результатов** — Детекции записываются в Redis Feature Store (ключ `robot:{id}:detections:latest`) и в Neo4j (граф связей: робот обнаружил объект X в координатах Y).

7. **Уведомление оркестратора** — Через Redis Pub/Sub (или MQTT) Orchestrator получает уведомление о новых детекциях. Если есть активная задача поиска — обновляет план.

8. **Визуализация** — Результаты детекции отправляются на фронтенд через WebSocket для отображения на дашборде.

## Поток 4: AI-планирование (Planning Flow)

**Направление:** Orchestrator ↔ AI-сервисы ↔ Feature Store  
**Задержка:** 1–10 секунд (для сложных планов)  
**Гарантия:** Exactly Once (идемпотентные операции)  

### Последовательность шагов

1. **Триггер планирования** — Инициируется командой пользователя, критическим событием, завершением подзадачи или таймером перепланирования.

2. **Сбор контекста** — Orchestrator собирает из Redis:
   - Текущие позиции и статусы всех роботов
   - Последние результаты детекций
   - Активные задачи и их прогресс
   - Ресурсы роботов (заряд, манипуляторы, скорость)

3. **Запрос к vLLM** — Orchestrator формирует промпт с контекстом и отправляет в vLLMService через gRPC для генерации плана высокого уровня.

4. **Запрос к SmolVLA (при необходимости)** — Для задач, требующих визуального понимания манипуляций, Orchestrator отправляет запрос в SmolVLA Cloud: «как лучше захватить объект X в данных условиях».

5. **Декомпозиция задач** — На основе ответов AI-моделей Orchestrator разбивает план на конкретные подзадачи с назначением роботов.

6. **Поиск похожих ситуаций** — Через Redis Vector Store выполняется поиск исторически похожих ситуаций для уточнения плана (если такие были успешно выполнены ранее).

7. **Утверждение плана** — План записывается в PostgreSQL (таблица `tasks`) и Redis (ключ `plan:{plan_id}`), статус каждой подзадачи — «назначена».

8. **Диспетчеризация** — Подзадачи отправляются роботам через MQTT (см. Поток 1, шаги 8–10).

## Поток 5: Экстренная ситуация (Emergency Flow)

**Направление:** Робот (Edge) → Облако → Все компоненты  
**Задержка:** Локальная реакция < 10 мс; облачная < 100 мс  
**Гарантия:** QoS 2 (Exactly Once) для MQTT  

### Последовательность шагов

1. **Обнаружение угрозы** — SmolVLA Edge или Tiny YOLO на роботе обнаруживает критическую ситуацию: человек на пути, препятствие в опасной близости, критический уровень заряда, аппаратная неисправность.

2. **Немедленная локальная реакция** — RobotEdge мгновенно выполняет экстренную остановку через ActuatorManager, не дожидаясь подтверждения из облака. Это занимает менее 10 мс.

3. **Публикация экстренного события** — Edge AI Proxy публикует событие в MQTT с QoS 2: `events/{robot_id}/emergency` с описанием инцидента, координатами и временной меткой.

4. **Получение оркестратором** — Orchestrator получает событие с приоритетом «критический». Прерывает текущее планирование.

5. **Анализ ситуации** — Orchestrator запрашивает vLLM для анализа: «человек обнаружен на пути робота 3 в координатах X,Y; как безопасно продолжить выполнение?»

6. **Перепланирование** — Orchestrator генерирует обновлённый план с обходом опасной зоны или приостановкой задачи. Оповещает соседних роботов о изменениях.

7. **Уведомление оператора** — Через RabbitMQ → GatewayService → WebSocket — оператор видит всплывающее уведомление с деталями инцидента на дашборде.

8. **Логирование** — Инцидент записывается в PostgreSQL (таблица `incidents`), InfluxDB (телеметрия вокруг инцидента) и Elasticsearch (полный лог).

## Поток 6: Обновление моделей (Model Update Flow)

**Направление:** Облако → Робот  
**Задержка:** минуты (фоновый процесс)  
**Гарантия:** At Least Once с подтверждением  

### Последовательность шагов

1. **Обучение новой модели** — Новая версия SmolVLA Edge обучена в облаке на данных, собранных от роботов. Модель загружена в MinIO с метаданными версии.

2. **Решение о развёртывании** — Orchestrator (или специальный Model Management Service) принимает решение о раскатке: на все роботы, на группу, или на конкретного робота.

3. **Отправка команды обновления** — Публикуется команда в MQTT: `commands/{robot_id}/update_model` с URL модели в MinIO, хэшем для проверки целостности и параметрами конфигурации.

4. **Скачивание модели** — RobotEdge скачивает модель из MinIO через HTTP, проверяет контрольную сумму.

5. **Горячая замена** — Edge AI Proxy загружает новую модель в рантайм. Старая модель остаётся доступной как fallback.

6. **Подтверждение** — Робот публикует подтверждение: `events/{robot_id}/model_updated` с версией и результатами self-test.

7. **A/B тестирование** — Часть роботов может работать на новой модели, часть — на старой, для сравнения эффективности.

## Поток 7: Мониторинг и наблюдаемость (Observability Flow)

**Направление:** Все компоненты → Мониторинг  
**Задержка:** 10–30 секунд (интервал скрапинга Prometheus)  
**Гарантия:** Best Effort  

### Последовательность шагов

1. **Экспорт метрик** — Каждый микросервис предоставляет HTTP-эндпоинт `/metrics` в формате Prometheus (количество запросов, задержки, использование ресурсов, ошибки).

2. **Скрапинг** — Prometheus опрашивает все эндпоинты с интервалом 10–30 секунд и сохраняет в TSDB.

3. **Визуализация** — Grafana подключена к Prometheus и отображает предопределённые дашборды: состояние роботов, загрузка GPU, задержки, ошибки.

4. **Алертинг** — Prometheus Alertmanager генерирует оповещения при превышении пороговых значений (GPU utilization > 90%, задержка MQTT > 200 мс, робот offline > 60 сек).

5. **Структурированные логи** — Все сервисы пишут JSON-логи с `trace_id`, `robot_id`, `service_name`. Логи собираются Filebeat/Fluentd → Elasticsearch → Kibana.

6. **Трассировка** — OpenTelemetry SDK интегрирован в каждый микросервис. Span'ы передаются в Jaeger для визуализации цепочки вызовов от пользователя до робота.

|-------|----------|------------|----------|---------|-------|-----|

| Батарея | RobotEdge | Redis, InfluxDB | MQTT | 0.1 Гц | ~50 байт | 0 |
| Изображение камеры | RobotEdge | Triton | gRPC / MQTT | 1–5 Гц | ~50–500 КБ | 0 |
| Команда роботу | Orchestrator | RobotEdge | MQTT | По событию | ~1 КБ | 1 |
| Критическая команда | Orchestrator | RobotEdge | MQTT | По событию | ~1 КБ | 2 |
