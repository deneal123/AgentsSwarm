# Развёртывание и инфраструктура

## Контейнеризация

Все компоненты системы контейнеризированы с помощью Docker. Каждый микросервис имеет свой Dockerfile с multi-stage build для минимизации размера образа.

### Принципы сборки образов

- **Multi-stage builds** — разделение этапа сборки и исполнения для уменьшения финального образа
- **Минимальный базовый образ** — Alpine Linux или distroless для сервисов без GPU; NVIDIA CUDA-образы для GPU-сервисов
- **Непривилегированный пользователь** — контейнеры запускаются от пользователя без root-прав
- **Health checks** — каждый контейнер имеет встроенный healthcheck для автоматического перезапуска
- **Версионирование** — образы тегируются по git-коммиту и семантической версии

### Реестр образов

- Внутренний реестр: Harbor или GitLab Container Registry
- Сканирование образов на уязвимости: Trivy интегрирован в CI/CD
- Подпись образов: Cosign для верификации целостности

## Оркестрация: Kubernetes

### Структура namespace'ов

| Namespace | Компоненты | Описание |
|-----------|-----------|----------|
| `frontend` | Frontend deployment, Nginx Ingress | Пользовательский интерфейс |
| `gateway` | GatewayService | API-шлюз |
| `orchestration` | Orchestrator, Celery Workers | Планирование и координация |
| `ai-inference` | Triton, vLLM, SmolVLA Cloud | GPU-ускоренные AI-сервисы |
| `communication` | EMQX, RabbitMQ | Брокеры сообщений |
| `data` | PostgreSQL, InfluxDB, Neo4j, Redis, MinIO | Хранилища данных |
| `monitoring` | Prometheus, Grafana, Jaeger, ELK | Наблюдаемость |

### Kubernetes-ресурсы по компонентам

**Stateless-сервисы (Deployments):**
- GatewayService, Orchestrator Workers, Triton, vLLM, SmolVLA Cloud
- Управляются через Deployment + HPA (Horizontal Pod Autoscaler)
- Rolling Update стратегия для zero-downtime обновлений

**Stateful-сервисы (StatefulSets):**
- EMQX, RabbitMQ, PostgreSQL, InfluxDB, Neo4j, Redis
- Управляются через StatefulSet с PersistentVolumeClaims
- Ordered, graceful deployment и scaling

### GPU-ресурсы

GPU-сервисы (Triton, vLLM, SmolVLA) требуют специальной конфигурации:
- Kubernetes Device Plugin для NVIDIA GPU
- Node Selectors или Node Affinity для размещения на GPU-узлах
- Запрос GPU-ресурсов через `nvidia.com/gpu: 1` в ресурсных лимитах
- NVIDIA GPU Operator для автоматического управления драйверами и runtime

### Ingress

- Nginx Ingress Controller или Traefik
- TLS-терминация на уровне Ingress
- Маршрутизация:
  - `/` → Frontend
  - `/api/` → GatewayService
  - `/ws/` → GatewayService (WebSocket upgrade)

## Docker Compose (среда разработки)

Для локальной разработки используется Docker Compose, воспроизводящий архитектуру продакшена в упрощённом виде.

### Состав сервисов в dev-среде

- **emqx** — одиночный MQTT-брокер (порты: 1883, 8083, 18083)
- **rabbitmq** — одиночный RabbitMQ с management plugin (порты: 5672, 15672)
- **postgres** — PostgreSQL с начальной миграцией (порт: 5432)
- **influxdb** — InfluxDB (порт: 8086)
- **neo4j** — Neo4j (порты: 7474, 7687)
- **redis** — Redis Stack с RedisSearch и RedisJSON (порты: 6379, 8001)
- **minio** — MinIO (порты: 9000, 9001)
- **triton** — Triton Inference Server (порты: 8000, 8001, 8002) — требует GPU
- **vllm** — vLLM Server (порт: 8003) — требует GPU
- **orchestrator** — Orchestrator + Celery Worker
- **api-gateway** — GatewayService (порт: 8005)
- **frontend** — React-приложение (порт: 3000)

### Volumes

- `postgres_data` — данные PostgreSQL
- `influxdb_data` — данные InfluxDB
- `neo4j_data` — данные Neo4j
- `redis_data` — данные Redis
- `minio_data` — данные MinIO
- `model_store` — хранилище AI-моделей для Triton

## CI/CD

### Пайплайн

Рекомендуемый CI/CD пайплайн (GitHub Actions или GitLab CI):

**Этап 1: Lint & Test**
- Линтинг кода (ruff/flake8 для Python, eslint для TypeScript)
- Юнит-тесты каждого микросервиса
- Статический анализ (mypy, bandit)
- Проверка Protobuf-контрактов

**Этап 2: Build**
- Сборка Docker-образов (multi-stage)
- Тегирование: `{service}:{git-sha}` и `{service}:{semver}`
- Пуш в Container Registry

**Этап 3: Security Scan**
- Сканирование образов на уязвимости (Trivy)
- Проверка зависимостей (pip-audit, npm audit)
- SAST (Static Application Security Testing)

**Этап 4: Integration Tests**
- Развёртывание в тестовой среде через Docker Compose
- Интеграционные тесты (API, MQTT, gRPC)
- E2E тесты с симулированными роботами

**Этап 5: Deploy**
- Обновление Helm charts
- Развёртывание в staging-среде
- Smoke tests
- Canary deployment в продакшен (10% трафика)
- Полный rollout при отсутствии ошибок

### GitOps

- Инфраструктура описана как код (Helm charts, Terraform)
- ArgoCD синхронизирует состояние кластера с Git-репозиторием
- Все изменения через Pull Request с ревью
- Автоматический rollback при обнаружении проблем

## Конфигурация

### Управление конфигурацией

- **Kubernetes ConfigMaps** — для неконфиденциальных настроек (URLs, параметры, feature flags)
- **Kubernetes Secrets** — для конфиденциальных данных (пароли, сертификаты, API-ключи)
- **Переменные окружения** — основной способ передачи конфигурации в контейнеры
- **Feature Flags** — управляются через Redis или специализированный сервис (LaunchDarkly, Unleash)

### Переменные окружения (основные)

Каждый микросервис ожидает следующие переменные:

**Общие:**
- `SERVICE_NAME` — имя сервиса для логирования
- `LOG_LEVEL` — уровень логирования (DEBUG, INFO, WARNING, ERROR)
- `TRACE_ENABLED` — включение трассировки (true/false)
- `JAEGER_ENDPOINT` — URL коллектора Jaeger

**GatewayService:**
- `RABBITMQ_URL` — строка подключения к RabbitMQ
- `REDIS_URL` — строка подключения к Redis
- `JWT_SECRET` — секрет для подписи JWT

**Orchestrator:**
- `RABBITMQ_URL`, `REDIS_URL`, `POSTGRES_URL`
- `MQTT_BROKER` — адрес MQTT-брокера
- `TRITON_URL` — адрес Triton gRPC
- `VLLM_URL` — адрес vLLM gRPC
- `SMOLVLA_URL` — адрес SmolVLA gRPC

**Triton:**
- `MODEL_REPOSITORY` — путь к хранилищу моделей
- `MODEL_CONTROL_MODE` — режим обновления моделей (poll/explicit)

## Физическая инфраструктура

### Облачный/серверный контур

Минимальная конфигурация для продакшена:

| Узел | Количество | CPU | RAM | GPU | Диск | Назначение |
|------|-----------|-----|-----|-----|------|------------|
| Master-узел K8s | 3 | 4 | 16 ГБ | — | 100 ГБ SSD | Control plane |
| Worker-узел (общий) | 3–5 | 8 | 32 ГБ | — | 200 ГБ SSD | Stateless сервисы, брокеры |
| Worker-узел (GPU) | 2–4 | 8 | 64 ГБ | 1× A100/A10G | 500 ГБ NVMe | AI Inference |
| Worker-узел (данные) | 3 | 8 | 64 ГБ | — | 1 ТБ NVMe | БД, хранилища |

### Краевой контур (на роботе)

| Компонент | Варианты | CPU | RAM | GPU | Диск |
|-----------|---------|-----|-----|-----|------|
| NVIDIA Jetson Orin Nano | Рекомендуемый | 6 ARM cores | 8 ГБ | Ampere GPU | 64 ГБ eMMC |
| NVIDIA Jetson AGX Orin | Высокая производительность | 12 ARM cores | 32 ГБ | Ampere GPU | 64 ГБ eMMC |
| Intel NUC | Без GPU (CPU inference) | 4 x86 cores | 16 ГБ | — | 256 ГБ SSD |

### Сетевая инфраструктура

- **Облако ↔ Роботы:** Wi-Fi 6 / 5G / Ethernet (в зависимости от среды)
- **Между узлами K8s:** 10 Gbps Ethernet
- **Внутри робота:** USB 3.0, CAN bus, Ethernet (для сенсоров и актуаторов)
