# Безопасность

## Модель угроз

### Поверхность атаки

| Вектор | Описание | Критичность |
|--------|----------|-------------|
| Перехват MQTT-трафика | Злоумышленник перехватывает команды или телеметрию между роботом и облаком | Критическая |
| Подмена команд | Несанкционированная отправка команд роботам | Критическая |
| Несанкционированный доступ к API | Доступ к REST/WebSocket API без аутентификации | Высокая |
| Компрометация Edge-устройства | Физический доступ к бортовому компьютеру робота | Высокая |
| DDoS на MQTT-брокер | Перегрузка брокера сообщениями | Средняя |
| Утечка данных из хранилищ | Несанкционированный доступ к базам данных | Высокая |
| Подмена модели при обновлении | Загрузка вредоносной модели на робота | Критическая |

## Транспортная безопасность

### Шифрование соединений

Все внешние соединения (между облаком и роботами, между клиентом и сервером) обязательно шифруются через TLS 1.3.

**MQTT (робот ↔ облако):**
- Протокол: MQTTS (MQTT over TLS 1.3)
- Порт: 8883 (вместо 1883)
- Требование: клиентский сертификат X.509 для каждого робота
- Поддержка: mutual TLS (mTLS) — и сервер, и клиент подтверждают свою идентичность

**WebSocket (фронтенд ↔ шлюз):**
- Протокол: WSS (WebSocket over TLS)
- Сертификат: серверный TLS-сертификат (Let's Encrypt или внутренний CA)

**gRPC (сервис ↔ сервис):**
- В продакшен-среде: mTLS между всеми микросервисами
- В dev-среде: допускается insecure для упрощения отладки
- Управление сертификатами: через Service Mesh (Istio) или Kubernetes Secrets

**HTTP (REST API):**
- Только HTTPS
- HSTS-заголовки для принудительного перенаправления

## Аутентификация

### Пользователи (операторы)

**Механизм:** JWT (JSON Web Token)

- Пользователь аутентифицируется через логин/пароль (или SSO)
- GatewayService выдаёт JWT-токен с полями: `user_id`, `role`, `exp` (срок действия)
- Токен передаётся в заголовке `Authorization: Bearer <token>` для REST-запросов
- Для WebSocket: токен передаётся при установке соединения (в query-параметре или первом сообщении)
- Срок действия access-токена: 15 минут
- Refresh-токен: 7 дней, хранится в HttpOnly cookie

### Роботы (устройства)

**Механизм:** Клиентские сертификаты X.509 + токены регистрации

- При первичной регистрации робота генерируется уникальный клиентский сертификат
- Сертификат прошивается в Edge-устройство при развёртывании
- MQTT-брокер (EMQX) проверяет клиентский сертификат при подключении
- Дополнительно: MQTT username/password как второй фактор
- При компрометации — сертификат отзывается через CRL или OCSP

### Микросервисы (service-to-service)

**Механизм:** mTLS + Service Account Tokens

- Каждый микросервис имеет свой сертификат, выданный внутренним Certificate Authority
- В Kubernetes: используются ServiceAccount и TokenReview для авторизации
- Управление сертификатами: автоматическая ротация через cert-manager

## Авторизация

### Модель: RBAC (Role-Based Access Control)

| Роль | Описание | Права |
|------|----------|-------|
| **admin** | Администратор системы | Полный доступ: управление пользователями, роботами, конфигурацией, моделями |
| **operator** | Оператор роя | Отправка команд, просмотр телеметрии, управление задачами |
| **viewer** | Наблюдатель | Только чтение: просмотр дашборда, телеметрии, статусов |
| **robot** | Устройство (робот) | Публикация телеметрии в свои топики, получение команд из своих топиков |

### MQTT ACL (Access Control List)

Роботы имеют ограниченный доступ к топикам:

**Робот `robot_001` может:**
- Публиковать в: `telemetry/robot_001/#`, `events/robot_001/#`, `ack/robot_001/#`, `status/robot_001/#`
- Подписываться на: `commands/robot_001/#`, `commands/broadcast`, `ai/robot_001/responses`

**Робот `robot_001` НЕ может:**
- Публиковать в топики других роботов
- Подписываться на телеметрию других роботов
- Подписываться на `commands/broadcast` (только получение, не публикация)

### REST API авторизация

Каждый эндпоинт имеет минимально необходимую роль:
- `GET /api/v1/robots` — viewer, operator, admin
- `POST /api/v1/tasks` — operator, admin
- `DELETE /api/v1/robots/{id}` — admin
- `PUT /api/v1/config` — admin

## Защита данных

### Шифрование данных в покое (at rest)

- **PostgreSQL:** Transparent Data Encryption (TDE) или шифрование на уровне диска (LUKS)
- **MinIO:** Server-Side Encryption (SSE-S3 или SSE-KMS)
- **Redis:** Шифрование не применяется (данные эфемерные, доступ только из внутренней сети)
- **InfluxDB:** Шифрование на уровне диска

### Управление секретами

- Все секреты (пароли БД, API-ключи, сертификаты) хранятся в Kubernetes Secrets
- В продакшене рекомендуется использование HashiCorp Vault для централизованного управления
- Запрещено: хранение секретов в коде, конфигурационных файлах или переменных окружения в открытом виде

### Персональные данные

- Система не собирает персональные данные пользователей сверх необходимого (username, role)
- Данные камер роботов: хранятся во внутреннем хранилище (MinIO), доступ ограничен ролями
- При обнаружении людей на камерах — координаты фиксируются для безопасности, изображения лиц не сохраняются

## Сетевая безопасность

### Сегментация сети

В Kubernetes используются Network Policies для изоляции:

- **Frontend namespace:** доступ только к GatewayService
- **Gateway namespace:** доступ к RabbitMQ, Redis, Orchestrator
- **AI namespace:** доступ только от Orchestrator (gRPC)
- **Data namespace:** доступ только от авторизованных сервисов
- **MQTT namespace:** доступ от GatewayService, Orchestrator и внешних роботов

### Zero-Trust между микросервисами

- Каждый запрос между сервисами аутентифицируется через mTLS
- Service Mesh (Istio) обеспечивает автоматическое управление сертификатами и политиками доступа
- Принцип наименьших привилегий: сервис имеет доступ только к тем ресурсам, которые ему необходимы

### Защита от DDoS

- Rate limiting на уровне GatewayService: максимум 100 запросов/секунду на пользователя
- Rate limiting MQTT-публикаций: максимальная частота сообщений на робота настраивается в EMQX
- Ingress Controller (Nginx/Traefik) с настройками connection limiting

## Безопасность моделей

### Обновление моделей на Edge

При обновлении моделей на роботах критически важна защита от подмены:

1. **Подпись модели** — каждая модель подписывается приватным ключом в облаке
2. **Верификация на Edge** — перед загрузкой модели робот проверяет цифровую подпись публичным ключом
3. **Контрольная сумма** — SHA-256 хэш передаётся в команде обновления, проверяется после скачивания
4. **HTTPS для загрузки** — модель скачивается из MinIO через HTTPS
5. **Rollback** — при неудачной верификации робот остаётся на предыдущей версии модели

### Защита промптов

- Системные промпты для vLLM хранятся в защищённом хранилище
- Пользовательский ввод проходит санитизацию для предотвращения prompt injection
- Логирование всех запросов к LLM для аудита

## Аудит и журналирование

### Что логируется

- Все действия пользователей (вход, команды, изменения конфигурации)
- Все команды, отправленные роботам
- Подключения и отключения роботов
- Экстренные события и инциденты
- Изменения прав доступа
- Обновления моделей

### Хранение аудит-логов

- Аудит-логи хранятся в отдельном индексе Elasticsearch
- Период хранения: минимум 1 год
- Доступ к аудит-логам: только роль admin
- Целостность: логи подписываются для предотвращения модификации
